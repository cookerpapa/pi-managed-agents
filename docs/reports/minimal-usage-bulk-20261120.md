# 会话累计用量的单行与多行写入

两种写法都保留每个 Conversation 的一行 `pi.usage`。Pi 计算完整累计值，PG 同时保存原生文档身份、提交位置和累计 JSON。逐行组在已有事务里为每次更新执行一条用量写入语句。多行组在同一分区批次内先确认每条源消息，至少两条用量更新且 Conversation 键互不相同时再一起写入。批次内存在重复键时保留原有逐条位置校验。单次对话的连续两条更新不能因为合并而跳过中间冲突。

## 压缩与用量的关系

固定的 Pi Durable 1.0 在准备模型请求时检查当前上下文。它从上次压缩标记之后，寻找最近一条有有效使用量的助手消息，用该回复的上下文 token 数作基准，再估算后来加入的消息和本次待加入的内容。没有可用基准时估算当前消息。累计多次请求得到的 Conversation 总数供用量查询。摘要请求本身消耗的 tokens 也会进入累计文档。两种 SQL 都保留完整助手 Entry 与累计值。 [阈值判断](https://github.com/earendil-works/pi/blob/v1.0.0/packages/durable/src/harness/generation.ts) · [上下文估算](https://github.com/earendil-works/pi/blob/v1.0.0/packages/durable/src/harness/compaction.ts)

## 测量口径

每份固定输入分别重复用于两种写法，在两套隔离资源上反转交错顺序。每轮投影 256 个 Run 的 51,200 条计数消息及其开头和收尾，核验全部 51,712 条正文摘要、终态、256 个累计值及其提交位置，PG 默认同步，被测可重放历史事务局部使用异步提交。每轮累计行都写入 26,112 次。用量 SQL 条数按已经成功执行的事务和实际选择的语句路径统计。WAL 取隔离 PG 实例测量前后的差值，表占用在测量结束后读取。详情见[实验入口](../../scripts/experiments/minimal-session-storage/README.md)和[上一次按开关对照的结果](minimal-projection-usage-20261120.md)。

## 实测

每个速率、每种写法各 4 个样本。每行数据先按各轮原始值计算，下表显示中位数。完整积压组在所有消息收到 Kafka 确认后才开始计时。

| 指标 | 逐行 | 多行候选 |
|---|---:|---:|
| 每秒计划 2,315 条，每轮用量 SQL 数 | 26,112 | 25,483 |
| 每秒计划 6,000 条，每轮用量 SQL 数 | 26,112 | 5,459 |
| 已有积压，每轮用量 SQL 数 | 26,112 | 3,409 |
| 已有积压，排空速度（条/秒） | 2,416 | 7,169 |

在 6,000 条/秒档，8 轮中有 3 轮的发送端迟到 P95 达 9.46–27.11 秒，接近同轮的端到端 P95。针对确实按期送入的其余 5 轮（发送迟到 P95 低于 2 ms），逐行端到端 P95 分别为 318、435 ms，多行分别为 152、192、366 ms。在反转顺序的夹具中，按期送入的逐行和多行分别为 318 和 366 ms。所有轮次以及异常都纳入原始数据。低档第一套夹具曾出现逐行 P95 10.62、14.47 秒，发送端迟到约 1.6 ms，采样积压峰值 12,954、16,214 条；另一套低档的两个写法均为 23–33 ms。第一套低档观察到的是投影排队，未从端到端指标定位到单条 SQL 或磁盘。

预装积压的逐行吞吐为 2,319–7,303 条/秒，多行为 6,428–7,455 条/秒。投影计时排除了预装时间，但仅发送同一份输入时的速度也波动很大。两组此前在相同主机上采取逐行写法时已经测到每秒约 6,300–7,100 条。单机两组中位数的倍数不能作为可以复现的 SQL 加速比。

两种写法都在每轮 26,112 次写入后保留 256 行。使用 `pg_column_size` 测得最新用量值合计均为 92,672 字节（90.5 KiB，每个 Conversation 362 字节）。`pg_total_relation_size` 包括索引、表页空闲空间等，逐行的轮末值为 352–464 KiB，多行为 272–400 KiB。物理占用受页复用、MVCC 旧版本、清理时机等影响，这组短测不能推算长期表大小。各组 12 轮的整个实例 WAL 写入量相差不到 0.01%，与上轮“存用量比完全不存多写约 3.9% WAL”的对照口径不同。

原生 Harness 小窗口实测中，阻塞压缩阈值为 3,584。会话累计 4,211 tokens、最近的助手回复报告 413 tokens 时，继续短问答没有压缩。加入一段足以超出窗口的长输入后，Pi 自动提交了一次摘要。该检查使用真实 Harness 和本地模拟模型。

## 固定输入的 PG 对照与决定

为区分执行 SQL 的成本和整条链路的等待，在单独的 PG 17.6 上复用同一个长连接、同一份已编码正文和实际投影 SQL。每个样本包含 64 个已准备好的事务，每笔 16 条消息、8 个独立 Conversation 的用量更新。每样本都检查 1,024 条消息和 16 个最新累计值。预热两种写法，再测 12 对，每对交换先后次序。计时覆盖客户端提交到 PG 返回；这里没有 Kafka、排队、活跃 Run 检查点更新，也没有 12 个连接的竞争。逐行和多行样本总耗时的中位数分别为 900.9 和 899.0 ms。多行在 12 对中快了 5 对，逐对耗时变化的中位数为多行慢 1.0%。[固定批次数据](minimal-usage-fixed-prefix-20261120.json)

**保留原型默认的逐行覆盖。** 多行写入能稳定减少内部 SQL 条数，现有测量不足以证明能稳定提高 PG 本身的速度，也没有减少 WAL。候选写法保留在显式实验参数中。当前方案继续在收到累计值的同一事务更新最新行，正文保留单次回复用量，查询和恢复语义一致。本次只验证原型。28 项原型辅助测试、8 项真实数据库／传输及用量回归测试通过。临时实例、Topic、消费组和压测数据库均已清理。
