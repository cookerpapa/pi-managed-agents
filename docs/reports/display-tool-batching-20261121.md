# #52 · 带网页展示事件的工具意图有多少能合批？

## 实验条件

本轮原型让同一 Bash 的工具意图、原生 `pi.live` 的 pending → running 变化及单独一个 `tool.started` 展示事件一起通过准入。网页事件仍引用原始 Task 的参数。Projector 逐条检查任务、会话及引用，PG 成功后才向展示观察器依次交付，并在 Kafka 许可确认后向沙箱发出命令。测试使用真正的 Pi 展示器和事件解析器，观察器核对事件、顺序、归属与工具输入。这里没有启动浏览器或将 SSE 客户端网络时间计入结果。其他展示、输入确认、封口仍截断这一批。

32 个 Kafka 分区，三副本，一个 Projector，12 条 PG 连接，4,000 个独立模拟沙箱各持有一条 WebSocket，接单延迟 100 毫秒。同一分区只合并眼下已经就绪的连续意图，单目标最多一个未收回执的发送，全局最多 3,072 个。数据、计时和故障检查均在隔离实验环境进行。与[上一轮](pg-tool-intent-batch-20261121.md)相比，带展示的记录沿用原型已有的同步 PG 提交策略。本轮同一组内各上限使用相同策略。

## 连续工具意图

每轮 32,000 条，每个目标 8 条。采用一次实际 Pi Bash 提交的结构，重绑定操作身份，使用正式展示器生成事件。提前准备待执行槽，计时只覆盖投影、派发与接单回执。稳定输入计划 4,600 条/秒，各轮源端实发 4,587～4,592 条/秒。每档正序和逆序各一次。

| 上限 | 均匀输入收齐回执（条/秒） | 预装 Kafka 后排空（条/秒） |
|---|---:|---:|
| 4 | 2,905～3,166 | 2,729～2,739 |
| 8 | 4,448～4,471 | 3,913～4,302 |
| 16 | 4,490～4,492 | 5,399～5,720 |
| 24 | 未在均匀输入组测量 | 5,309～5,669 |
| 32 | 4,488～4,492 | 6,582～6,862 |

均匀输入按预定起点至最后一条回执计时，包含收尾延迟；上限 8、16、32 的实际平均批长只有 5.4～6.1。上限 4 时积压采样峰值为 6,684～8,717 条，其他三档为 254～764 条。宽度 1 另做了 8,000 条的短冒烟对照，收齐速率 1,150 条/秒。不同轮长的数据不用于计算严格的提速比。

## 更大的上限

单独在实验分支为显式启用有序许可的消费者放宽可配置范围，预取和派发的内存限制保持原设置。在同一个新的 Kafka Topic 上按 32、64、128、128、64、32 的顺序比较，每轮预装 32,000 条。宽档试验的读取窗口上限设为 128，表内另测的两轮 32 是这一组的对照。

| 上限 | 排空吞吐（条/秒） | 每个事务平均包含 | 观察到的最长批次 | 峰值已占派发名额 |
|---|---:|---:|---:|---:|
| 32 | 5,916～6,396 | 23.5～23.6 | 32 | 2,206～2,345 |
| 64 | 6,520～6,665 | 32.1～33.2 | 64 | 3,072 |
| 128 | 6,172～6,245 | 33.7～34.6 | 106 | 3,072 |

在同一组两轮对照中，64 的排空速率都最高。之前一组的 32 也出现过 6,862 条/秒，跨轮次波动足以覆盖相邻档位的部分差距。工具消息平均约 1,861 字节，预取还有逐条记账开销，每批现成记录合计有 256 KiB 的限制。上限 128 下实际最长 106；相较于 64，平均每批只多约两条。最多等待发送名额的分区由 2 个变为 17～22 个。这些数字没有证明更大的单批能提高容量。越大的派发许可，在确认后、发送中途失去分区时，也允许越多未发命令保留为结果未知。

## 完整 Pi 会话中的批次

在一个采集进程中并发运行 128 个固定 Pi Harness，累计 4,000 个独立会话。每个会话接收一条用户输入，经模拟模型调用一次固定 Bash，再由模型输出最终文字。模型和工具有不同的等待时间。完整记录包括原生存储提交、网页事件、工具结果和 Run 收尾。按 Session key 写入同一套 32 分区 Kafka，逐一核对接收端身份、数据库完成行、正式 Tool Result 条数、展示次数和 Kafka 位置。

第一组用 Pi 内存存储采集原始提交顺序。4,000 个会话一共 64,000 条记录，包含各 4,000 个 `tool.started`、`tool.completed` 和 `assistant.text.delta`。所有工具意图都符合合批形状；按分区观察，恰好没有相邻的两条工具意图。对同一份记录按约 4,600 条 **Kafka 记录**/秒回放，上限 8 和 32 都形成 4,000 个单条工具事务。包括其他投影在内，两轮均完成 48,000 个 PG 事务。此时“整条流每秒 4,600 条”与“每秒 4,600 条工具意图”的负载完全不同。内存存储能立即确认提交，另做下列真实 Kafka 确认对照。

第二组仍用相同的 Pi、模型及工具行为，但采集时每个 Session 的 Storage 必须等实际三副本 Kafka 确认，再将本次提交应用到 Pi。第一轮一边生成一边投影，接着对相同顺序、相同字节做 8、32 两次定速回放。三次都经过实际 PG 和 Kafka 派发许可。模型与工具执行均为替身，采样保留 Pi 本身的输入、原生任务交接、结果及结束过程，没有使用用户会话。

同一分区中有 256/4,000（6.4%）个意图紧邻另一个意图，最长连续 4 条。这是忽略“是否同时已经取到”时的理论上限。按真实 Kafka ACK 节奏在线投影时，上限 8 得到 3,832 个单条批、62 个双条批、8 个三条批、5 个四条批。168/4,000（4.2%）个意图实际和其他会话共享了事务。工具投影因此用了 3,907 笔事务，比全部逐条少 93 笔。所有 4,000 条工具开始展示均按各自身份交付。

| 同一份真实 ACK 顺序 | 实际共享事务的工具 | 最长实际批次 | 全部 PG 事务 |
|---|---:|---:|---:|
| 采集并在线投影，上限 8 | 168 / 4,000（4.20%） | 4 | 47,907 |
| 原顺序定速回放，上限 8 | 212 / 4,000（5.30%） | 4 | 47,876 |
| 原顺序定速回放，上限 32 | 213 / 4,000（5.33%） | 4 | 47,875 |

这两轮回放源端均实际送入约 4,594 条记录/秒。从 8 增到 32，总共只再省一笔事务。对这一种短任务组成的负载，能否合批主要由同分区的相邻消息内容决定。连续工具意图排空实验则有充足的相邻记录，较大的上限有收益。该结果不能替代多工具并行、长 Agent、不同 Worker 数或线上真实流量的分布数据。

## 故障与回归

真实 PG 故障实验在批中第二个原始操作引用上制造冲突，确认事务回滚、展示和派发均未发生；随后重试成功，两条原始展示按顺序发出，重读已覆盖提交时没有重复发出。额外验证了错误的 Task、参数写入位置和带额外展示进度的记录均不能走此快路。其他回归保留了原有的 PG/Kafka 确认丢失、取消、过期 Writer、接手以及预取容量边界。128 条上限也覆盖了只发送未获许可的后缀和重放抑制测试。

首次完整混合测试遇到了夹具启动问题：这种输入不预先生成种子消息，部分空分区尚无消费组提交位置。修正热身检查后，两个完整混合试验在结束时仍核对全部分区位点。已核对本轮隔离 Topic、消费组、临时 PG 和夹具资源清理。
