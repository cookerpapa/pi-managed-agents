# PostgreSQL 提前确认提交的耗时与恢复结果

这次比较 `synchronous_commit=on` 和 `off`。前者等本地 WAL 达到持久化要求才向客户端确认，后者允许先返回成功，由后台刷 WAL。PG 仍然执行相同的 SQL、更新索引和产生 WAL。两边都开启 `fsync`，沿用默认 `commit_delay=0`、`commit_siblings=5`。这里测的是确认时间的改变，上一次测的是让多笔同步事务等待同一轮刷盘。[PG 17 异步提交语义](https://www.postgresql.org/docs/17/wal-async-commit.html) · [上次组提交对照](pg-native-group-commit-20261119.md)

## 实验边界

临时 PG 17.6 和 Projector 使用同一组可用 CPU。实验直接重新加载临时 PG 的服务端配置，在每轮开始时核对 12 条预热投影连接。全链路场景的入口、Worker 和 Projector 都连接到这台临时 PG，因而这组数据反映的是数据库整体切换的效果。线上实例单独核对。

录制 6,240 个真实 Pi Harness 处理的合成新会话，每个 Run 有一条 4 KiB 助手回答、7 条有序 Kafka 记录和 4 次独立 PG 投影写入。每轮回放从相同的已领取 Run 初始状态开始，按分区检查顺序、SQL 和参数，核对消息、Inbox 和终态内容。另测直接执行同样的 SQL，以及从用户登记、Worker 领取、模拟模型到 PG 终态的完整链路。全程在单台 WSL/K3s 上串行测量。

端到端延迟及排空计时止于客户端收到 PG 成功。测量结束后，从只读连接取一个固定的 WAL 插入位置，约每 5 ms 查询一次刷盘位置，直到覆盖它，才继续清场。这一步不主动刷盘，也不计入客户端 ACK 延迟。首次探测与最后一笔写入之间可能已经完成后台刷盘。采到的差值是实例 WAL 的观察值，不能换算成丢失的消息条数。[复现命令](../../scripts/experiments/minimal-session-storage/README.md) · [逐轮数据](pg-async-commit-20261120.json)

## 同一份录制的速度

第一组用相同录制交替回放，在 260 Run/秒下每种设置各四轮，在 520 Run/秒下每种各两轮，另以 520/s 直接执行同一批 SQL。下表是各轮范围。积压按到期但尚未处理完的记录数计算。完整链路的 P95 另从提交用户请求算起。

| 路径 / 目标 Run/秒 | 同步 ACK 的每轮 P95 | 异步 ACK 的每轮 P95 | 同步实际 Run/秒 | 异步实际 Run/秒 |
|---|---:|---:|---:|---:|
| Kafka → Projector → PG / 260 | 76–79 ms | 59–60 ms | 259.6–259.7 | 259.9 |
| Kafka → Projector → PG / 520 | 2,637–3,322 ms | 47–55 ms | 426.3–429.5 | 519.4–519.5 |
| 直接执行相同 SQL / 520 | 366–653 ms | 26 ms | 494.3–506.2 | 518.4–518.5 |
| 用户登记到 Run 结束 / 260 | 97–106 ms | 69–71 ms | 259.5–259.6 | 259.7 |

260/s 时，每秒需要 1,040 笔 PG 投影事务。同步回放每笔平均占住连接 6.06–6.22 ms，异步为 1.19–1.21 ms。两者都吃满了此轮投喂速率，所以收益体现为更快回复和更大的余量。520/s 时预算收紧到约 5.77 ms/笔，同步版出现 6,374–7,511 条记录的峰值积压，异步版是 89–191 条。主系列中两种设置的外部固定计算中位耗时在这些 Projector 回放里约为 2.2–2.4 ms。

主系列的四轮 260/s 投影回放中，同步模式在测量结束后的第一份快照都已覆盖所取的 WAL 位置。异步模式第一次检查时还有约 104–262 KiB 待刷，观察到整批插入位置被覆盖时距测量结束已有 287–364 ms。这是实例末尾的观测，不表示每条记录都有一样长的风险窗口。

## 完整链路的高负载复测

独立录制 4,160 个新 Run，反转 520/s 投影回放的起始顺序，再以 520/s 实际提交用户消息。完整链路每轮计划在 20 秒内发出 10,400 条请求。负载驱动最多同时等 384 个请求，到上限时跳过该时刻尚未发出的请求。

| 完整链路，目标 520 Run/秒 | 同步确认 | 异步确认 |
|---|---:|---:|
| 两轮实际完成 Run/秒，含排空时间 | 381.1 / 387.9 | 483.5 / 517.8 |
| 各轮用户提交到收到 PG 终态确认的 P95 | 2,174 / 1,915 ms | 1,212 / 168 ms |
| 已发出且完成 / 计划 | 16,203 / 20,800 | 20,272 / 20,800 |
| 峰值待处理 offset，两轮 | 2,401 / 2,407 | 2,127 / 47 |

这一组各轮的独立 CPU 校准中位数为 2.7–2.8 ms。异步模式提高了面向调用方的完成率，也有一轮仍积压。单独回放的复测同样可见差别，520/s 时同步实际完成 432–441 Run/秒，异步约 519。低负载的完整链路另做了 10/s 主对照，同步两轮 P95 都是 72 ms，异步为 56 和 68 ms。高压复测尾部再做的一对 260/s 完整链路，异步为 71 ms、同步为 4,398 ms；独立主机校准同时从 2.3 变为 8.6 ms，故没有用这对数字计算调参收益。

两套正式实验合计 20 轮有序回放，116,480 个 Run、465,920 次实际 PG 投影写入。所有回放最终表内容都与原始录制一致。对照在同步提交等待上的明显差异，证明这一负载有显著的事务确认成本。它并没有给出独立 CPU 瓶颈或硬件写入带宽上限。

## 故障验证

在已完成性能测量的临时 Pod 中，用同一个 PostgreSQL 二进制启动第二个私有 Unix socket 实例。它有独立数据目录，`fsync=on`、`wal_writer_delay=200ms`、`wal_writer_flush_after=1MB`。每轮先做检查点，客户端再以 32 笔独立事务写入连续编号，在数据库目录外记录全部成功回执。接着用 `pg_ctl stop -m immediate` 停止这个子实例并重启，检查基准行、恢复的编号及其顺序。Windows 主机和操作系统页缓存继续运行。[故障脚本](../../scripts/experiments/minimal-session-storage/pg-async-crash.sh) · [PG 对立即停机的说明](https://www.postgresql.org/docs/17/wal-async-commit.html)

两套正式试验中，每种模式各 6 轮。同步模式的 **192 笔已确认事务全部恢复**。异步模式同样收到 192 笔成功回执，恢复了 42 笔、丢失 150 笔；每轮恢复条数依次为 22、0、0、0、20、0，都是已确认序列的前缀。故障刻意发生在小批写入之后，不能用这个比例估算日常丢失率。

**部署判断。** 线上继续使用 `synchronous_commit=on`。性能提升来自更早允许调用方继续，后台仍要把 WAL 刷到盘上。在现有架构中，初始 Run 会先在 PG 登记并向用户确认，随后才由 Worker 领取和写入 Session Kafka 日志。若已确认的登记在这两步之间丢失，Kafka 无法补回。只对可重放的派生数据使用较弱确认，需要额外验证检查点、日志回收及外部副作用边界，这次全库参数实验未验证该设计。

实验辅助测试共 20 项通过，原组提交回归及常规会话冒烟均通过。临时实例、凭据、数据库、Topic、消费组均已清理，服务实例复查为 `synchronous_commit=on`、`fsync=on`、`commit_delay=0`、`commit_siblings=5`。
