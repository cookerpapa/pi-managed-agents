# 候选存储读路径审查与发布门槛

## 已经可以从候选库读取的子会话内容

Session API 用租户和公开的子 Session、Turn 找到所属根 Run 和物理 Pi Session，
再用子 Conversation 编号读取自己的正文、工具参数和结果。工具位置、正文和参数依赖
使用相同的范围。首条已放置的子输入用作 Turn 标题。待创建或尚未放置的子输入没有
这份正文，尚不能用这一项证明与旧的「从父工具意图读原始提示」完全相容。

验收发现第二个原因：即使正文找对了，子会话自己的展示序号仍为零，含正文的 HTTP
资源会被协议校验拒绝。现在在已有稳定投影事务中分别推进根与子会话原有的展示位置。
子会话复用 `subagent_conversations.output_display_seq` 和 `output_display_native_seq`。
纯流式片段沿用原路径。此次没有改表、加索引或保存子任务的终态。

真实 Cube / Pi / PG / RF3 验收分别通过现有双写对照与候选单写组合读取公开 API。
父会话和子会话的正文隔离。子会话有正确的输入、原 Bash 参数与结果、最终文本。
按工具 ID 定位、用包含当前位置的游标重新打开、用排除当前位置的游标向后翻页，
以及在父会话使用子游标时的拒绝，都通过同一组客户端断言。两组使用各自的
随机身份，比较的是用户可观察的结果。候选单写时仍观察到子状态为 `unknown`。
原始输入、附件、一个条目一页、运行中与已完成的工具、租户与兄弟会话隔离另有 PG 回归。

## 实测查询

隔离 PG 17.6，分别装入 8,192 和 131,072 条记录。大 Run 中每 128 条才有一条属于
被测子会话。使用真实 Kysely 读取器与其绑定参数，每个操作预热后串行读 31 次；
对一次代表性调用的每条 SQL 独立运行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。
P95 是 Node 读取器构造出返回值的耗时，包含数据库往返。下表为 13 万条记录、每页
32 条的成对实验，未并发写入。命中缓冲区也需要遍历和判断记录。

| 操作 | 修改前 P95 | 修改后 P95 | 分页元数据查询主要索引扫描中过滤的行数，前 → 后 |
| --- | ---: | ---: | ---: |
| 根会话，从中间读更早的消息 | 24.99 ms | 8.50 ms | 65,569 → 32 |
| 根会话，从中间读更晚的消息 | 26.08 ms | 7.07 ms | 65,568 → 32 |
| 稀疏子会话，读更早的消息 | 27.49 ms | 10.89 ms | 69,728 → 4,191 |
| 稀疏子会话，读更晚的消息 | 27.80 ms | 9.49 ms | 69,727 → 4,191 |

原 SQL 用「其他 Turn 或当前 Turn 符合游标条件」做过滤。对于当前长 Run，PG 从索引端点
读到了中间的游标。现在给每个 Turn 算出自己起读的提交序号与批内位置，PG 可直接在
现有索引上定位。其余 Turn 使用完整边界。含四十个 Turn 的测试独立核对了同一批次多条
消息的边界，覆盖两个方向和包含／排除锚点；返回次序和预期一致。使用产品默认每页 64 条复测，中间向前翻页的 P95 为根会话 13.72 ms、子会话 17.81 ms。

两项仍有读放大。稀疏子会话同一 Run 内仍会越过其他 Conversation 的记录。查询一个已完成
的 `task:N` 也缺少匹配的结果索引：大 Run 实验中 PG 并行扫描正文表，三个循环平均
各过滤约 43,690 行；普通 Entry 锚点可以直接用已有索引。两轮大 Run 对照中，根和子会话的工具 ID 定位 P95 约 40–47 ms。导航样本只测了指定 Conversation 的索引过滤和强制包含 Entry 的读成本；公开的多层树仍有旧读取器，不能由此认定子节点的 Turn ID 已兼容。是否给工具结果加部分索引要与
每个结果的插入成本一起权衡。此次没有用新索引改善测试结果。

## 会触及存储设计的边界

对同样两个已登记、尚未在 Pi 创建的子请求 A/B，控制夹具请求停止两者，双方都没有可用的
调用方确认。一组只让 A 的停止操作抵达真实的 `DurableAgentSession.stopConversation`；
另一组只让 B 的抵达。其余父会话轨迹、请求范围和控制关系固定。正常收尾后，候选投影涉及的
11 张表逐行相同。用实际迁移安装的 `subagent_executions` 视图、相同关系数据及原生文档
索引测试，两个子请求分别是「已取消／未知」和「未知／已取消」。候选库缺少能区分这两种
历史的长期证据，改变 SELECT 无法补全。该实验证明的是信息可区分性；RPC 丢失为受控时序，
没有测线上发生率。活动 Run 的交接快照和轮转前 Kafka 记录具有不同的保留期。
[原生对照](child-stop-evidence-20261122.json)

建议评估在既有子会话关系上按原生确认更新一份当前状态，带原生提交位置去重，在根 Run
收尾后保留已确认的结果。是否还要保留原始输入对应的回答 Entry，取决于 `result(originalInput)`
的兼容要求；活跃根 Run 中的后续输入也要能再次进入运行状态。未确认的投递保留 `unknown`。
另一种产品选择是接受缺证据时统一返回 `unknown`，并明确与旧接口的差异。两种方案都未实施。
