# 两张业务表、Pi Inbox 和独立结束信号的压测

普通一问一答没有设置随机等待。真实 Pi Durable Harness 在两个 Worker 进程中处理输入、调用本地确定性模型、生成提交并等待空闲。64 个并发客户端下，主测三次为 **164.90、158.76、163.45 Run/s**。独立 `work_finished` 在这组测试中的 PG 处理 P50 为 5.75–5.95 ms。突发登记时，通知锁显著拖慢了入口。持续高于当前处理能力时，终态记录也会排在更早的同分区记录后面。

[可复现的实验](../../scripts/experiments/minimal-session-storage/README.md) · [分组数字与源码摘要](minimal-session-storage-load-20261119.json)

## 测了哪条链路

- 驱动在独立、正常写 WAL 的 PG 17.6 数据库中登记 Run，PG 的 fsync 与同步提交开启。唯一键确保同会话的请求幂等，按会话顺序领取。两个 Worker 各在自己的 K3s Worker Pod 内运行独立测试进程，通过 PG LISTEN 和 250 ms 兜底复查发现工作，用一条带 `FOR UPDATE SKIP LOCKED` 的查询领取并记录领取身份。
- 每个被测 Run 是一个新物理 Session 中的根 Conversation。每个 Worker 复用一个真实幂等 Kafka 生产者，使用生产代码的 Session 分区算法、32 个分区、RF3、min ISR 2。Pi 的一次 `Storage.commit` 在 Kafka 确认后才应用到 Worker 内存。普通负载每个 Run 有 6 批原生提交，然后单独投递第 7 条 `work_finished`。每个会话内部串行，不同会话可以并行。
- Projector 使用维护中的原生消费者，普通单条 poll，一个消费组和 12 个 PG 连接。它按同一 Pi 批次原子投影正式消息与 Inbox 最新值，检查 Run 领取身份、原生序号和重复投递。纯 live 片段产生零 PG 操作。成功结束时检查当前 writer 和已观察到的原生末尾，单独更新 `runs.state` 及 `settled_at`。常规显式事务路径每个普通 Run 有 13 次 Projector 侧 SQL 调用，含事务命令。
- 消息、队列项、最终正文及提交顺序都在计时后逐项核验。客户端计时从发起登记，到收到 Projector 的 PG COMMIT 成功回执。登记、领取、Kafka、PG 均真实运行。入站 HTTP、网页 SSE、完整 Pi Task/Submission 持久化、跨 Worker 冷恢复、模型计量、Fork、真实沙箱均不在原型里。steer 用注册的无副作用测试工具制造真实的 post-tools 边界。追加输入的测试客户端会等对应 Pi 提交在 PG 投影完成的确认。
- 主测模型生成确定性的 4 KiB 答案。固定分片大小，服务商计时延迟为零。只有标为 10 秒的场景故意给模型一次固定等待。忙时输入场景的合成模型或工具会让出执行，直到测试输入被接纳。SQL 时间、Kafka ACK 和 OS 调度都会自然波动。

## 单个 Run 到底有多快

| 简化布局与真实 Pi | 完成 / 发起 | Run/s | 从提交到确认完成 P50 / P95 |
|---|---:|---:|---:|
| 串行，零模型延迟 | 12/12 | 18.19 | 49 / 71 ms |
| 16 并发 | 192/192 | 154.89 | 93 / 154 ms |
| 64 并发，三次 | 每次 192/192 | 164.90 / 158.76 / 163.45 | P95 为 405 / 418 / 392 ms |
| 同时发起 192 个 Run | 192/192 | 165.57 | 617 / 1,120 ms |
| 64 并发，每轮追加一次 follow-up | 192/192 | 144.04 | 404 / 509 ms |
| 64 并发，每轮在工具执行中 steer 一次 | 192/192 | 131.69 | 463 / 595 ms |
| 同时发起 192 个，每轮给模型固定等待 10 秒 | 192/192 | 17.26 | 10,596 / 11,069 ms |

串行零延迟的最快一轮是 47 ms。固定等 10 秒的最快一轮是 10,053 ms。follow-up 与 steer 两个负载各调用了 384 次模型，追加输入投影确认的 P95 分别是 52 和 167 ms。先前同机探索样本的普通 64 并发落在约 79–167 Run/s，表内给出正式测量组。机器与负载窗口会影响绝对数字。

同一天还用完整性能分支做了两次对照，各跑了 192 个 Run，64 并发，4 KiB 模拟回答，首字和分片延迟都设为 0。第一次用了 10.70 秒，17.94 Run/s。单 Run 从提交到 PG 终态最短 406 ms，中位 2.19 秒，P95 为 5.38 秒，最长 6.07 秒。第二次用了 21.37 秒，8.98 Run/s，P95 为 9.54 秒。完整路径包含正式 Session API、模型网关、完整原生存储、账务和冻结历史。两个结果都排清了积压。原型和完整实现的比率不能用来预计一次正式上线的收益。

## 实时生成与“一股脑塞进 Kafka”

从一次真正的 Pi 执行录下完整原生批次，再给两个 Worker 同一份轨迹，替换当次身份和合成输入。重放控制保持领取、分区、消息内容、投影和独立结束信号。预录流水发送先按序提交全部原生批次并等待全部 ACK，再发结束信号。只有这个控制省掉了实时 Pi 的生成与逐批等待。

| 64 并发，每波 384 个 | Run/s | Worker 领取后到最后发送确认 P50 |
|---|---:|---:|
| 实时 Pi，常规投影，两端对照 | 161.69 / 165.37 | 42.74 / 39.59 ms |
| 同一份预录提交，每批等 ACK | 170.67 | 38.39 ms |
| 同一份预录提交，按序流水发送 | 173.14 | 11.16 ms |
| 实时 Pi，只投影最后的 Run 状态 | 195.05 | 43.07 ms |
| 预录流水发送，只投影最后的 Run 状态 | 196.84 | 11.24 ms |

流水发送明显缩短了 Worker 的工作时间。整个服务同时受 PG 登记与投影限制，所以对应吞吐增幅小得多。省去消息/Inbox 的两行是定位成本的对照，不提供可用聊天历史。常规 64 并发三次，从最后一条完整助手消息的 PG 提交回执到 Run 结束的 PG 提交回执，中位 6.06–6.23 ms。负载更大时，结束消息可以花更长时间等待分区前面的工作。这两个区间应分别观察。

## 第一个实测瓶颈在 Run 登记通知

对同一份普通负载，以 64 并发、每波 768 个 Run 做开、关、关、开的对照。四波都由**同一条测试控制连接**在 PG 登记成功后唤醒 Worker，Worker 接受同样的任务。唯一切换的是登记语句是否还产生一次 PG NOTIFY。

| 登记事务内通知 | Run/s | 登记 SQL P50 | 登记连接 checkout P50 | 被通知锁阻塞的非空闲登记后端采样 |
|---|---:|---:|---:|---:|
| 开 | 167.83 | 68.92 ms | 234.86 ms | 442/492 |
| 关 | 316.52 | 6.44 ms | 0.02 ms | 0/38 |
| 关 | 331.16 | 6.56 ms | 0.02 ms | 0/46 |
| 开 | 172.50 | 68.05 ms | 234.84 ms | 431/480 |

样本中等待的是 `pg_database` 对象 0 的 `AccessExclusiveLock`。PG 17.6 在带通知的事务提交前取得这把共享对象上的锁，从而保持通知顺序。普通数据写入保留自己的事务与行锁。[PG 17.6 源码](https://github.com/postgres/postgres/blob/REL_17_6/src/backend/commands/async.c#L841-L870)

另一次采用真实 PG 唤醒：登记先单独提交，随后在 5 ms 窗口合并唤醒。768 个 Run 产生 257 次通知，测得 **322.39 Run/s**。Worker 还会周期复查持久队列，专门屏蔽全部唤醒的 4 个任务也全部完成。这个方案可以把提示移出关键事务。试验只测了一个入站进程，多个 API 实例和重启时的唤醒延迟需要另验。

完整部署也有 `runs_notify_run_queue` 触发器。在第二次完整链路的 138 次观测里，Session API 有 85 个非空闲后端样本，其中 4 个等待该通知锁，最大同时等待 1 个。它说明现网路径确实经过这里。这份完整负载的证据不足以把原型的近两倍增益外推到原有系统。[触发器定义](../../packages/database/src/migrations/188_session_work_and_tool_dispatch.ts)

## 固定到达率与压力转移

每个计划到达时刻独立安排，最多 384 个测试客户端在途。碰到客户端上限会把尚未发往系统的请求单独记作未发出。所有已接纳请求都验证了最终状态，所有阶段结束时实测 Kafka lag 为 0。表中的 lag 是消费到的提交位置与 Kafka 高水位的采样差，包含其他 Session 在同一分区里的排队。

| 直接在登记事务通知 | 完成 / 计划 | P95 | 峰值 Kafka lag | 最后一个计划到达后排清所用时间 |
|---|---:|---:|---:|---:|
| 20/s，30 秒 | 600/600 | 81 ms | 4 | 58 ms |
| 60/s，30 秒 | 1,800/1,800 | 89 ms | 9 | 51 ms |
| 90/s，30 秒 | 2,700/2,700 | 72 ms | 11 | 50 ms |
| 90/s，独立重复 60 秒 | 5,400/5,400 | 126 ms | 36 | 58 ms |
| 120/s，30 秒 | 3,550/3,600，50 个未发出 | 3,755 ms | 2,318 | 1,998 ms |
| 120/s，独立重复 30 秒 | 3,600/3,600 | 75 ms | 21 | 55 ms |

第一轮 120/s 的后半段出现持续积压。接近停止发起时，PG 里有 1 个 Run 等领取，348 个仍登记为 running，Kafka 还有 2,318 个 offset 的 lag。Worker 可以在 PG 完成投影之前释放自己的工作位置。原型在本机两次都跟上了 90/s，120/s 的长尾缺乏稳定性。30–60 秒的窗口不代表长期部署容量。

将通知移出登记事务后，压力可以移到 Projector。对仅写一行的常见消息，用一个带所有权行锁的 SQL 同时验证 Run 和写入；同时变更 Inbox 和消息的批次仍用原来的显式事务。普通 Run 的 Projector 调用由 13 降到 4。突发时每事务通知仍在，两个单语句样本为 163.86、166.33 Run/s。固定 120/s 并合并唤醒时，慢的一轮显式写入 P95 为 3,266 ms、峰值 lag 2,035，单语句的一轮 P95 为 242 ms、峰值 lag 91。重复后单语句 P95 为 169 ms、显式写入 P95 为 78 ms。这些窗口里的同一份 4 MiB 主机哈希校准中位数分别为 8.37、7.52、2.12 和 2.06 ms。稳定结论是少了九次 PG 调用，主机状态会显著影响能否观测到端到端差距。

## Inbox 深度与完成边界

每条追加输入有 512 字节，测试客户端等该输入投影成功才发送下一条。每个深度测 6 个 Run、2 个并发，Pi 在最终边界一次取用全部 follow-up。

| 单个 Conversation 队列深度 | 每个 Run 的 Inbox 当前值写入次数 | 累计绑定给 PG 的队列 JSON 字节 / Run | 每次输入确认 P95 |
|---:|---:|---:|---:|
| 1 | 3 | 582 | 16 ms |
| 16 | 18 | 78,612 | 15 ms |
| 64 | 66 | 1,202,244 | 14 ms |
| 128 | 130 | 4,772,675 | 15 ms |

表里只保留最新值。每次修改仍要向 PG 提交整份数组，所以连续填充的累计传输量随深度近似平方增长。128 条原始输入只有 64 KiB，累计队列 JSON 达到约 4.55 MiB。这是应用交给 PG 的字节，不能等同于实际 WAL 或磁盘占用。

对“单独发结束信号”还做了这些校验：

- 暂扣 `work_finished`，已有完整回答且 Inbox 为空，PG 中的 Run 仍为 running。放行后才完成。
- Pi 取走 follow-up 或 steer 后，单独让下一次模型请求停在可检查处。PG 已看到队列为空，Run 仍在执行，实际模型上下文里包含被取用的内容。
- 在第一次 `waitForIdle` 已返回、关闭输入入口之前注入新输入，两个用例都重新等到空闲，在原 Run 内完成第二次回答。
- 编辑后取用的新文本进入上下文，已撤回的输入没有正式消息。重复已确认的原生批次和终态不会重复插入。过期写入身份的完成与闭合后的迟到批次被忽略。锁住第一个 Run 的领取行或使其保持 running 时，第二个领取者都取不到同 Session 的后续 Run。

这些检查覆盖原型的基本成功路径、相邻重投和边界竞态。完整接管仍需验证 Pi Task/Submission、持久提交指纹、输入元数据、部分输出恢复和受保护的 Kafka 后缀。本轮没有将原型安装为服务实现。专用数据库、Topic、消费组和完整对照使用的临时角色配置均已清理或恢复。
