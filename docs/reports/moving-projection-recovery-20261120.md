# 按可恢复位置重放，并按事务选择同步或异步提交

本实验在最小存储性能分支上运行。Kafka 分区的读取顺序、PG 的事务结果和外部工具的派发许可各有独立的确认位置。Projector 仍然等 PG 返回后才推进处理。它可以选择一次处理单条，也可以在同一分区一次取最多 16 条已经到达的记录。两种方式均可在一笔 SQL 调用内提交数据及分区进度。 [实验决定](../adr/0340-selective-async-projection-study.md)

## 哪些数据可以异步投影

数据库默认使用 `fsync=on` 和 `synchronous_commit=on`。首条用户消息的 PG 入队事务照常同步。它随后出现在 Kafka，Projector 将它复制进正式历史时可以单独采用异步确认。实验还允许纯文本的完整回答、初始空 Inbox、未保存部分的首个 Kafka 位置，以及带有原回包位置和截止时间的沙箱工具意图异步提交。这些数据都可以由保留的原记录重建。工具执行另外经过原有的消费组派发确认。

最小原型在现有 Run 行上保存尚未完成的原生工具任务引用，包括操作 ID、原回包位置和截止时间，任务结算时移除。实际回包仍在原 Worker 的 Kafka Topic。正式运行时已有原生 Task 当前值用来保存这类引用。

实验对用户输入的修改回执、取消、工具终态、计费证据和 Run 收尾保守地选用同步确认。只要一批中混有这类操作，整批等待 WAL 刷盘。PG 函数在可放宽的事务中执行事务局部的 `set_config('synchronous_commit','off',true)`，并返回事务内观察到的实际模式。单独检验同一连接复用后的默认值。两种模式的身份检查、PG 原子写入和 Kafka 派发边界一致。 [PostgreSQL 对异步提交的定义](https://www.postgresql.org/docs/17/wal-async-commit.html)

另有一组对照，连正常完成的 Run 投影也采用异步确认。在这些只做一次文本回答的 Run 中，来自 Kafka 的投影事务因而可以全部异步提交，PG 侧原始入队和领取事务继续同步。专门验证原型里只修改 PG 并通知观察者的正常收尾。它没有把业务系统的其他控制写入、资源释放或扣费一并放宽。

## 恢复从哪里开始

稳定提交同时更新这个 Run 可恢复到的原生序号、身份、必要的原生文档信息和 Kafka 位置。恢复元数据只保留一份当前值。记录很少、状态已落稳的 Run 也可以从足够新的 PG 分区进度恢复，空闲 Run 的首条输出不会钉住分区。首个尚未覆盖的变化会留下一个回放位置，同一段后续流式更新只修改内存。主对话和子对话都检查，若还有半截文字、正在执行的工具或未清空的 Inbox，就保留已有的恢复起点。不能用有限元数据表达的状态继续依赖 Kafka。16 KiB 的界限只影响是否生成新检查点。

Projector 在一份 PG 快照中加载活动 Run 的基准及分区位置。它选择最早仍然需要的后续记录，与 Kafka 消费组位置一起决定从哪里开始读。PG 断连或发现持久位置回退时，即使 Projector 进程还活着，也会丢弃旧内存、重新取得分区并加载 PG。专用实验 Topic 配置 Kafka 原生七天保留。故障试验在独立 Topic 上主动推进 Kafka 的最早可读位置，验证恢复需要的数据过期后该分区会明确报错。 [恢复实现](../../scripts/experiments/minimal-session-storage/moving-checkpoint.mjs)

## 压测和故障验收

压测使用两个运行固定 Pi Harness 的 Worker 进程、确定性模拟模型、三副本 Kafka、32 个分区和 12 个投影连接。一次短 Run 产生 7 条 Kafka 记录、4 次业务状态变更，完整回答约 4 KiB。另计第一次建立未覆盖后续记录的恢复位置产生的写入。完整链路的延迟从开始提交输入算到 PG 确认 Run 收尾，回放则单独记录发送迟到。发压器最多保留 384 个在途请求，达到上限时跳过新增计划到达。各轮核验原始记录顺序、PG 完整消息、Inbox 和最终历史头。 [复现命令](../../scripts/experiments/minimal-session-storage/README.md)

下表为先后顺序互换的两组实验结果。每轮按计划持续发新 Run 20 秒。每个组合在 520/s 下测两轮，780/s 下测四轮。表中 P95 是每轮各算一次后所得的范围。两种 16 条合批模式在 10/s 下均接住了全部 400 次计划到达，P95 分别为 62–68 ms 和 60–63 ms。

| 计划 Run/秒 | 每笔 PG 提交 | 确认方式 | 实际完成 Run/秒 | 完成延迟 P95 | 接受并完成 / 计划到达 |
|---:|---|---|---:|---:|---:|
| 520 | 单条 | 同步 | 296–302 | 2.54–2.87 s | 12,842 / 20,800 |
| 520 | 单条 | 选择性异步 | 454–469 | 1.67–1.71 s | 18,970 / 20,800 |
| 520 | 最多 16 条 | 同步 | 516–517 | 223–311 ms | 20,800 / 20,800 |
| 520 | 最多 16 条 | 选择性异步 | 513–517 | 180–216 ms | 20,800 / 20,800 |
| 780 | 最多 16 条 | 同步 | 612–645 | 1.14–1.27 s | 52,127 / 62,400 |
| 780 | 最多 16 条 | 选择性异步 | 680–696 | 1.05–1.20 s | 56,265 / 62,400 |

在这个简单形状下，每个 Run 还需要一笔同步收尾事务。PG 允许多个这样的事务共用一次 WAL 刷盘。单条写入时，业务变更和首次恢复位置合计每个 Run 有五笔投影事务，四笔可异步。合批时与收尾同批的记录一同等待确认，520/s 下实际异步事务占 71.6%，780/s 下占 33.1%。单独回放同一录制的 780/s 记录时有一轮选择性异步降到 696 Run/秒，发送迟到 P95 为 1.37 ms，等待数据库连接平均约 17 ms，占用连接平均约 12 ms。

在 780/s 的完整链路中，选择性异步合批的领取延迟 P95 为 36–43 ms，结束消息从生成到 Projector 开始处理的 P95 为 870–1,007 ms。取连接等待平均约 18 ms。6,135 个计划投入因为在途上限而跳过，所有已接受的 Run 均完成，测量收尾时 Kafka 积压归零。 [逐轮指标](moving-projection-recovery-20261120.json)

第三套独立夹具只改变收尾策略，每批仍最多 16 条，两种模式交错执行。下表对应同一套夹具内的对照，PG 默认、入队、领取、数据形状及在途上限相同。

| 计划 Run/秒 | 正常收尾的投影事务 | 实际完成 Run/秒 | 完成延迟 P95 | 接受并完成 / 计划到达 |
|---:|---|---:|---:|---:|
| 520 | 同步 | 515–517 | 250–491 ms | 20,800 / 20,800 |
| 520 | 异步 | 517–518 | 191–196 ms | 20,800 / 20,800 |
| 780 | 同步 | 649–673 | 1.09–1.14 s | 27,057 / 31,200 |
| 780 | 异步 | 751–756 | 685–806 ms | 30,633 / 31,200 |

在放宽收尾的四轮完整链路中，PG 在每一笔 Kafka 投影事务里都实际报告了 `off`。780/s 时仍有 567 个计划请求被发压器跳过，已接收的全部结束，两轮停止新投入后分别用 333 和 332 ms 排空。因此这批数字适合比较策略，尚不能证明长期稳定承载每秒 780 个完整 Run。

三套正式实验共完成 24 轮有序回放和 28 轮完整链路。回放对齐了 99,840 个 Run 的最终表内容。完整链路接收并完成 281,894 个 Run，计划投入共 312,800 个。上述两项口径均未将预热和功能验收计入吞吐成绩。

故障夹具使用另一套私有 PG 和三台 Kafka 容器。直接执行 PG 的 immediate shutdown，保留同一 Projector 进程和原 Kafka 消费组。故障实例的 WAL writer 间隔特设为 5 秒，以便复现“客户端已收到确认但 PG 尚未刷盘”。吞吐压测使用正常的默认时序。可观察的外部工具执行会在独立临时文件中追加一次记录，原任务的结果通过真正的 Kafka 回包邮箱返回。 [故障用例](../../scripts/experiments/minimal-session-storage/run-moving-recovery.mjs)

- Kafka 消费组和 PG 的确认位置都达到 2126 后停掉 PG。重启时 PG 恢复到 2101，缺一项沙箱执行意图和 24 条回答。相同的 Projector 进程重新取得分区并恢复全部 25 条记录，外部文件只写了一次。接手的邮箱按原操作 ID、原 Topic、原 offset 及原截止时间读到了已产生的回包。
- 在 PG 确认工具意图、Kafka 尚未授予派发许可时打断处理，接手后执行一次。在 Kafka 已授予许可、执行请求还未发出时打断，实际执行零次，到原截止时间得到 `tool_reply_timeout` 和 `unknown`，最终保存了结果不明的工具回复。
- 允许正常收尾异步时，先确认 PG 中有两条消息、Run 为 `completed`、位置为 2133。实际停机恢复后直接读 PG，位置退到 2131，只剩一条消息，Run 为 `running`。模拟调度器通过既有的分区追平等待后才读取，看到两条消息、`completed`、位置 2133。
- 在同一个 Run 中先完成 32 条回答，再追加 2,048 条回答。每次在稳定位置重启都读取零条旧记录。让主、子对话各留一段流式文字，然后主对话完成、另一 Session 推进分区，两次都只读取 6 条后续记录，正确拼回子对话的半截文字。第一次流式变更留下恢复位置，同段后续片段产生零笔 PG 事务。两个样本的序列化检查点是 390 和 399 字节。PG 恢复查询实测 1.50–1.75 ms，包含 Kafka 重新入组的整个过程约 3.36–4.36 秒。
- 核验了 PG 提交成功但客户端丢失回执、Kafka 实际最早可读位置超过恢复起点、所有抽查连接在上笔事务结束后回到 `synchronous_commit=on`。 [故障观测数据](moving-projection-faults-20261120.json)

在第二套独立故障夹具里重跑，第一次停机时 24 条回答中有 8 条需要补写，工具意图已经保住。再制造一次停机时，意图和 24 条回答都需要恢复，工具也只派发了一次。异步确认过的 Run 完成状态再次经历了从 `running` 恢复为 `completed` 的过程。两套夹具均已清理。

这轮验证面向存储原型。压力负载没有真实模型推理、Cube 工具时延、完整收费流程或所有产品侧子 Agent 操作。两份交错的原生 `pi.live` 文档用于验证主、子对话的恢复依赖。将策略用于服务版前，还须把恢复就绪状态接入正式的读取、调度和清理，并验证实际业务的历史和资源引用。

我的建议是把有界合批与可重建数据的事务级异步确认组合使用。收尾异步在更高负载下另外带来收益，也能让调度器在 PG 刚恢复时看到已经过时的 `running`。服务版在采纳这一档之前，需要验证所有据此采取行动的路径均等到所属分区追平，包括 Worker 的领取、租约恢复和资源清理。

事件日志和运行时单元测试通过 189 项，原型辅助测试通过 24 项，真实传输集成测试通过 17 项，原有常规路径通过 16 组冒烟场景。K3s 实验资源清理后，服务实例复查为 `synchronous_commit=on`、`fsync=on`、`wal_writer_delay=200ms`。
