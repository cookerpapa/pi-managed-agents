# #52 · 真实 Bash 工具在混合负载下的耗时

## 实验口径

两台原型 Worker、一个 Projector、32 个 Kafka 分区、三个 Kafka 副本、12 条投影 PG 连接，
使用同一台开发主机。每个 Run 是一个新 Session，发两次确定性模型请求，产生一次原生 Bash
调用、一条与之配对的 Tool Result 和一条约 4 KiB 的最终回答。实际调用经过原生工具意图、
Kafka、执行侧路由、PG 投影、Kafka 派发位置确认、固定 Guest、HTTPS completion 和原 Worker 的
Kafka 回包 Topic。对照组通过同一个 Pi Harness 返回固定的同形文本。每个比例保持同样的 Run 到达
速率，按到达序号分散真实工具，使不同轮次使用相同的分区排列。

每台临时 VM 的命令都将 Run ID 追加一次到文件，输出实际目录、文件标记和 Bash 自身的两个时间戳。
逐 Run 比对第二次模型请求与 PG 中的最终 Tool Result。每轮排空后独立核对每台 VM 的执行 ID
多重集合。限速使用开环到达，报表单列丢弃数、等待领取数和 Kafka 积压。下面的完整轮次均无丢弃，
最终 lag 为 0。故障轮次单列。

## 每秒 4 个 Run，单台 Guest

每个比例 64 个 Run，先升后降，各测两轮。下表是两次测量的范围，排除预热。
CPU 为 Guest 内核统计的忙碌时间占两颗 vCPU 总时间的比例。

| 真实 Bash 占比 | 每秒目标真实调用数 | Run 开始提交至 PG 收尾 P95 | Guest CPU | 采样到的 Kafka 最大积压 |
|---|---:|---:|---:|---:|
| 0% | 0 | 103–120 ms | 0.3% | 3–6 |
| 25% | 1 | 420–429 ms | 13.4–13.8% | 1–2 |
| 50% | 2 | 423–430 ms | 26.5–26.7% | 3–4 |
| 100% | 4 | 434–458 ms | 52.5–54.0% | 1–2 |

全真实的两轮合计 128 个命令，真实调用数量与 PG 中的 Bash 结果数一致。

| 同一条真实工具操作的测点 | P95 范围 |
|---|---:|
| Projector 开始处理意图，到取得并固定本次路由 | 9.6–9.7 ms |
| 路由就绪，到意图的 PG 投影事务返回 | 1.2 ms |
| 意图投影事务返回，到 Kafka 确认派发位置 | 8.7–13.6 ms |
| 执行适配器开始提交，到收到 Guest 接单确认 | 约 77 ms |
| 执行适配器开始提交，到 Bash 执行命令正文 | 262–271 ms |
| Bash 命令正文 | 5.0–5.8 ms |
| Bash 正文结束，到 Worker 收到原回包 | 58–59 ms |
| Worker 收到回包，到规范 Tool Result 投影可见 | 12–14 ms |

接单和进程启动两行共享起点，时间重叠。各阶段 P95 独立计算。
同一主机的进程使用高精度墙上时间，Guest 与主机的时差通过轮次前后分别四次往返约束。
这两轮估算单边误差均小于 1 ms。命令正文时长使用同一 Guest 的时钟。
PG 耗时指候选投影事务返回，沿用原型的提交策略。


用带 HTTP 分段观测的最终实现复测同一组负载。两轮全真实 Bash 的 Run P95 为 451 和
457 ms，意图 PG 投影 P95 为 1.28 和 1.37 ms，派发位置确认为 8.99 和 8.90 ms。
适配器提交至 Bash 正文开始为 275 和 272 ms，其中 envd 启动请求至客户端就绪、可发送输入
约为 69 和 66 ms。命令正文分别为 5.18 和 5.10 ms。

## 增加到每秒 6 和 8 次真实 Bash

同一台 Guest 的每秒 6 次试验重复两轮，每轮 192 个 Run，全部完成。
Run 收尾 P95 分别为 503 和 464 ms，Guest CPU 为 83.3% 和 81.3%，
采样最大 lag 都是 5 条。在本负载中，每秒 4 次与 6 次的 Guest CPU 增幅，
折算约为每次短命令占用 0.26–0.28 个 CPU 秒，包含 Guest 侧服务与工具进程开销。

单台 Guest 每秒 8 次的全真实试验中，两次出现接单状态未确认。具备故障采样的一次，
128 个 Run 都已领取，120 个操作已开始提交给适配器，88 次收到了提交确认。一个操作
在适配器中等了 8.18 秒才得到未确认的结果。此时已收尾 56 个 Run，最后一次采样还有
72 个运行中，待领取数为 0，Kafka lag 为 168 条，采样峰值 216 条。
Guest 当轮 CPU 忙碌 98.9%，每 200 ms 采样可见的未完成操作峰值为 25 个，最低可用内存
685 MiB，内核 OOM kill 增量为 0。停止测试后查到 76 个物理执行标记。这次未确认调用
在采样时尚无标记，无法据此确定它的最终物理状态。测试没有重新派发它。

执行侧在对该分区的工具取得 Kafka 派发确认之后，等待执行适配器返回接单情况。运行中的
Bash 靠独立回包结束。在 Guest CPU 已饱和且接单变慢时，同分区后面的消息会等候，
因此能够同时看到 Guest 堆积和 Kafka lag 上升。正常工具的意图 PG 投影仅约 1 ms。
这组证据把首个明显拥堵定位在沙箱执行链路。它不能把某次接单未确认精确归因到一个系统调用。

正式执行器通过 Cube envd 启动短命 Guest 客户端。Guest 服务确认顺序和身份、保存操作、
启动操作进程，随后以普通用户运行固定工具执行器，才会到达 Bash。上面的“命令正文”
计时从 Bash 已经启动后算起。[Cube envd 传输](../../packages/sandbox-control/src/cubesandbox-runtime-client.ts)、
[Guest 接单](../../packages/tool-sandbox/src/guest-executor-service.ts)与[工具执行](../../packages/tool-sandbox/src/guest-tool-operation.ts)。

每台分担约 4 次/秒时，双 Guest 的两轮 128 个 Run 全部通过，总完结率 7.83 和
7.84 Run/s（包含排空时间），无丢弃，Run P95 为 648 和 558 ms，采样最大 Kafka lag
为 3 和 6，单台 Guest 的 CPU 范围为 53.7%–56.9%。此前一轮 256 个 Run 的双 Guest
试验曾在已发送命令后丢失接单确认。长轮复测另列如下。


### 两台 VM 的长轮复测

每轮 256 个 Run，仍固定每秒 8 次真实工具调用，共两轮。两轮的 512 个指令都找到各自对应
的唯一物理执行和规范结果，但第二轮发生明显积压。

| 相同负载 | 第一轮 | 第二轮 |
|---|---:|---:|
| 含排空的完结速率 | 7.91 Run/s | 6.07 Run/s |
| Run 开始提交至 PG 收尾 P95 | 669 ms | 18.60 s |
| 采样峰值 Kafka lag | 4 条 | 496 条 |
| 两台 Guest CPU | 59.7% / 60.0% | 91.3% / 95.5% |
| 适配器开始提交至 Bash 正文开始 P95 | 481 ms | 12.61 s |

在慢轮中，适配器开始提交到接单返回 P95 为 6.95 秒。利用客户端侧被动 HTTP 测点，
envd 的 `Start` 请求发起至能够发送 `SendInput` 耗时 P95 为 5.22 秒，`SendInput`
的 HTTP 响应仅约 6 毫秒。Bash 正文本身 P95 为 27 ms。两台 VM 的内核 OOM kill
增量均为 0，最低可用内存均超过 1,000 MiB。

这一轮等待也传回了会话链路：意图发出到 Projector 开始处理 P95 为 3.98 秒，
Worker 收到回包到对应 Tool Result 投影可见为 6.25 秒。与此相对，意图投影事务返回
P95 约 2 ms，派发 Kafka offset 确认约 15 ms，未观测到投影 PG 连接池排队。
预定发送窗口结束后又花了 10.33 秒排空。不同阶段的 P95 数值不能逐项相减推得单一入口的耗时。

## 结论和范围

在这个原型中，短 Bash 的成本主要集中在命令正文开始之前。当 Guest 接单变慢，
等待还会拖住对应分区。两台 VM 在相同速率下既有成功且低积压的轮次，也有长尾和
未经确认的接单。这些对照不能给出生产集群的固定上限，也没有证明每次接单异常的内部原因相同。
值得进一步单独测量短命 Guest 客户端启动、Guest 服务接单和操作进程到固定工具就绪这三个区间。

每个 Run 的中位数为 15 个原生提交，另有 1 条完成记录。一轮 256 个 Run 实际消费
4,096 条 Session Kafka 记录。即使每秒输入 8 个这样的 Run，对应的工作量也只有约 128 条 Session 记录/秒。分区等待外部接单就足以形成队列。此前每秒 4,630 条的基准只投影已录制的历史，两种速率
计数单位不同。这里使用预先创建的独立 Cube VM、同一 WSL 主机和确定性模型，覆盖新建
根会话中的单次短 Bash。全部测量来自 #52 实验分支。线上容量和发布仍需在对应部署上验证。

首轮单 Guest 过载中，一台测试 Worker 未在退出时限内确认收尾，该试验按失败记录。
实验环境随后确认临时 Pod、Service 和认证资源清除，集群列表中未发现该系列 Session
测试 Topic 或 Projector 消费组。补充故障计数与关闭测试等待器后，单 Guest 的 8 次/秒
故障复测记录了未确认结果和清理成功，两者在报告中独立判定。

复现方式见[实验说明](../../scripts/experiments/minimal-session-storage/README.md#mixed-native-history-and-real-guest-load)。
