# #52 · Worker 只读 PG 能否接手原来的工具等待

研究对象是最小存储原型。本实验沿用正式 Session API、租约过期扫描、封口、原生父子会话、Cube Guest 和原工具回包通道。比较的变量是 B 如何恢复 Pi：一条路径只读取原型已存的数据，另一条路径额外读取 Projector 在封口时生成的一份临时交接记录。

## B 已经能读到什么

| 问题 | 本次数据来源和结果 |
| --- | --- |
| A 是否已经封口，封到哪儿 | B 用新领取的 Run 和身份，在 PG 关联旧租约、同 Run 的恢复 Outbox 凭据、候选分区投影位置，一次查询取回已确认的封口。测试驱动不传旧 writer、封口序号或沙箱绑定给 B。 |
| 原来有哪些消息和待发输入 | 正文表有 6 条稳定 Entry，两个 Conversation 各有一个 Inbox。排队项有 Pi 内部数字编号、模式和改过的正文。子会话身份和发起委派的父工具任务编号也能从已有的控制表读回。 |
| 应该等哪个结果 | Run 的 projection_tools 有 Bash 的原 operation ID、Pi 工具任务及 Conversation 编号、回包 Topic、分区、起始 offset 和原截止时间。读取这些字段就能定位原工具回包。 |
| Pi 的执行停在哪儿 | 当时有两个等待中的 generation 任务、两个运行中的 tool 任务。候选投影检查点停在原生提交 7，本次封口前最后的原生提交为 20。正常的 Projector 检查点会避开有未结工具或非空 Inbox 的状态；它服务于 Projector 重建。 |

## 一项无法从原型 PG 反推的数据

A 使用 Pi 的原生提交接口，用一个随机请求 ID 提交子 follow-up，然后单独修改排队正文。网页输入 API 的额外业务凭据不在此场景内。原生 Inbox 保留数字编号、模式和内容，Pi 的 Submission 记录另有字符串请求 ID。Pi 用后者在重试时找回已接受的请求。只有输入真正放入历史后，原型才有机会把其请求 ID 写到对应 Entry 的 source_input_id。

我们在同一隔离 PG 事务里建立保存点，分别把真实提交和仅替换请求 ID 的提交交给同一个版本的投影函数。两次都从同一 PG 状态和 Projector 视图开始，均实际更新 Inbox、推进候选分区位置，然后读回比较 Run、正文、Inbox、分区位置和已有子 Agent 控制行。两次的这些数据完全相同。比较结束后回滚保存点，真实消息继续走原有链路。另一份输入从未发给 Kafka、Pi 或 Guest。

紧接着的编辑使现有 Projector 内存视图中的 lastBatch 也不再含有原请求 ID。对照查询确认正式存储的 pi_durable_current 中确实有该 Submission 和请求 ID。B 原型冷读使用独立的只读角色，无权读取正式存储的原生表，也无权读取实验交接记录。在这个角色能提供的 Entry 和 Inbox 上打开原生 Harness，Pi 检查到 0 个活跃任务，现有 reattach 路径拒绝继续。即使另外编写一个读取器猜出这四个任务之间的依赖，上述两个输入仍无法从相同的投影值还原成各自的原请求 ID。

## 只在封口时写一份交接记录的对照

研究用 Projector 在处理已获准的原生提交时，另外维护当前 Conversation、Task、Submission、文档值、原工具执行目标和展示序号。恢复封口到达时，把它们与候选投影位置一起提交到隔离 PG，一次写入。稳定 Entry 和 Inbox 正文仍从原表读取，交接记录不复制这两类数据。Task 自身可能含有与正文相同的工具参数。新增的累积状态在 B 启动前释放。测试另外通过独立 Kafka 集群的删除记录 API 推进 Session Topic 起点，并向 broker 核实旧封口及之前的记录均已不可读。原工具回包 Topic 保持可读。

本例通过尚在 PG 的恢复 Outbox 关联前后身份，并实查旧租约的封口位置。长期保存这条 Outbox 不是实验提出的生产要求。B 先完成只读原型对照，再用另一个仅读交接记录的角色获取与 Run、旧 writer、Topic、分区、封口 offset 和封口 ID 全部匹配的记录。B 找回原 follow-up 请求 ID，测试在驱动端对比 A、B 独立计算的摘要。B 沿用 A 的 Bash 操作和截止时间。这个读取路径只用 PG；工具回包依然使用 Kafka。使用确定性模型，父模型、父子 HTTP 历史以及 VM 内执行标记分别接受独立核验。

## 实测

每种时序一次，串行，独占 VM。下表的冷恢复计时与上一组使用相同的起止点，还包含只读失败对照的少量时间。

| 时序 | Run 终态 | 读取候选 PG | 读取并装入额外交接记录 | 恢复原回包邮箱 | 冷恢复合计 |
|---|---|---:|---:|---:|---:|
| B 开始等之后才回包 | completed | 12.3 ms | 11.3 ms | 3.08 s | 3.12 s |
| B 接手前同一结果已到两份 | completed | 15.3 ms | 13.2 ms | 4.10 s | 4.14 s |
| 超出原期限，原结果迟到 | completed | 15.5 ms | 12.9 ms | 3.05 s | 3.09 s |
| 交接期间用户点 Stop | cancelled | 12.8 ms | 12.1 ms | 3.11 s | 3.14 s |

四次的附加记录为 7,941～7,945 字节。每个 Guest 的实际执行标记均为 1，B 的新 Bash 意图均为 0。提前送达的重复回包只形成一个最终结果。超时场景保留 unknown；Stop 场景 B 发出一次指向原操作的取消，模型调用为零，排队 Submission 最终为 unanswered。冷读的数秒开销主要是恢复原回包邮箱。每类单样本，不能外推为线上平均值。

另外串行复跑原有 Session 日志读取路径，正常运行与四种交接共 5 例通过。四种交接的冷恢复分别为 6.224、7.273、7.305、7.257 秒。原有用例没有新增的队列编辑，计时用于定位消费者启动成本。29 项原型辅助测试通过；独立核对带本实验标签的存活 Guest 与临时 PG、Kafka 容器均为零。

## 边界

这个实验验证一轮 Run 在一个旧身份之后的当前状态恢复。交接记录包含 2 个 Conversation、4 个 Task、3 个 Submission，以及 pi.agent、pi.live 等当前文档。这个保守的对照会保留已见过的 Task 和 Submission 的当前值，尚无清理已结束工作所需的完整依赖分析。部分字段可能可以从已有控制记录推导。没有证明每种文档都必须复制，也没有验证任意历史时刻的文档版本。计量大小使用 PG 中 JSON 文本的字节数，实际占盘和 WAL 写入量会不同。

每条正常提交都要在 Projector **内存**中更新额外的执行状态。只有封口才产生交接记录的 PG 写入；保存点对照和观测查询属于测试开销。此轮未测十万级活跃会话时的内存和吞吐，未测 Projector 在生成记录之前也崩溃、连续交接、跨压缩的祖先或长 Run 的历史裁剪。隔离测试同时使用已有服务版投影；交接记录和候选游标同事务，正式控制侧重新入队仍是另一事务。生产切换时还需保证可领取的恢复 Run 有可用的交接状态。
