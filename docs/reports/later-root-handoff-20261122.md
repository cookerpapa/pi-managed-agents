# 第二个 Run 中断后的恢复

第一轮通过 Session API 入队，Worker 运行固定 Pi，用受控模型生成一个带随机标记的回答并正常收尾。
删除隔离 Kafka 中第一轮的 Session 日志后，在同一会话接受第二轮用户输入。第二轮的父 Agent
委派子 Agent 去真实 Cube 执行 Bash。确认 Guest 写下执行计数、子会话的 follow-up 已投影后
终止 Worker A。等 PG 租约过期、原写入者封口、同一 Run 重新入队，再删除第二轮截至封口的
Session 日志。Worker B 拿到的校验值只是第一轮回答的散列，不能用它重建原文。

| 第一轮和回包时序 | B 读回的上一轮 / 合计 Entry | 父模型最终收到第一轮回答和 Guest 结果 | Bash 实际执行 / B 重新派发 |
| --- | ---: | --- | ---: |
| 第一轮正常收尾，B 挂回等待后才放行 Guest | 3 / 8 | 是 | 1 / 0 |
| 第一轮实际做过 Pi 压缩，回包在 B 接手前已投递两份 | 5 / 10 | 是，含摘要且不含已压缩的原始标记 | 1 / 0 |

两组均只产生一个规范 Bash 结果，B 沿用原操作 ID、回包 Topic 和截止时间。父会话 HTTP 历史
有两轮，候选 PG 含成功的子 Agent 最终回答。旧原生存储提交数为零。该实验保留 Projector
运行，只更换 Worker。模型和 Worker 管理端点由测试提供，PG、三副本 Kafka、Pi、Cube、公开
Session API 和 Worker 冷加载使用实际组件。第一轮只有根 Conversation，本轮仍未验证前一轮
也创建过子 Agent 的情况。这是功能验收，没有测量整套服务的吞吐。

## 读取与投影

此前双写实验在第二轮的原生提交上触发了旧库 `pi_durable_current_document` 唯一约束。
本轮启用候选存储自己的读写路径作为独立对照。在新 Run 开始时，Projector 使用与 Worker
相同的正常收尾历史头及根文档身份建立原生序号起点；建立投影起点不读取历史 Entry 正文。
同一 Run 内的旧写入者封口继续使用原有交接字段。接手的 Worker 在一个 PG 一致性快照中
读取当前 Run 的工作状态，以及仍在所需范围内的先前根正文，然后一次性恢复到空的 Pi 存储。
当前 Run 和继承的正文采用互不重叠的提交区间。需要整个先前根前缀时，还核对其条数和字节数。
再次收尾保留之前的压缩下界。现有 PG 表结构未改动。

## 下一项公开读接口问题

两组中，父 Agent 收到子 Agent 成功返回的随机值，子会话的 PG 结果也可查。单独读取子会话
时，HTTP 返回了一条 Turn 外壳，没有子 Agent 的最终回答或已完成的 Bash 正文；子 Agent
状态接口返回 `unknown`。根会话已经使用新正文读取器，子会话仍选用旧历史目录与依赖旧
Task/Submission 的状态视图。在这两个场景中，子会话自己的终态事件数也为零。部署中的旧
存储没有被切换，本次观测针对候选组合。

先验证能否由现有 Conversation 编号、工具结果和会话关系恢复子会话分页，再分别验证成功、
失败和取消的状态证据，之后才能决定需不需要额外保留终态。不能仅凭最后一句文本推定成功。
