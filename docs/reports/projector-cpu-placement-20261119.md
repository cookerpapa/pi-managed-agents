# PG 和 Projector 分开使用 CPU 的实测

在单机 WSL/K3s 原型上，分配互不重叠的 CPU 改善了投影回放的部分长尾。加回 Worker 和用户登记后，**两种布局都未能持续满足每秒 260 个 Run 的完整链路目标**。这个结果支持继续研究每个 Run 的持久化提交成本。它不足以支持在默认部署中固定划分核心。[逐轮观测](projector-cpu-placement-20261119.json) · [相同 SQL 的直写基线](projector-pg-path-baseline-20261119.md)

## 如何做到只换 CPU 布局

WSL 报告 16 个核心、32 个逻辑 CPU。同一完整 SMT sibling 组始终放在一起。主对照的总预算都是 8 个 guest 核心：

| 布局 | PostgreSQL | Projector |
|---|---|---|
| 共享 | 两边都能用逻辑 CPU 8–23 | 同左 |
| 分开 A/B | 8–9、12–13、16–17、20–21 | 10–11、14–15、18–19、22–23 |
| 分开 B/A | 使用上面 Projector 的四个核心 | 使用上面 PG 的四个核心 |

负载驱动、两个独立 Worker 进程和唤醒路由使用另外八个核心。PG 和 Projector 各在独立临时 Pod 中，PG 的 WAL writer、checkpointer 和新建数据库后端同样受其容器 CPU 集合约束。沿用部署镜像、同一节点磁盘文件系统和原有三副本 Kafka。实验 PG 是独立实例，使用磁盘卷、独立临时凭据、12 条预热投影连接，`fsync` 和 `synchronous_commit` 开启。Kafka、WSL 和 Windows 的其他工作仍由原调度器管理。Linux 的 CPU 集合约束到 guest 的逻辑 CPU；这次没有在 Windows 上给应用预留物理核心。[Linux CPU 集合语义](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpuset)

每次切换只修改三个经 Pod UID、命名空间和容器 ID 核对的实验 cgroup。切换后检查进程和线程的允许列表，测量中持续读取内核的生效集合。30 轮回放和 8 轮完整链路中，共核对 **1,030 个 PG 和 4,171 个 Projector 时刻**，均符合指定布局，两个容器的 CPU 配额限流计数增量均为零。测试结束后确认临时数据库、Topic、消费组、Pod、Service 和凭据均已清理。上线服务的 CPU 配置没有参与切换。

## 相同消息的交叉回放

两套独立录制各有 6,240 个新 Run，每个 Run 产生 7 条有序 Kafka 记录、4 次独立 PG 写入和 4 KiB 模拟回复。每套录制在自己的对照内使用同样的输入、身份、分区顺序、SQL 与参数。每轮从相同 PG 状态开始，处理完所有输入，再逐项核对消息、Inbox 和终态摘要。主对照交替共享和分开、互换 A/B；第二套使用不同顺序复验。另测直写 PG、每秒 390 个 Run、两边重叠使用四个核心，以及两边都能使用所有 16 个核心的参考组。30 轮合计回放 187,200 个 Run 和 748,800 次真实 PG 写入。

“达标”沿用之前的三个条件：计划的请求全部发出并完成、P95 不超过 1 秒、停止投喂后 1 秒以内排空。回放的 P95 从该 Run 第一条原生记录应当到达开始，算到终态提交。

| 每秒 260 个 Run 的八核心主对照 | 达标 | 每轮 P95 范围 | 实际完成 Run/秒 |
|---|---:|---:|---:|
| 共享八核 | 5 / 8 | 58–3,781 ms | 234.4–259.8 |
| 分开四核加四核 | 8 / 8 | 95–665 ms | 255.9–259.8 |

主对照的快慢主机窗口分布不均匀。用另一个 CPU 集合上驱动进程的相同 4 MiB SHA-256 工作量对齐速度，仅取稳态投喂中有时钟样本的完整秒。每条写入的均值按当秒实际写入数加权：

| 固定计算耗时 | 布局 | 秒数 | 每秒完成写入 | 平均占用连接 | 平均等连接 |
|---|---|---:|---:|---:|---:|
| 小于 3 ms | 共享 | 89 | 1,040 | 5.94 ms | 0.06 ms |
| 小于 3 ms | 分开 | 121 | 1,041 | 5.97 ms | 0.07 ms |
| 7 至 8 ms | 共享 | 29 | 955 | 12.56 ms | 17.17 ms |
| 7 至 8 ms | 分开 | 9 | 1,018 | 11.35 ms | 7.57 ms |

目标负载需要每秒 1,040 次写入，12 条连接对应每次平均约 11.54 ms 的占用预算。分开后，部分较慢窗口中占用更接近这个预算。校准只能给主机速度提供参照，各秒来自少数几轮，不能视为独立随机样本。

敏感性对照给出了这项收益的界限。额外的 260/s 对照中，分开 A/B 也出现过 2,538 ms 的 P95；这轮按事先指定的顺序属于四核重叠与分开布局的对照。390/s 时，共享和分开均是两轮中一轮通过，两种布局都出现过超过 7 秒的 P95。相同负载下直接写 PG 的四轮 260/s 对照均通过，P95 为 42–51 ms。

## 完整链路

每轮持续 40 秒，计划发出 10,400 个用户请求，实际走 PG 登记、Worker 领取、Pi 与模拟模型、Kafka 和 PG 收尾。初试的顺序是共享、A/B、B/A、共享，复试使用 B/A、共享、共享、A/B。这里的 P95 把用户提交和 Worker 执行也算在内。

| 每秒 260 个 Run | 达标 | 各轮端到端 P95 | 已发出并完成 / 计划 |
|---|---:|---|---:|
| 共享八核 | 1 / 4 | 94、3,796、4,317、2,381 ms | 36,125 / 41,600 |
| 分开四核加四核 | 1 / 4 | 94、3,348、3,569、3,115 ms | 37,299 / 41,600 |

所有已发出的请求都完成。两组分别有 5,475、4,301 个计划请求在驱动达到 384 个在途上限时没有发出。快轮两边的 P95 都是 94 ms。慢轮仍有成千条记录待处理，分开 CPU 也会出现约 3.6 秒的用户等待。快慢窗口比例有差异，所以不能把两组累计完成数的差额解释为隔离带来的固定吞吐增益。

这次实验改变了 PG 与 Projector 能在哪些 CPU 上运行。它没有改变每个新 Run 的四次事务提交，也没有单独隔离 WAL 磁盘、Kafka 或宿主机调度。若继续做代码实验，优先用同一份回放评估可以共同确认的稳定写入能否少做一次事务提交，同时验证输入持久化确认、工具派发以及崩溃重放的边界。[复现说明](../../scripts/experiments/minimal-session-storage/README.md)
