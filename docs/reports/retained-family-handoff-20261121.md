# Worker 更换时从现有 PG 和保留的 Kafka 日志恢复

在 #52 的隔离实验里，Worker A、B 是不同的 Node 进程，均使用项目的 `DurableAgentSession`、固定 Pi Harness 和 Worker Kafka producer。每个场景使用专属的原生 Cube VM，固定 Guest 执行一次 Bash，先追加一行标记，再等待放行，最终返回 VM 内生成的随机值。Guest 通过已安装的 HTTPS completion 服务投递到 A 原来的三副本 Kafka 回包 Topic。父子模型是确定性的本地模拟模型。父模型实际拿到的工具结果必须含有该随机值。

## 读取边界

确认沙箱已写标记、子会话 follow-up 已被接受并投影后，对 A 发 SIGKILL。隔离控制夹具发布 recover 封口，Projector 将原租约撤下，随后为同一个 Run 指派新身份。迟到旧身份记录被拒绝。B 只接收新身份、已确认的旧封口身份与位置、服务连接等启动参数。没有传递 A 的内存、native 写数组、任务树或回包地址。

B 的 PG 连接强制只读。如果有已正常结束的上一个根 Run，B 用原型已有的历史头、消息和根 Inbox 读取器建立起始状态。接着在指定分区读到固定封口，只应用属于本 Run、本次旧身份且原生序号连续的提交。完整 Entry 使用 PG 正文并逐项比对序号、批内位置和内容；原生 Task、文档和 Submission 从保留的日志补回。再核对 PG 当前 Inbox、原操作的保护引用和本场景最后提交的原生序号见证（已投影的待发输入）。对于这个实验，重放过程既不派发工具，也不使用 Projector 消费组提交进度。

B 通过生产代码 `KafkaToolReplyMailbox.restore/resumeWait` 重建原操作的 waiter，Pi 自身处理重开后的正常状态转换。父子循环都恢复到了等待原工具的阶段。B 发布后续原生提交，原有 Projector 正常落盘并收尾。没有新增 PG 表、恢复检查点或热路径写入。运行时授权变更、封口进度、B 接手后 Pi 正常继续工作所需的持久化仍然发生。

## 四种时序

| 实验条件 | B 实际读了什么 | 结果 |
|---|---|---|
| 原回包已到，并在同一 Topic 再投递一次 | PG 正文 6 条，当前 Run 的 19 次原生提交和原回包位置 | 子会话形成 1 条最终 Bash 结果，父会话收到随机值 |
| 回包在 B 重新挂上 waiter 后才到；同 Session 有上一个已结束 Run | 上一轮从 PG 取 3 条 Entry，跳过分区中已覆盖或无关的记录，重放本轮 18 次提交 | 同一 Run 正常完成，已排队的子输入处理一次 |
| 上一个已结束 Run 的整段 Kafka 已轮转 | 上一轮从 PG 取 3 条 Entry，原生序号从 7 接起，再读本轮 18 次提交。下次父模型请求中核对了上一轮原回答 | 成功接回原结果；B 没有要求从 Session 创立重新消费 |
| 当前 Run 较早的创建凭据已轮转，但后面的 Bash 意图、排队输入和封口仍在 | PG 已追平，原回包也在；可读日志中第一份本 Run 的提交为 11，期望为 1 | 缺口可检测，拒绝开始执行，未重发命令 |

每个成功场景实际 SIGKILL A，B 均为全新进程，沿用原 operation ID、reply Topic 和原截止时间；B 新派发的 Bash 数是 0。核对 VM 文件只有一行、PG 中只有一个最终 Bash 结果。旧身份在封口后发送的候选记录被跳过。3 个成功样本的最终模型输出到 PG 收尾分别为 13、14、12 ms。每种时序各一次；这些是功能样本，不据此估计 P95 或并发吞吐。

B 从开始恢复本轮前缀到原回包邮箱就绪的三个样本为 6.28、7.22、7.27 秒。PG 本轮正文和元数据查询 3–5 ms，会话日志消费者取得分区约 3.1 秒、原回包邮箱重新订阅约 3.1 秒，日志追平另耗 0.02–1.02 秒。这个时间未包括 B 进程启动和自身新邮箱的初始化；它暴露了实验中启动两个临时读取器的成本，不能直接外推到常驻读取器或长历史。

## 到期的判定

本实验创建的 Session Topic 配置为 7 天按写入时间删除；原操作的回包 Topic 有自己独立的保护。为了确定性地复现轮转，使用 Kafka 的删除记录 API 仅推进专属测试 Topic 的起始位置。没有等待七个自然日，也没有改服务 Topic 的策略。

在失败场景中，PG 已追到封口，实际 Bash 已完成、回包在 Kafka，新的 Bash 意图和 Inbox 更新仍然可读。测试把更早的子会话创建记录移出可读范围，核对其随机幂等键没有出现在原型 PG 的 Run、正文或 Inbox，也没有在所保留的 Session 记录里再次出现。B 发现原生序号缺口，在开启 Harness 之前停止，产生零条新的原生提交。该结论针对最小存储视图。服务版另有 `subagent_conversations.id` 和关联的 Session/Run/原生源记录身份，子会话启动使用 `view.id` 作 `requestId`，不能凭这个实验断言服务版也缺同一个键。应先核对可从现有控制记录还原的字段，再决定是否需要额外持久化。[服务版创建关联](../../packages/subagent-control/src/postgres-subagent-conversations.ts) · [启动时使用创建身份](../../packages/sandbox-supervisor/src/remote-tool-sandbox-turn-runner.ts)

## 实验范围

实测使用原型的真实 PG 投影函数和有序 Kafka 派发许可、真实 Kafka 传输及真实固定 Guest。父级委派由研究工具调用实际子 Conversation 创建及重接接口；Run 登记、旧身份封口和新身份领取由隔离控制夹具驱动。没有替换线上 Worker，也未经过 Web/Session HTTP API、正式子 Agent 控制器或生产租约到期扫描。读取器只验证本 Run 的单次旧身份区间和普通已结束根 Run 的 PG 前缀。多次交接、用户 Stop、缺回包至原截止时间、含完整压缩状态和图片的祖先，以及长分区扫描成本仍属于 #52 后续范围。

第一次联调发现模拟模型每个进程使用随机 API 标识，重接按设计拒绝了模型身份变化；固定假模型身份后通过。另一轮复用同一测试 VM 却切换 Session Topic，固定 Guest 拒绝更换执行日志流。最终每个场景均使用独立 VM。上述失败未计入成功样本。
