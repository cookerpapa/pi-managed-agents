# 会话配置与回答共享提交顺序

原型将配置版本追加到已有的 `messages` 表。历史配置和聊天 Entry 使用同一组原生提交坐标，配置行保存原生文档 ID 及该次生效的值。文档退役占一个位置。读取聊天、装配模型历史和统计完整消息都只选择 Entry 行。数据库视图 `message_entries` 只提供过滤查询。[存储决策](../adr/0345-ordered-agent-configuration.md)

Fork 通过选中回答的真实物理来源、Conversation ID 和提交序号查找配置。Pi 的一次提交是原子的，回答所在提交中排序在它后面的配置变更，也在该回答的 `asOf` 范围内。分支只登记选中配置的引用。源被删除后，仍可选中分叉里更早的一条回答，这也要求保留该回答当时有效的版本。最后的引用消失后，回收同时清理不可达正文和配置。新的运行仍根据其当前环境决定可执行的工具。

## 实验

重跑之前的失败对照。每条轨迹有 13 次真实 Pi 原生提交，测试使用可控模型。第一个模型请求发出时两边都只有 `bash`，返回回答 A 前分别热更新为 `bash + read` 和 `bash + edit`，随后都撤回至 `bash` 再生成 B。每段轨迹在 PG 增加 3 个配置版本。两次模型请求和分叉可见的 3 个历史 Entry 相同；从 PG 打开的两个新 Harness 分别读回与原生 Fork 完全相同的 `pi.agent` 文档。实验还验证了幂等请求、源裁剪及删除、嵌套分叉、回收后再选更早的回答、本地分支首次配置更新前的继承和最后一次回收。[结果](ordered-agent-configuration-20261122.json)

在真实 Chrome、Kafka、PG 和 Cube 上，执行中的 Bash 刷新、第二个 Worker 冷续聊，以及 Stop 发生于 Worker 失联后的原邮箱接管通过。测试模型可检查实际请求。两个场景中，Guest 执行计数均为 1。当前线上组合继续使用原存储。

## 下一项独立的存储门槛

服务中的 `pi-cloud.runtime_world_state` 记录某个 Conversation 最近一次观察到的环境。它声明的 Fork 策略是 `current`。在新分支第一次采样时，控制面配置的 Workspace 可以仍是原来那个，但原沙箱里的后台进程可能已经随着计算实例更换而消失。

诊断使用服务版的 `PiSessionWorldStateController` 和真实原生 Fork，给出两组受控的实例观察值。两段轨迹都先保存回答 A，最后一次观察分别是实例 1 和实例 2。都从 A 分叉，新分支第一次观察到的都是实例 1。服务版控制器只在第二组发出 `sandbox_reset`。候选分支的两组消息、配置及所比较的 PG 数据均相同，冷开后两组都没有提示。这是对会话存储的验证，未在该对照里物理重启 VM，也未将集群的即时资源状态当作会话观察记录。

下一步需要确定该观察值的持久化位置和保留方式。可优先评估每个 Conversation 保存最新的已观察值，在 Fork 时捕获源的当前观察；还需核对旧锚点裁剪、嵌套分支和并发观察的读取边界。该诊断没有更改这项存储。复现时在同一配置验证命令末尾加 `--probe-current-world`，当前退出码为 2。[控制器及文档定义](../../packages/sandbox-supervisor/src/pi-sandbox-continuity.ts)

RF3/PG 传输与恢复回归通过 26 项；另外通过原生共享历史、会话树、历史分页以及前缀和检查点专项测试。Fork 冒烟负载核对了并发重试、裁剪、独立追加、竞态与资源清理。
