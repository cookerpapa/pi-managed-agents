# #52 · 同一分区合批确认工具派发许可

## 同样的命令，不同的许可粒度

一个 Projector、12 条投影 PG 连接、RF3 Kafka 和 4,000 条预连接的逻辑沙箱 WebSocket，
每秒计划输入 4,600 条工具意图。各目标独立，模拟接单延迟 100 ms。本次只改变同一分区
最多多少条意图共享一次派发位置确认，以及新建 Topic 的分区数。每条意图仍有一次独立
PG 投影事务。接收端验证目标、操作编号、顺序和完整数量，PG 核对待回包操作的摘要，
每轮最终检查每个分区的消费组位置。这里度量派发到接单的能力，使用模拟沙箱，不运行 Bash。

每轮 32,000 条，1、8、32、32、8、1 的顺序各测两次。表中速率包含最后一条回执和积压排空。
两种分区配置都使用一个 Projector，所有测试串行运行。

| Topic 分区 | 每次确认 1 条 | 最多 8 条 | 最多 32 条 |
|---|---:|---:|---:|
| 32 | 892–939 次/秒 | 3,523–3,667 次/秒 | 3,804–3,849 次/秒 |
| 64 | 1,274–1,328 次/秒 | 3,307–3,329 次/秒 | 3,504–3,516 次/秒 |

Projector 只取当前已经到达的连续记录，不等凑满。以 32 分区短轮为例，上限 8 时实际平均
每批约 7.4 条，上限 32 时约 21.8 条。Kafka 客户端原有的跨分区合并仍然启用。
“同一分区的许可次数”和“原生客户端提交次数”分别计数。

## 较长的输入窗口

下表每轮发 92,000 条，约 20 秒，生产者实际收到 Kafka ACK 的速率在 4,592–4,593 条/秒。
每轮 4,000 个目标各收到 23 条，所有 PG 摘要和组位点吻合。

| 分区 / 批量上限 | 分发速率 | 每批实际条数 | 同分区许可 / 原生提交次数 | 最大 Kafka lag | 预定输入窗口结束后排空 |
|---|---:|---:|---:|---:|---:|
| 32 / 8 | 3,349 次/秒 | 7.7 | 11,878 / 2,142 | 24,107 | 7.47 秒 |
| 32 / 32 | 3,535 次/秒 | 27.1 | 3,399 / 1,619 | 22,425 | 6.03 秒 |
| 64 / 8 | 3,368 次/秒 | 7.5 | 12,330 / 2,063 | 24,765 | 7.32 秒 |
| 64 / 32 | 3,503 次/秒 | 21.0 | 4,388 / 1,704 | 24,798 | 6.26 秒 |

64 分区试验后回到 32 分区，用最终实现再运行相同长轮，上限 8 和 32 分别得到 3,387 和
3,647 次/秒，积压峰值分别为 23,745 和 21,440 条。所有长轮的 92,000 次 PG 事务均采用
实验原有的事务内异步提交，未把 PG 合批收益混入 Kafka 许可对照。

增加分区拓宽了独立等待许可的并行度，效果在逐条确认时最明显。已经合批后，64 分区长轮
没有给出持续吞吐的明显改善。在上限 32 时，增加分区后实际批次变小，每个 PG 事务的平均
取连接等待从约 1.9 ms 增至 4.6 ms，占用连接的时间约 3.1–3.2 ms。这些实测现象说明
分区数需要和主机、连接池及单分区可聚集的工作量一起估算，不能从并行度推出线性收益。

## 故障边界

预留不同目标的派发容量并逐条投影后，再确认最后一条的 offset + 1。待发命令在许可
前就已解析、匹配到预留的目标并检查发送大小。遇到非普通执行意图、同一目标已占用、
记录不连续或额外容量不可用时结束本批。从旧位置重放时，只准发送尚未被组位点覆盖的
后缀，每次实际开始发送前仍检查分区所有权。

故障测试使用真实三副本 Kafka、独立的旧/新消费者进程、简化的 PG 投影和独立的 PG
模拟发送记录，发送记录表允许重复。旧进程在确认 8 条、写下第 2 条发送记录后立刻
SIGKILL。新进程从 0 重新消费。验证覆盖的 8 条中只有最初的 2 条有发送记录，另外
6 条保持未发，重放也没有制造重复。96 条记录全部能从重放投影读出，工具取消、
绑定关闭和封口均截断批次，模拟准入还阻止了各自后面的一条失效命令。该项验证
消费和派发许可，不把测试用的发送记录当作真实 Bash 或 Agent 超时查询验收。

最坏的不确定范围是每个已获许可批次的未发部分，多个分区同时在途时可以叠加。本轮
支持继续在原型使用批量许可。上限 8 已取得主要收益，上限 32 在两组 32 分区长轮另提高约
5.6%–7.7%。正式服务的准入、挂起的 Stop / 资源关闭与交接仍需在相应发布门槛下验证。

## 单独增加 Projector 的 PG 连接数

固定 64 个分区和一个 Projector，把投影进程的连接池上限按 12、24、24、12 的顺序切换。
每次使用独立的临时 Topic 和 PG，按相同顺序跑上限 8、32 两档，每档 92,000 个意图。
保持三副本、4,000 个模拟目标、100 ms 接单延迟和逐意图 PG 事务，与前述长轮一致。
计时覆盖从向连接池借连接到借到连接，以及从借到连接到事务返回并归还这两个区间。
后者包含客户端、网络和数据库执行时间。测试驱动另行记录实际打开的 Projector 连接数。

前四次按上述顺序完成。24b 的上限 8 轮未达到计划输入，追加 24c 复核。下表保留全部结果。
十轮均核对了每轮 92,000 条发送、接收与 PG 操作，排空后核对消费组位点，五套临时资源均已清理。

在输入达到约 4,600 条/秒的轮次，扩池缩短了两个批量档位的取连接等待。以上限 32 为例，
等待从 4.17–4.67 ms 降到 2.48–2.75 ms，但拿到连接后的持有时间从 2.95–3.15 ms 升到

2,002 条/秒，取连接和持有都慢。24c 在目标输入下重新观测到较短的取连接等待。
本机没有观测到从 12 扩到 24 条就能稳定分发 4,600 次/秒的结果。

## Stop 和独立派发 Topic 的取舍

活跃 Run 的 Stop 先登记为取消请求。Worker 启动原生取消，通过 Session 日志提交操作取消，
当前 Run 的有序终态再投影到 PG。原型在同一分区遇到取消、绑定关闭和封口时会截断派发许可。
已经送上网络的命令仍可能稍后才到沙箱，Run 的取消终态也不能证明物理进程已经退出。
[取消请求](../../packages/control-plane/src/control-plane-store.ts) · [Run 的取消收尾](../../packages/runtime-core/src/run-cancellation-executor.ts)。

如果改成独立派发 Topic，旧命令可能还在积压，而 Session 已经投影为取消。若产品要求停止
生效后不再发出旧命令，独立派发器也必须关闭该 Run 的发送权限，处理尚未发出的旧命令，
并让相关组件知道何时关闭完成。把 Stop 追加到第二个 Topic 的末尾，旧命令仍然排在前面。
本轮只评估单链路上的连接池大小。

## 部署时增加分区

本次 32 与 64 使用两份独立的临时 Topic。当前正式 Session 日志对同一代 Topic 的分区数
做一致性校验，生产者按物理 Session ID 的哈希和分区总数选分区。直接原地增加分区可能让
某些 Session 的后续消息进入另一个分区，历史记录仍留在旧位置。正式扩容需规划新一代
Topic、会话路由和已有恢复位置的交接，或在首次建集群时选定较高分区数。
[当前代码](../../packages/runtime-core/src/execution-log-topic.ts) · [Kafka 官方运维文档](https://kafka.apache.org/43/operations/basic-kafka-operations/)。
