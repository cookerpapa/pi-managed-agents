# Independent Session input and explicit agent messages

The subsequent [boundary implementation and measurements](pg-input-boundaries-20261126.md) supersede the immediate delivery of pending mail described in this report.

This is the isolated #52 storage candidate. A ready row is unique by tenant and logical Session. The existing management socket serves two purposes. An idle slot receives a claim hint, while a full Worker can receive a message hint for one of its current leases. The listener carries identities only. Reconnect resynchronizes owned Sessions, and the Worker reconciles pending inputs in one query per active boot heartbeat. ## Delivery and withdrawal

A strict initial submission locks its target Session. A busy-mode submission keeps its request identity across the active/idle boundary. The Turn anchors history and fencing. The ready directory never contains one entry per waiting message. The prototype permits 64 outstanding human messages per sender and Session. It pages native delivery in groups of 32 and the Web queue in groups of 20. Agent mail carries its sending Session identity and does not consume the human allowance.

Registered, handed to the Worker, queued in Pi, and placed in the transcript are distinct states. Before handoff the API can withdraw locally. After handoff it saves the withdrawal and the owning Worker arbitrates it with native placement. A successor can settle an unsubmitted input only after ordered closure and native restoration. A missing native submission with known prior admission is an error. Native receipts update the input row in the accepted projection transaction. Returning the draft retains text, upload references and a request ID until the browser acknowledges restoration. Replaying the browser acknowledgement cannot restore the same returned input twice to the same composer. An explicit change checks the target and the neighboring human input inside the Pi transaction.

A named delegation atomically registers the child, frozen ranges, first input and creation acknowledgement. Later reports use `send_message(to, priority, text)`. The executor resolves the address in the caller's family and commits the input plus its acknowledgement. Child completion appends to the child's history. Closing a parent retires its undeliverable tool acknowledgements. A Web Fork inherits history while starting with an empty mailbox.

## Verification scope

The transport coverage uses disposable PostgreSQL, a three-broker Kafka fixture, real Pi, a deterministic model and separately killable Workers. The browser check drives the shared composer submission controller, delivery indicator and pending-input component in headless Chrome against the candidate HTTP API. It submits while a one-slot Worker is occupied, takes a message back and preserves an existing draft. The test also checks attachment references, five concurrent strict starts, lost handoff before native submit, ordering, promotion, late withdrawal and child reports across Workers. The front end and control API use the candidate in this test composition. Production rollout remains under #48. `wait_for_input` remains deferred.

Input work takes the Session lock before touching the admission rows. The Projector takes that lock only on frames carrying an input receipt or a queue change. Before this change a Worker could hold the Turn while waiting for an input row held by projection, and an API admission could wait on a conflicting foreign-key check. The stress test exposed both lock cycles. The ready hint carries tenant and Session identities for delivery to the current boot. The queue generation advances only for human-visible changes.

The standalone 32-click Chrome trial measured 1.5 ms P95 and 1.7 ms P99 from click to the sending indicator entering the DOM. These are DOM timings on a local headless browser. In a separate 32-message series on the same run, HTTP submit to its registration receipt took 12.4 / 12.9 ms P95/P99. PG registration to native Inbox projection took 19.7 / 20.3 ms. This last timing is sampled inside the receipt transaction. HTTP submit to observing the queued status took 35.2 / 35.4 ms and includes observation delay. The latency fixture directly delivers native commits to the ordered projection function. Real Kafka handoff is tested independently.

The PG benchmark replays the same 256-Session, 20-tool trace over 32 partitions. One Run contributes 41 visible outputs. Each trial therefore projects 10,496 visible outputs and 47,616 native commits. Baseline and candidate both use independent Session projection. Only the mailbox receipt path changes. This measures the PG projection leg and excludes provider latency, real device execution, socket capacity and end-to-end fleet throughput.

The matched transport run passed all 51 cases across 29 files. Its browser trial measured 1.5 / 2.0 ms click-to-DOM and 20.7 / 23.8 ms PG-registration-to-Inbox P95/P99. The Worker wake test counted one PG listener for 32 Workers, one claim query for one arrival, eight for eight committed Sessions, and zero idle claim queries between reconciliation ticks. Type checking passed across the workspaces. The existing browser queue regression also passed after updating its fixture to supply the returned-draft and acknowledgement callbacks used by the application.

For the 256-Session trials, the eight-trial order was baseline, candidate, candidate, baseline, candidate, baseline, baseline, candidate. Measured rates were 527, 539, 745, 1,027, 974, 1,018, 1,003 and 937 visible records/s in that order. Both paths made 22,016 projection transactions per trial. The baseline used 10,496 synchronous transactions, and the candidate used 10,752. The difference is one confirmed input admission per Session. A second series with two warm-up trials still showed large changes within each implementation, including the baseline falling from 980 to 570 visible records/s. A single sequential comparison cannot separate host variation from mailbox overhead.

The shorter counterbalanced check used 32 Sessions per sample, with the same 32 partitions and 20-tool traces. After two warm-up samples it compared twelve adjacent baseline/candidate pairs, alternating which ran first. Baseline and candidate medians were **939 and 888 visible records/s**. Taking the percentage difference within each adjacent pair gives a median of **−5.2%**. Each path used 2,752 PG transactions. The candidate changed 32 additional transactions to synchronous, one per input. This measures the combined cost of admission locking, receipt materialization and confirmation. It does not attribute the entire difference to WAL flushes or predict peak production capacity.
