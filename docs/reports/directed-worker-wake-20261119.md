# Worker 定向唤醒与批量领取压测

本实验比较了一次入队通知送给全体 Worker 和只送给有空位的 Worker 两种方式。在两种情况下，Run 都先提交到 PostgreSQL，Worker 都以同一条带 `SKIP LOCKED` 的 SQL 领取，每条被领的 Run 都获得独立的领取身份。路由器只保存当前管理连接、等待连接的顺序和一个待发送提示位。[复现步骤](../../scripts/experiments/minimal-session-storage/README.md) · [聚合数据](directed-worker-wake-20261119.json)

## 1,000 条连接收到 171 次入队通知

一次只新增 7 个 Run 时，广播产生了 1,001 次实际领取查询，其中 998 次返回零行。定向方案两次都是一次 SQL 领完 7 个。广播的 1,001 次含一次定时补问。

随后在一秒内发出 171 批、每批 7 个 Run。三个阶段分别使用 1,000 条等待连接，按定向、广播、定向顺序执行。每个阶段都核实 1,197 条 Run 完成，领取身份唯一。发起端提交完所有通知用了 997–1,001 ms。

| 一秒突发，1,197 个 Run | 广播 | 定向第一次 | 定向重复 |
|---|---:|---:|---:|
| Worker 收到的入队提醒 | 171,000 | 171 | 171 |
| 实际领取 SQL | 2,005 | 219 | 242 |
| 其中空查 | 1,855 | 27 | 36 |
| PG 登记至领取 P95 | 2,802 ms | 12 ms | 13 ms |
| 从开始发起到确认全部完成 | 3,995 ms | 1,026 ms | 1,025 ms |

一次通知与一次 SQL 没有固定对应关系。每个客户端同时只允许一次领取查询，查询过程中收到的多条提醒可以合并。广播仍让大量连接同时接收数据、竞争 PG 连接池并查空。千连接负载的 WebSocket 处理也位于同一进程，因此观测到的耗时同时包含进程调度、数据库连接排队和 SQL。定向方案将实际领取 SQL 减少约 88%–89%，这不能直接外推到使用一千条原生 PG LISTEN 连接的部署。

持续 30 秒按每秒 171 批注入，定向方案完成 **35,910 / 35,910** 个队列任务，PG 登记至领取 P95 **14 ms**，P99 **18 ms**。实际发送了 5,130 次入队提醒和 150 次定时补问，领取 SQL 共 7,470 次，其中空查 1,013 次。这个数字只度量单主机的队列与唤醒能力。真实 Pi 运行、模型额度、跨主机 PG/Kafka 扩展需要独立评估。

## 测量口径

- 真实执行测试在两个独立的 K3s Worker Pod 各运行一个实验进程。Pi Harness 使用本地模型，普通负载没有人为等待，产生 4 KiB 回答。原生提交和独立结束信号经过真实 Kafka，使用 32 个分区、三副本及两个最小同步副本。Projector 将数据投影到正常写 WAL 的专用 PG 数据库。30 个唤醒对照场景共完成 8,647 个 Run。每轮逐条检查最终正文、顺序和完成状态，并验证 Kafka 积压清零。
- 实验管理端和 Projector 在同一个 Session runtime Pod 内运行。Worker 通过真实的跨 Pod WebSocket 举手。管理端将每次 PG 提醒发给所有连接或少量等候连接。两组使用相同的 WebSocket、领取 SQL 和存储链路。生产环境仍使用原有管理协议和 PG 通知。
- 千连接测试在同一主机上打开 1,000 条真实的回环 WebSocket。每条连接独立判断空位和提出领取请求，共用最多 12 条 PG 连接，其中 1 条订阅通知。独立的负载进程每批提交 7 个独立会话的 Run，再发送一条真实 PG 通知。所有已领取的 Run 均用带领取身份的 PG 更新结束，并核对唯一 Run 和领取身份。该测试绕开模型、Pi 和 Kafka，以单独观察唤醒和队列。
- 表中的空查是实际发给 PG、返回零行的领取语句。总领取查询含成功和空查，不含入队、完成、通知、观测 SQL。千连接阶段的初始化扫描单独完成。PG 排队时间取同一数据库时钟上的行创建时间至写入领取时间，端到端时延从客户端发起请求计至收到 PG 终态确认。

## 恢复边界

正常路径在一批入队事务提交后才发提醒。每 200 毫秒最多补问一个等待者。只有一个 Worker 时，如果它的举手消息丢失，或者它已被移出等待名单、定向提醒却丢失，名单会暂时为空。Worker 每隔约 3.2–4.8 秒重新举手可以恢复。改进方案在名单为空时也允许同一个定时器轮流问一条在线连接。已经满载的 Worker 在本地忽略提醒。管理端不因计时器本身查询 PG。

200 毫秒是每个管理实例的补问间隔。在多人同时漏报或连接不可用时，发现某个特定 Worker 所需时间还取决于轮转、重新举手和连接恢复。缩容和扩容用开关实验 Worker 的接单连接验证。该范围涵盖领取与现有执行的排空，生产 KEDA 扩缩、跨主机延迟、多管理副本的重复提醒和 Session 租约接管需分别验证。

| 定向唤醒故障场景 | PG 登记至领取 | 观察到的结果 |
|---|---:|---|
| 漏掉 PG 入队通知 | 200 ms | 已举手的 Worker 被定时器叫醒 |
| 漏掉发往唯一 Worker 的提醒 | 199 ms | 名单为空，定时器轮询到这条连接 |
| 漏掉唯一 Worker 的首次举手 | 198 ms | 在线连接被补问，本次领取找回了任务 |
| 管理连接中断 | 108 ms | Worker 重连后的第一次 PG 领取发现任务 |
| 只补问名单中的 Worker，分别丢提醒或丢举手 | 3,802 / 3,698 ms | 等到 Worker 再次举手才找到该 Run |
| 两个 Worker 都离线时登记 8 个 Run，随后接入一台 | P95 66 ms | 8 个都由该 Worker 的首次查询领走 |
| 单独停止实验唤醒进程，其停机期间登记 8 个 Run | P95 644 ms | 新进程收到零条原入队通知，Worker 重连后取回全部 8 个 |

缩容测试在首台 Worker 忙时关闭其接单连接，它完成已领取的 2 个 Run。另一台上线后完成剩余 14 个。单空位被一个 850 ms 模型请求占用时，Worker 在本地忽略补问。另行验证了同一会话前序 Run 被锁定和运行中时，批领 SQL 都无法越过它。旧连接迟到的关闭事件也无法撤销替代连接的举手。

## 两个真实 Worker 的结果

每次以 90 Run/s 注入 10 秒，四次都是 900 个全部完成。下表每格给出同一配置的两次结果，控制组和实验组交替运行，批领上限都是 8。

| 每 900 个 Run | 广播 | 定向 |
|---|---:|---:|
| 总领取查询 | 1,837 / 1,785 | 945 / 947 |
| 返回零行的领取查询 | 973 / 918 | 70 / 68 |
| PG 登记至领取 P95 | 16 / 15 ms | 14 / 14 ms |
| 提交至 PG 终态 P95 | 107 / 89 ms | 74 / 77 ms |

在 64 并发、每轮 384 个短 Run 的突发对照中，固定定向唤醒，单条领取的 PG 排队 P95 为 275 和 308 ms，批领上限 8 的两轮都是 41 ms。批领减少了填满 Worker 时的数据库往返。同一次测试中，后续独立窗口的端到端吞吐在 115–341 Run/s 间波动，完整应用的持续容量仍需单独测量。

在 20 Run/s 的稀疏输入下，将合并窗口由 5 ms 增至 20 ms，每 100 个 Run 两种设置都发了 100 条 PG 通知。客户端提交至领取确认 P95 由 19–21 ms 增至 32–33 ms。对交互消息保留 5 ms 更合适。密集入队时，20 ms 窗口确实合并了更多提醒。

本次结论适用于继续评估 5 ms 入队合并、最多批领 8 个和每实例 200 ms 一次的定向补问。临时数据库、Kafka Topic 和消费组已核实移除，跨 Pod 实验使用的两条临时网络策略也已删除。唤醒实现位于实验目录，线上继续使用现有领取路径。
