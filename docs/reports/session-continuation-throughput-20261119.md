# 连续 Run 与 Worker 缓存亲和的原型压测

## 实测吞吐

同一主机、两个 Worker 上，混合负载两次以 100 Run/s 连续发两分钟，每次 12,000 个全部完成，两次实测均为 99.96 Run/s，终态 P95 分别为 185 和 230 ms，停止发起后分别用 59 和 61 ms 排清。最终一轮中 6,000 个新会话首次启动，另外 6,000 个续聊有 4,526 次命中已确认的历史前缀。下面四组由相同的单行投影语句、批领与缓存配置连续执行。

| 输入场景 | 输入速率与时长 | 完成 / 计划 | 实际完成 Run/s | 提交至终态 P95 | 停止发起后排清 |
|---|---|---:|---:|---:|---:|
| 全部新会话 | 120/s，60 秒 | 7,200 / 7,200 | 119.81 | 543 ms | 99 ms |
| 全部续聊，起始 512 KiB | 110/s，60 秒 | 6,600 / 6,600 | 109.90 | 176 ms | 62 ms |
| 新会话、续聊各半 | 100/s，120 秒 | 12,000 / 12,000 | 99.96 | 185 ms | 59 ms |
| 新会话、续聊各半 | 116/s，60 秒 | 6,960 / 6,960 | 115.85 | 208 ms | 85 ms |

独立重复 116/s 混合负载时也全部完成 6,960 个，P95 为 778 ms，但最后一次发起后用了 1.59 秒排清，含排清的实际吞吐为 113.02 Run/s。这一轮超过了本文的 1 秒排清门槛。提高输入速率后出现长尾。独立的一分钟窗口中，混合 120/s 时完成 6,974 / 7,200，终态 P95 为 5.77 秒。全续聊 140/s 时完成 7,276 / 8,400，P95 为 5.79 秒。全新 160/s 时完成 9,257 / 9,600，P95 为 2.89 秒。这里的差额都是发起器达到在途上限、尚未发出的请求。已经登记的 Run 最终全部完成。早期 20 秒的新会话窗口曾跟上 190/s，不能将其用作一分钟或全天的保证。

全新 160/s 时，提交至领取确认 P95 为 37 ms，进入模拟模型为 251 ms。结束记录从 Worker 创建至 Projector 开始处理为 2.68 秒，终态 PG 事务自身 P95 为 13 ms。样本中 Kafka 最大处理位置差为 2,534。这段等待包含发布、传输及等同分区前序投影完成。连续同一会话的下一轮还需要等前序终态提交，因此积压也能反映在它的首次模型调用时间上。

对同一 140/s 混合负载依次使用显式事务、单语句、单语句、显式事务。普通单步 Run 平均 Projector SQL 从约 11.5 次降至 4 次，含事务命令。四次实际完成速率分别为 116.21、118.11、139.60 和 139.65 Run/s。后两次的发起请求全部完成。主机独立哈希校准中位数依次为 7.56、9.02、2.12 和 2.14 ms。由此可以确认 SQL 往返减少，端到端吞吐的变化不能全归因于 SQL。原型默认用单语句完成符合条件的一行写入，涉及 Inbox 和正式消息的混合批次仍在一个事务内处理。

## 测量范围

两台实际 Worker Pod 各运行一个实验进程，每个进程最多同时运行 128 个根会话。Worker 最多一次领取 32 个 Run。入队提醒在提交后合并 5 ms，正常情况下定向发送，另有每实例 200 ms 的单连接补问。每个普通 Run 经固定版本 Pi Harness 调用本地确定性模型，生成 4 KiB 的回答，通过三副本 Kafka 和单个 Projector 写入 PostgreSQL。计时从客户端开始登记，一直计到 Projector 确认终态事务提交。Kafka 有 32 个分区，最小同步副本数为 2，Projector 使用 12 个 PG 连接。[实验命令](../../scripts/experiments/minimal-session-storage/README.md) · [分组数据与源码摘要](session-continuation-throughput-20261119.json)

三种主要工作负载分别是每次新建物理会话、在 128 个已有会话上反复续聊，以及二者各半。续聊从每个会话 512 KiB 的独立合成历史开始，后续用户输入和完整回答都会增长这段历史。大上下文对照单独使用 16 个已有会话，每个起始历史 4 MiB。所有续聊从正常收尾的根 Conversation 开始。实验用 PG 领取 UUID 隔离写入，在不同 Run 正常交接时使用会话队列位置作为递增代数。运行中崩溃后的同 Run 租约接管、原生子任务、Web/SSE、真实沙箱、计费和外部模型推理均需在完整系统另测。

开环测试按独立时钟安排每一条请求，生成器最多允许 384 个请求在途。超出在途预算或发起器迟到而尚未发出的请求单独计数。每档结束后逐条核对已接纳请求、模型输入的历史顺序、完整回答及 PG 终态，等待所有 Kafka 分区排清。突发测试使用固定并发，整波耗时含排清时间。为了区分短时峰值，本文的“一分钟通过”要求整整 60 秒没有未发出的请求、终态 P95 和停止发起后的排清时间都在 1 秒以内。这是本次实验选定的判据。

公开汇总包含 75 个集成负载和正确性样本，共完成 178,814 个 Run。另有 4,348 个预定请求在超载组未发出。各次实验的起始版本与实际 Worker、Projector、唤醒器代码摘要分别保留。早期显式事务对照仍列出当时的执行路径，最终配置的功能回归、混合负载复测和突发样本标为 `accepted-*`。

## 会话历史与领取

PG 在原有终态更新里一并登记稳定历史版本、原生提交序号、下一个 ID、有效历史起点和覆盖的条目数、字节数。Worker 领取下一轮时，在同一条 SQL 取得已完成前序的版本和 Inbox 当前值。新 Run 使用新的领取身份和 Harness，读取最新用户输入并配置模型。命中后从只读 Entry 恢复原来的提交位置，未命中则从 PG 读取有效范围。已经确认过的历史不再随新 Run 写回 Kafka。Inbox 仍然在同一行保存完整最新队列，消费输入与正式用户消息的写入仍然原子提交。

起始缓存阈值取 256 KiB，每个 Worker 预算 96 MiB 序列化数据，保留 5 分钟并按最近使用逐出。可复用内容包括普通文本、配对并已写成正式历史的工具调用和文本结果。相同 Tool Call ID 可在不同轮次重用。含图片、未配对调用或不支持的附加数据的前缀走 PG 冷读。Node 的实际总 RSS 还包含 JS 对象、活动 Harness 及其他缓冲。缓存候选可在 Kafka 确认终态发布后形成，必须匹配下一次领取返回的 PG 版本才能使用。旧 Worker 已满或离线时，正常 FIFO 随时可以领取该 Run。一个 Worker 的领取事务有真实缓存线索时最多优先提升一条，其他名额从普通队列取得。

正确性验证覆盖版本变化、截断到新上下文标记、从更早的种子边界分叉、租户和会话隔离、Worker 离线、更换模型、缓存逐出、旧身份和重复投递的终态、同会话多个在途请求，以及续聊中的 steer/follow-up。针对故障和版本的样本逐字节核对模型看到的文本。负载样本核对每条消息的角色、长度、首尾标记和顺序，并在计时后逐条验证当轮正式消息正文。分叉和历史修改使用静止会话夹具，未改动生产分支和历史保留实现。

## 短时吞吐与缓存收益

两个 Worker 完成一批 1,024 个全新会话时，以 64、128、256 个并发客户端分别测试，再按逆序重复。在显式 PG 事务路径上结果为 103–347 Run/s。同机独立的 4 MiB SHA-256 耗时中位数在这些阶段从约 7–8 ms 变为约 2 ms。最终候选的单语句配置完成相同六组突发，实测 94.86–402.82 Run/s。最高一组用 64 并发，终态 P95 为 212 ms。单次突发值不足以建立全天容量。

在 64 个起始历史 512 KiB 的会话上，每秒发 40 条消息，每组 640 个 Run，按禁用缓存、只用本机缓存、定向唤醒和逆序各跑一次。全部请求都完成。每个会话第一次访问也计入测量。

| 策略 | 同一历史前缀命中 | 每 640 个 Run 从 PG 读取的历史正文 |
|---|---:|---:|
| 关闭缓存 | 0% | 334.1 MiB |
| 只用碰巧位于本机的缓存 | 44.1%–46.6% | 176.8–186.3 MiB |
| 优先提醒已举手的缓存持有者 | 83.1%–87.3% | 41.0–55.2 MiB |

表中字节数按从 PG 读回的正文 UTF-8 长度计算。64 个客户端持续补交时，同样 512 KiB 的历史在定向模式下命中约 45%。领取者可以继续排清 FIFO，一批 32 个 Run 也只为一个命中线索改变优先顺序。此处缓存的主要可复现收益是减少读取正文。对起始 4 MiB 的历史，16 客户端并发、每批 192 个 Run，关闭缓存两轮为 34.89 和 44.75 Run/s，定向缓存两轮为 44.35 和 56.78 Run/s。该组是闭环突发测量。

一次额外 follow-up 或 steer 会改变每个 Run 的工作量。在 512 KiB 起始历史、64 并发的测试里，384 个带 follow-up 的 Run 实际各请求两次模型，吞吐为 78.05 和 234.88 Run/s。steer 组每个 Run 正好执行一次固定测试工具并请求两次模型，吞吐为 94.65 和 167.65 Run/s。工具历史纳入缓存后，串行对照的三个 Run 依次冷读、命中、命中，并验证模型收到之前的完整调用参数和工具结果，历史工具没有再次执行。生产沙箱耗时需按实际工具负载另测。

## 测量过程中的异常

第一次投影顺序对照完成并排清了四个负载阶段，但一台实验 Worker 在退出时返回 139。此轮未纳入正式数据。独立检查确认专用数据库、Topic、消费组和临时网络策略均已移除，两个正在服务的 Worker Pod 保持 Ready 且未重启。实验程序现等领取、执行、Kafka 生产者和 PG 连接排空，收到清理确认后让 Node 自然退出，并要求退出码为零。重新执行同一对照后通过。原始退出异常缺少原生调用栈，不能确定具体原因。
