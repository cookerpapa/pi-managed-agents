# 候选库的子 Agent 状态与回答

在已有 `subagent_conversations` 上保留一份原生执行证据，包含当前活动状态、已确认停止、
调用任务收尾情况、原始输入对应的回答 Entry ID、提交序号和观察时间。Pi 继续调度子
Conversation。Projector 在原生提交已被接纳后，与原分区进度一同写入有变化的子关系。
未送达和不确定的请求不会确认取消。子会话仍有任务或输入时显示运行中；父 Run 已经
结束但子工作没有结论时，状态视图保留 `unknown`。原生队列和历史正文保持各自的读取路径。

核对了以下行为：

- 两个创建前停止请求的控制输入相同，只有 A 或 B 的停止送达。候选和旧状态视图在父
  Run 收尾后均分别返回「已取消／未知」和「未知／已取消」。候选仅子关系行产生证据差异。
- 真实 Pi Harness 的原始输入成功、模型报错及正在生成时 abort 分别投影为 completed、
  failed、cancelled。又发一条输入时，已完成的子会话重新进入 running，再次完成后仍
  能找到第一条输入的原回答。单独验证了旧写入者、重复投递和调用任务的取消标记。
- 两种真实 Cube 回包时序分别在接手之后返回，或在接手前已收到两份；后者包含真实的上轮
  上下文压缩。每组 Bash 实际执行一次，API 的子状态为 completed。list 能找到该子任务，
  status、wait 和聊天页一致。原任务结果和后续输入的最后回答特意做成不同文本，并逐一核对
  返回的 Entry。测试使用受控模型，故障时序、Pi、PG、Kafka 和 Guest 均实际执行。
- 一个有 20 次工具调用的受控子任务产生了 185 次原生提交，只有 2 个提交需要写入子状态。
  这是实际提交次数，不是整套服务的吞吐测试。

## 长历史读取

使用 PostgreSQL 17.6，单个 Run 含 131,072 条正文，其后还有 40 个短 Turn。列表包含 31 个子任务，
每次取前 24 个。各项分别暖身后串行测量 31 次，结果读取传入已知状态。下表是客户端耗时；
每行一条 SQL。

| 读操作 | P50 | P95 |
| --- | ---: | ---: |
| 查状态 | 1.51 ms | 1.96 ms |
| 列表首页 | 2.05 ms | 2.46 ms |
| 原任务的回答 | 1.10 ms | 1.64 ms |
| 最新回答靠近末尾 | 1.09 ms | 1.39 ms |
| 子任务很早结束，最新回答在 Entry 1023 | 39.95 ms | 43.83 ms |

原查询先关联历史再从关联结果中选一行。在相同的靠近末尾场景中，执行计划过滤
130,171 行，P95 为 69.05 ms。现用 LATERAL 先固定子会话，再按原生 Entry ID 倒查一条回答。
同一索引在这个场景只需过滤 120 行；第二次独立运行的 P95 为 1.37 ms。
早早结束的子会话依旧需要越过后续其他会话的约 13 万行。原始回答可用已有的准确 ID
直接读取。若需要给任意历史位置的最新回答也提供稳定延迟，应对照测量
Conversation 范围内的助手 Entry 索引对写入的代价，再决定是否新增索引。
这里测的是 SQL 读取；服务混合读写、完整交接及发布压力仍是独立门槛。

复现用 `node scripts/run-with-test-postgres.mjs -- node --import tsx scripts/experiments/minimal-session-storage/read-query-study.mjs --child-outcomes`。
完整传输回归通过 18 个文件的 30 项用例。

## 下一项保留策略

在真实的控制面创建事务提交后、进入 Worker 的原生创建方法之前读取 list。
旧路径已经能用原始 native intent 给出任务描述。候选返回相同的子编号和 preparing，
但此时还没有子输入 Entry，任务描述为空。子输入已放入历史之后，两边的列表描述一致。
创建前取消的子关系可能始终没有输入 Entry。尤其是工作流动态计算的 hostcall 参数，
不能普遍依赖父会话里可见的脚本来还原原文。

如果产品要求 list 在这个窗口也显示原任务，可在登记关系时保存现有列表契约规定的
最多 160 个 Unicode 字符，并供列表读取。若接受列表先只显示身份与状态，可以保留现有
策略，等原输入出现后再显示描述。列表摘要与子页面是否需要显示尚未放置的完整提示词
是两项不同承诺。本次没有多存任务文本，也没有修改线上数据库。
