# Projector 到 PostgreSQL 的读写成本

这次审查沿单条消息从 Kafka 到 PG 提交、页面可见和恢复的路径执行。单机 K3s 的服务链路与隔离数据库使用同一台 PostgreSQL 17.6，保持 `fsync=on` 和同步提交。端到端测试使用本地模拟模型。隔离实验逐层启用真实投影方法，单独测量了原始追加、索引、原生恢复状态、网页展示、计量、写入身份检查和收尾。

[字段、索引、外键、触发器、视图和脱敏 SQL](projector-pg-catalog-20261118.json) · [各轮测量](projector-pg-review-20261118.json) · [复现命令](../../scripts/experiments/projector-sql-20261118/README.md)

## 两处修复

1. **稳定写入与冷启动共用同一段最新位置查询。** 先在 `pi_durable_commits(tenant_id,session_id,seq)` 主键上倒序取一条，再与该 Session 的唯一继承基线比较。获胜行同时提供 `seq` 和 `next_id`。独立保留按收到的序号查指纹、检查空洞和 ID 倒退、验证未重放的 live 检查点等逻辑。测试覆盖空库、只有分叉基线、两种来源各自较新、有效平局、迟到的相同和冲突提交。10 万条本地收据加其他会话的 8,192 条收据，用户态正式代码实际编译出的 SQL 在 PG 上的执行中位数从 22.214 ms 到 0.249 ms，本地分支输出从 100,000 行到 1 行。8 条时是 0.213 和 0.214 ms。两版沿用同一套索引。
2. **全新根会话只写一次云端初始配置。** Pi 先创建根 Conversation。Worker 把首份环境观察、云端 Run 配置和 Pi Agent 配置放进下一次公开的 `conversation.commit`，成功后才记住已观察到的环境，再接受用户输入。进程在绑定前失败只留下原生根，绑定成功后替代 Worker 能同时读到两份文档。已存在的会话、Fork、子会话、恢复、手动压缩和后续真实环境变化各自保留原有处理。实测 192/192 个新会话的两份文档具有同一创建序号。每 Run 需要 PG 事务的原生提交由 8 次变成 7 次，计数轮平均 61.73 次原生 PG 调用，之前同形负载约 70 次。该数包括事务命令。[ADR-0338](../adr/0338-initial-world-and-run-binding.md)

## 整条路径怎样落库

| 顺序与工作 | PG 实际读写 | 消费者和失败边界 |
|---|---|---|
| Kafka 分区领消息 | 同一物理 Session 的消息按顺序进入一个分区。分配和恢复时读取 `accepted_fact_projection_offsets`、未封口 Run 的首位置、`pi_durable_current` 的最早待重放位置。 | 一条分区记录可以属于其中任何一个 Session。重分配从安全的起点开始，已覆盖的稳定内容可以验证后跳过。 |
| 判定写入身份 | 内存保存已验证的 writer/Run 边界。稳定写入在事务中按 Run、租约、物理 Session 的顺序锁定记录，再读取锁后最新的原生状态。 | 保护迟到的旧 Worker、并发接管和未确认的 PG 提交。执行工具的沙箱不查 Worker 租约。 |
| 判断提交与生成派生数据 | 查询当前 head、本批序号对应的收据、涉及的文档/父任务来源、Fork 基线。纯 live 首次需要保护原 Kafka 位置。只读重放校验原始指纹。 | 一批可以同时包含 Entry、Submission、Task、live 与 usage。后续已保护的纯文本增量可从 Kafka 推进内存和前端。 |
| 写入原生历史 | 一条数据修改 CTE 插入 `pi_durable_commits`，写不可变 `pi_history_records`、正文对象 `pi_history_bodies`、归属引用 `pi_durable_write_refs`，更新 `pi_durable_owned_records` 与相应 `pi_durable_current`。按文档语义维护修订索引。 | 收据、当前值、记录位置和指纹在同一事务中一致。正文通过不可变引用供原会话和 Fork 共用。 |
| 构建可展示条目 | `captureNativePresentation` 按刚写入的序号回读记录、归属、正文大小、关联任务和 Tool 配对。复用/创建 Turn 块、写展示描述和 `pi_history_frames`。系统 Entry 跳过。 | 活动页面从原生数据分页，冻结页面使用不可变范围。普通助手正文由原生对象持有，展示描述另存时间和关联等元数据。人工输入、附件及无结果 Tool 有额外分支。 |
| 输入确认、计量与覆盖 | 人工变更按精确操作 ID 在提交后向订阅者确认。`model_invocations` 和 `model_metering_events` 与被接受的原生结算同事务。根据需要更新根 Run 或子会话的页面覆盖序号，并推进分区位置。 | 保证刷新时历史与实时文本可交接。计量区分服务商实际用量与用户可计价执行。`pi.usage` 只服务会话累计查询。 |
| 普通控制通知 | 初始 Run 的排队、领取等动作会触发 PG Outbox，经过同分区交付。输入队列订阅者按需刷新。仅有检查点的控制消息常见 SQL 是 BEGIN、一次单调 UPSERT、COMMIT。 | 观察到“没有 follow-up”仍可能需要显示首次输入从排队转为已领取。关闭沙箱绑定时还有持久确认，不能把所有控制消息当作丢弃型通知。 |
| 正常收尾 | 先关闭旧 writer 的执行路由，再核对原生 head、收齐必要 live 检查点、提交 Run 转移、终态事件、会话状态、writer 退役和计量闭合。随后冻结历史头和目录，推进队列。 | 新计数轮每条正常 `work_finished` 的内部事务都是 25 次 PG 调用，外层路由关闭另有 5 次。内部第 11 至 21 次用于根会话的冻结头和可见范围目录，占本轮内部 SQL 调用时间的 37.6%。 |
| 停止、失联、Tool 与恢复 | 封口按控制意图和旧写入前缀验证。用同一事务处理检查点和退役。派发外部 Tool 前必须确认 Kafka 进度，替代 Worker 按原回复 Topic/offset 恢复。图片与附件另由持久引用保护。 | PG 回放不得重复运行 Shell。暂停、故障期间的已见文本、迟到回包及无有效 usage 的财务行为各有专门语义。独立 Tool 主机和资源管理器的业务写入不在“保存一条答案”的计时里。 |

稳定消息的 SQL 分支在[原生投影](../../packages/runtime-core/src/postgres-durable-commit-projector.ts)、[存储](../../packages/pi-session-postgres/src/durable/postgres-projection.ts)和[共享正文](../../packages/pi-session-postgres/src/durable/shared-entry-bodies.ts)。正常收尾在[生命周期投影](../../packages/runtime-core/src/work-finished-projection.ts)和[展示目录结算](../../packages/runtime-core/src/presentation-settlement.ts)。

**以一条完整回答为例。** 在新计数轮的 192 条回答中，142 条的原生投影是 14 次 PG 调用。BEGIN、事务超时设置和 COMMIT 占 3 次，锁定本轮写入身份 1 次，合并此前 live 收据、读取提交前状态和执行原生写入共 3 次，财务证据 3 次，查找并建立可见帧 3 次，推进页面覆盖与分区进度 1 次。另有 49 条用了 13 次，1 条用了 12 次。SQL 目录的汇总次数还包含外层处理和部分重叠的异步观察读取。

## 表与索引的归属

目录列出了本次边界内 **46 张物理表、13 个普通视图、202 个索引**。其中 88 个是部分索引。正常短文本计数轮的 SQL 直接提到了 27 张物理表和 2 个视图。其余对象服务于分支、退出、恢复、附加文件、资源路由或管理操作。视图本身没有独立索引。命中次数是 SQL 模板的调用次数，不能用来推断某个物理索引有没有被规划器使用。目录采自运行中的布局 226，性能分支的 228 标记检查既有业务数据格式，不增加物理表或索引。

| 数据族 | 热点、索引和读写取舍 |
|---|---|
| Run、会话、租约 | `runs` 有 59 列和 22 个索引，包括领取、每条 Lane 的唯一活动/就绪 Run、幂等、可见历史与未封口前缀。状态变化会维护相应部分索引并触发通知。普通展示序号更新和状态转移影响的列不同。`sessions`、`pi_sessions`、`session_leases`、`run_transitions`、`turn_control_requests`、`session_terminal_events` 各自承担逻辑会话、物理所有权、转移或可恢复控制的事实。分区检查点只有一个主键。 |
| 稳定原生状态与序号 | `pi_durable_commits` 的主键同时服务精确重投与有界的最新位置查询，另有控制引用的部分索引。`pi_durable_bases` 保存继承起点。`pi_durable_current` 保存当前值及待重放位置。最早 replay floor 支持 Kafka 保留。修订表供需要历史的文档查找基线和增量。将全部文档改成“只留当前值”会影响按历史位置建立 Fork。 |
| 可查询的 Pi 记录 | `pi_durable_owned_records` 只有 11 列，却有 22 个索引，多个是从 `fields` 取值的表达式或部分索引。读者包括上下文组装、Conversation/Task 所有权、输入请求去重、等待中的 Tool 和历史导航。一次写只命中相应谓词，但更新共用 JSON 字段会影响创建 heap-only tuple 的机会。 |
| 共享不可变历史 | `pi_history_streams`、`pi_history_records`、`pi_history_bodies`、`pi_durable_write_refs`、`pi_history_nodes` 分别承担源身份、原生版本、正文去重、所有者引用和分叉范围树。联合唯一键、内容摘要和父/子引用索引同时供防冲突、删除和 GC。指向共享记录的 `(tenant_id,id)` 唯一索引在数据库目录中被 4 项外键引用。 |
| 网页历史与分叉操作 | `pi_history_blocks`、`pi_history_frames`、`pi_history_view_nodes`、`pi_history_views` 决定按逻辑会话读到的冻结范围。帧主键为 `(tenant_id,block_id,seq,ordinal)`。另有 Entry 定位、工具关联、正文引用和 GC 索引。Fork/prune 操作表记录管理操作幂等。此前 1 GiB 用例验证了源删除后的独立读取，首个 Fork 实测 765 ms。这是保留范围目录的具体收益。[原始 Fork 实验](single-path-shared-forks-20261030.md) |
| 子会话、设备与沙箱 | 子会话关系和监督请求用于当前子 Agent、Run 收尾及重新投递。设备绑定、执行目标、沙箱绑定及 Workspace/开发机对象由各自管理模块维护。普通会话结束也会关闭该 writer 的派发权限。资源生命周期、卷容量、外部执行效果与这次 PG 回放分别管理。 |
| 附件及财务 | 附件对象、Session 引用、上传保留和冻结头/记录的附件边用于 Fork、恢复与最后一个引用消失后的 GC。模型发起身份、结算事件和 writer 闭合保留不同证据。会话删除后仍可完成对账。计价、管理端资源报表和物理 Workspace 字节不属于同步文本投影。 |
| 后台和只读视图 | Outbox 的 8 个索引覆盖待投递、实体版本、未发布顺序和关闭确认。Worker 成员/退役在故障时参与恢复。普通 PG 视图把共享祖先、本地当前记录、根/子 Run 展开为 native 或页面读模型。详情已记录视图定义、触发器和外键，读路径的间接成本要结合查询计划判断。 |

**发现两组值得单独验证的重叠。** `runs_tenant_session_turn_id_unique` 的键是 `(tenant_id,session_id,turn_id,id)`。已有三列唯一键覆盖它的唯一性，目录中也没有外键使用这个四列索引。另一个 `runs_tenant_turn_unique` 的唯一性已由全局唯一 `turn_id` 覆盖。应在登记 Run、按租户查询和封口三条路径上单独比较后再删。相邻的三列唯一键正在被 `turn_control_requests` 引用，`(tenant_id,id)` 唯一键有 5 项外键使用。`runs_pending_inputs_session` 与 `runs_session_pending_input` 键顺序相同，后者的谓词额外要求 `pruned_at IS NULL`。目录中没有完全相同的索引定义。本次对线上索引的改动数为零。

## 按功能累加的实验

从固定版本的 Pi Harness 和本地模型取得真实的最终 Storage 批次，包含助手 Entry、输入 Submission、生成 Task、live 与 usage 两份文档变更。每个 Session 有自己不同的 4 KiB 正文，完整内存事实约 7 KiB。先在独立数据库建好前一稳定检查点，再从同一模板克隆每个实验库。每层使用 12 路并发、同一组 96 个独立 Session。每个 Session 的身份和输入在各层之间保持一致。按正序、反序及轮换顺序各测一轮。每次都等 PG 提交，验证最终正文、收据、网页帧、计量和终态行数。原生能力通过现有代码启用，任何删索引都只影响当轮克隆库。

| 单份最终回答所需的功能 | 每份客户端 SQL 次数 | 三轮吞吐，份/秒 | 吞吐中位数，份/秒 | 每份 WAL 区间中位数 |
|---|---:|---|---:|---:|
| 仅追加一份原始事实 | 3 | 1701.8 / 1745.7 / 1384.3 | 1701.8 | 7.7 KiB |
| 相同追加，增加唯一键 | 3 | 1600.2 / 1610.8 / 1681.2 | 1610.8 | 7.8 KiB |
| Pi 原生存储，保留约束与唯一索引 | 5 | 671.6 / 768.8 / 793.7 | 768.8 | 14.7 KiB |
| 再加共享历史查询索引 | 5 | 707.1 / 740.2 / 813.2 | 740.2 | 15.8 KiB |
| 再加其余原生查询索引，即正常索引布局 | 5 | 666.8 / 679.8 / 684.9 | 679.8 | 20.5 KiB |
| 再建网页可见帧 | 8 | 472.4 / 472.6 / 463.1 | 472.4 | 22.1 KiB |
| 再结算模型执行证据 | 10 | 404.4 / 407.7 / 408.4 | 407.7 | 24.3 KiB |
| 完整的已接受答案投影，含身份和覆盖 | 13 | 338.1 / 341.4 / 348.6 | 341.4 | 27.4 KiB |
| 再处理真正的 Run 终态消息 | 38 | 160.6 / 161.5 / 167.2 | 161.5 | 39.9 KiB |

这是每秒处理多少份**已生成的最终回答**。前两层把相同内存事实放入普通有 WAL 的表，使用一次 BEGIN、INSERT、COMMIT。最后一层多处理一条真正的终态事实。工作领取、模型请求、第一份 live 引用、前序提交、Kafka 拉取和浏览器均在这张表的计时外。独立 Kafka 对照和完整 Run 结果在下文。WAL 数字是服务实例在测量时段的增量，含少量其他后台流量。表行变更统计来自独立实验库。

在正式原生索引布局里，一份完整回答实际产生 **7 次插入与 7 次更新**。它插入一条收据、一条当前记录、两条历史引用、两条原生历史记录和一份正文，更新四条记录定位信息及三个当前值。正文物理上只存一份。开启网页帧会再写帧与展示描述。计量再写调用身份和结算证据。完整收尾还要改 Run、Session、租约与队列，写终态、转移、目录根、writer 闭合等。一次客户端 SQL 可以在一个 CTE 内改多张表。

将 7 张原生表上的 30 个非唯一二级索引仅在实验库里剔除，保留主键、唯一性及外键。相同写入的原生吞吐中位数从约 680 升到 769 份/秒。按已有索引写入，WAL 区间约 20.5 KiB/份。仅保留必需索引时约 14.7 KiB/份。第一轮 `pi_durable_owned_records` 更新了 384 行，完整索引布局下其中 0 行是 HOT 更新，对照里是 94 行。它说明索引维护有代价，但单删索引不能解释整条链路的数量级差距。

## 读性能要付出的代价

在独立连接的临时表中构造 10 万条混合记录，复制完整的 22 个索引。每次仅移除一个，再恢复，其他索引全部保留。下面是 PG 实际执行中位数，返回内容全部相同。

| 实际读选择条件 | 索引存在 | 移除 | 恢复 | 额外工作 |
|---|---:|---:|---:|---|
| 按 Conversation 与 request ID 确认一次用户输入 | 0.065 ms | 10.484 ms | 0.101 ms | 过滤 9,999 行，读取/命中 2,861 个本地缓冲块，原来为 4 个 |
| 取某原始 Tool 回复 Topic 的最早未完成位置 | 0.075 ms | 0.519 ms | 0.062 ms | 过滤 990 行，缓冲块从 12 个变成 1,001 个 |

另外，用同一个已结束的 Turn 分别走现有原生分页和冻结分页读法。两者逐项核对了页面位置、正文及翻页标志，每个方向交替读取 15 次正式样本。

| 数据与方向 | 每页可见条目 | 从原生日志分页 P50 | 从冻结目录分页 P50 |
|---|---:|---:|---:|
| 0 条额外历史，最新页 | 1 | 4.99 ms | 5.84 ms |
| 0 条额外历史，最早页 | 1 | 5.11 ms | 5.85 ms |
| 2,048 条额外历史，最新页 | 64 | 102.99 ms | 20.74 ms |
| 2,048 条额外历史，最早页 | 62 | 123.03 ms | 26.77 ms |

这些读数提供延迟冻结的对照。测试仍建立了真实冻结目录，并未把线上终态改成异步。首次 Fork 与源会话并发剪枝、删除时的可见性和保留责任要在变更策略时重新验收。

## 真实链路、恢复与处置

独立 Kafka 原始落库对照使用真实的 Worker producer、RF3、32 个分区、一个原生消费者和 12 个 PG 连接。每条是 6,953 字节的合成 Session 事实。每条在有唯一键的普通表中单独提交，预热 32 条后连续发送三波各 192 条。从开始发送到全部生产确认和 PG 提交完成，测得 **706.6、849.0、756.7 条/秒**。全部 608 条（含预热）逐条核对摘要，专用 Topic、消费组和数据库均已清理。这里复用服务中的普通单条 poll，按 192 条准备好的事实一起发送。完整 Run 试验则有工作领取、多个 Kafka 事实、PG 权威状态、页面投影和 SSE。

21 组相关回归共 283 项通过，另有 3 项离线计时归因测试、全工作区 TypeScript 检查和镜像依赖闭包检查通过。七项集群故障场景均通过。Projector 中途重启恢复了四条完整答案，用户停止的两条回答各保留了 192 字节可见文本，Worker 交接恢复了原 Run，丢回包场景观测到四次预期的物理写入，零重复。八次受控部署的 Worker 与 Projector 模板均恢复，原来的四个开发会话仍在，临时数据库、Topic 和诊断资源均已清理。

## 哪些改动值得继续

1. **优先验证冻结网页历史的时机。** 对普通回答，先验证能否直接复用原生 INSERT 返回的不可变引用、字节数和时间，省去同步读回再组装展示描述。对未 Fork 的普通会话，单独比较在终态事务中冻结目录和在首次需要独立历史时冻结。后一种可以减少热写，但会增加首次读取或 Fork 的延迟。必须在源删除/剪枝前固定所有外部引用，并证明分页顺序、工具配对、已中断正文和附件 GC 正确。
2. **针对索引族做取舍。** 优先在 Run 入队与转移基准中测试没有外键依赖的四列唯一键及两个重叠的排队谓词。原生混合表若成为持续瓶颈，可以在独立试验里拆开不可变 Entry 定位信息与经常变动的 Task/Submission 状态。一次只替换一个读者的数据来源，检查写放大和冷读 P95。此次测到明确收益的输入去重与回复保留索引应继续保有。
3. **底层重写有了可对照的基线。** 只存原始事实可以作为下限，但它单独不能提供 Pi 冷启动、精确幂等确认和源删除后独立 Fork。若另起原型，先加入有界 head、收据和连续性，再加入可恢复当前状态、完整消息、查询与页面投影、共享历史、附件、计量和生命周期。每一步使用相同输入、验证相同获准行为，记录写入吞吐、读 P95、存储/WAL、重放与断点恢复。Tool、图片、重度子 Agent 和长会话的生产容量需要各自的负载，不能由纯文本吞吐推算。
