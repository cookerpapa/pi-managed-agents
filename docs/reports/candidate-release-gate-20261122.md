# 新会话存储发布门槛

候选分支通过了普通根会话的发送、历史刷新、冷续聊、已确认输入的交接，以及 Stop 遇到 Worker 失联的浏览器验收。历史 Fork 的原生配置回读出现了可重复的数据缺口。正式服务继续使用现有存储。此次工作没有改表或修改持久化策略。

## 历史回答能读回，回答落盘时的工具配置不能唯一确定

在两个隔离的实验里，固定版 Pi Harness 都向模拟模型发出两个请求，两次请求都只提供 `bash`。第一个请求发出后，让模型等待，再通过原生配置接口热更新该 Conversation 的工具选择。实际 Worker 的目录更新也会异步更新 `pi.agent`。两个实验得到同样的回答 A 和 B。

| 时点 | 执行一 | 执行二 |
| --- | --- | --- |
| 模型开始生成 A | `bash` | `bash` |
| 模型等待时更新选择，随后 A 落盘 | `bash, read` | `bash, edit` |
| 恢复共同配置并生成 B | `bash` | `bash` |
| 从 A 的 Entry 10 原生 Fork，读取子 Conversation 的 `AgentDoc` | `bash, read` | `bash, edit` |

每条源轨迹有 13 个真实 Pi 提交。将两份提交分别交给候选原生 Projector、普通结算逻辑和 PG Fork 目录，固定相同的身份、提交位置、结算编号和测试时钟。比较分叉前夹具中全部 10 张表的每一行，结果完全相同。分叉结果可见的 3 个 Entry（含系统工具声明）与对应原生前缀逐项一致。送到模型的消息也逐项相同。该对照直接投影原生提交，使用真实 PG 和 Pi，控制行与位置由夹具提供，冷读不使用 Kafka。它检验的是保留信息能否区分两段合法历史，没有通过等待七天来模拟故障。[对照结果](fork-document-evidence-20261122.json)

工具声明描述的是那次请求里提供给模型的工具。原生 `pi.agent` 的 `fork: asOf` 描述的是选中 Entry 提交时的配置。服务版 Fork 按分叉位置导入这类文档；候选 Fork 目前保留消息范围与结算头，普通结算还会清掉活跃交接快照。超过 Session Kafka 的保留期后，即使把查询改成从末尾倒读，也无法从相同的持久数据得出两个不同的答案。[服务版导入逻辑](../../packages/pi-session-postgres/src/durable/history-import.ts) · [候选 Fork 决策](../adr/0341-minimal-storage-fork-study.md)

保持现有原生语义的一种办法是在被选中的可回溯文档发生有效变更时，随已有事务保留版本或能长期解析的不可变引用，用原生提交位置定位。只需当前值的文档和流式片段可继续采用各自的保留策略。历史配置的读取和新 Run 当前允许执行的工具仍分别受原有规则约束。另一种产品选择是明确只继承可见对话，分叉后按当前配置重新初始化。后者会改变现有原生 Fork 的可观察行为。本次只提供复现和取舍，保留策略待定。

复现命令如下。退出码 2 表示两种原生结果与相同的 PG 保留数据已同时复现。

```sh
node scripts/run-with-test-postgres.mjs -- node --import tsx \
  scripts/experiments/minimal-session-storage/verify-fork-document-evidence.mjs
```

## 已验证的执行边界

网页确认一个 follow-up 和一个 steer 后，先杀掉 Worker A，再按 Stop。实际 PG 租约过期、Kafka 封口和重新领取后，B 在恢复模型循环前处理这条 Stop。原操作仍运行时，有一次发往原 Guest 的取消。原回包已经进入原 Topic 时，取消次数为零。两个场景 B 的模型请求都是零，工具各执行一次，原来的两条输入均回到草稿，明确重新发送前没有启动下一 Run。模型响应可控，浏览器、Worker 进程、Pi、Kafka、PG 和 Cube 参与实际链路。[浏览器实测](stopped-root-inputs-20261122.md#stop-after-losing-the-worker)

## 同口径吞吐与降速归因

沿用已有的单 Projector、32 个 Kafka 分区、12 个 PG 连接、1,024 个 Run、每 Run 20 次顺序工具调用、1 KiB 结果、100 ms 模拟设备回执。每档验证 191,488 条 Kafka 记录、44,032 条完整历史行、20,480 对工具和所有终态位点。完整历史行含 1,024 条用户输入、1,024 条系统消息、21,504 条助手消息、20,480 条工具结果。吞吐分母含排空时间。模型与设备受控，Run 行和热路由预先准备，此处测量既有批处理 Projector 负载。完整服务组合的吞吐和终态 P95 仍需单独验收。[既有负载定义](tool-loop-capacity-20261121.md#每天百万-run每个-run-20-次工具调用) · [各档计数与时间](candidate-capacity-20261122.json)

| 稳态目标 | 以前的结果，Run/s | 本次候选，Run/s | 同机旧程序复跑，Run/s |
| --- | ---: | ---: | ---: |
| 日均 1 倍，两轮 | 11.5 / 11.5 | 11.5 / 11.5 | 10.2 / 11.3 |
| 1.5 倍 | 17.2 | 12.5 | 13.8 |
| 2 倍 | 22.8 | 20.9 | 12.1 |

1.5 倍候选标准轮实发 3,238 条/秒，积压峰值 54,650 条，停发后还需 22.91 秒。该轮每笔事务持有 PG 连接的平均时间从旧报告的 4.42 ms 升至 7.24 ms，Kafka 派发位点确认从 11.75 升至 18.04 ms，设备回执从 100.97 升至 103.15 ms。PG 事务数由 108,750 变为 108,239。旧代码复跑时，Worker、Projector 和唤醒组件的打包 SHA-256 与旧报告逐个相等。旧程序的 2 倍档实际只送入约 2,269 条/秒，而候选标准轮送入约 4,321 条/秒。两者都有明显波动，其中包含供给不足和消费积压两种情形。

在候选上另外捕获一次工具流，按 1.5 倍、3 倍、1.5 倍、1.5 倍顺序依次重放。三个 1.5 倍样本实际送入 3,236–3,243 条/秒，同一份捕获分别得到 **12.7、17.2、13.6 Run/s**，积压峰值分别是 **65,228、284、40,937**。第二次 1.5 倍样本紧跟 3 倍过载样本，仍在停发后 0.47 秒追平。全部样本最终积压为零。

### 同一份程序为何出现两种速度

在旧代码复跑和候选重复组，采集 Windows 的 `Win32_PerfFormattedData_Counters_ProcessorInformation(_Total).PercentProcessorPerformance`。该计数器和 CPU 利用率分开记录。候选诊断同时在 WSL 固定逻辑 CPU 上运行固定工作量的计算，记录线程实际 CPU 时间和墙钟时间。计算使用同一优化编译产物、同一 64 位种子、5,000,000 轮相依的异或移位，分别绑定 CPU 8 和 24，约每 3 秒采样一次。Linux 块设备刷新和 PG 等待、检查点也独立采样。基准没有改变宿主机电源设置。

下表只取 1.5 倍档的生产窗口。每 10 个 Projector 采样点形成一个约 5 秒区间，要求实际进 Kafka 的速率在目标的 ±10% 内；同区间宿主机采样全部 ≤90% 或全部 ≥130% 时分别列入低档或高档。中间档也保留在 JSON。表内是区间中位数，低速的第一轮标准数据没有同步宿主机采样，归因来自后续复现。

| 程序与状态 | 区间数 | 实际输入 / 处理（Kafka 记录/秒） | 宿主机性能读数 | WSL 同一计算的 CPU 时间 | 块设备平均 flush 时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 旧程序，低 | 9 | 3,251 / 2,142 | 68% | 未在该窗口采集 | 2.75 ms |
| 旧程序，高 | 2 | 3,247 / 4,095 | 167% | 未在该窗口采集 | 2.69 ms |
| 候选，低 | 16 | 3,247 / 2,112 | 72% | 19.07 ms | 2.77 ms |
| 候选，高 | 16 | 3,248 / 3,247 | 151% | 7.81 ms | 2.62 ms |

旧程序高档时还在消化已经积累的记录，所以处理速率可以超过输入；候选高档时能跟上这档供给。独立计算在低档消耗约 2.4 倍 CPU 时间，相同程序和输入也会明显降速。复现确认这台 Windows/WSL 主机的有效计算速度变化是长尾的重要因素。PG 和派发确认耗时一起上升，不能仅凭它们变慢判定新增 SQL 是原因。第一次未采样的慢窗口无法追溯到具体宿主机事件，温控、电源策略及其他宿主机因素之间仍无法区分。本次数据不足以承诺固定的峰值容量，也不能排除较小的代码开销。

首次基准启动时，旧操作镜像缺少 `nativeNavigation` 导出，Projector 尚未开始测量便退出。已让实验包携带匹配版本的纯函数，再用新夹具重跑。该次启动没有计作零吞吐样本。三个完成的基准组均验证了临时 PG、Kafka Topic/组和夹具资源的清理。

## 放行状态

已完成的是上面列出的功能验收、历史状态对照和基准归因。保存哪些原生文档版本仍需决定。之后还需用选定策略覆盖服务入口的 Fork/裁剪、后续 Run 及多代交接，并重新测量完整服务组合。浏览器功能夹具和批处理压力夹具目前是两种组合，单个夹具通过不能替另一种组合放行。

此次 RF3/PG 传输回归通过 25 项。服务版历史引用、会话树和网页输入取回回归通过 36 项，其中包含原有历史分叉的 as-of 对照。候选文档信息缺口在两次独立临时 PG 实验中复现，专门诊断返回 2。已推送的执行改动仅用于验收 Stop 时序，正式存储和线上部署都未切换。
