# 同步合并 Session 投影的压测

保留 PostgreSQL 的同步提交，把 Projector 已经收到的同分区记录合成一笔事务。两次独立实验中，按每秒 520 个短 Run 投入的四轮完整链路都接住了全部请求，实际完成 515.5–517.3 Run/秒。带相同恢复点的逐条同步提交完成 366.9–375.6 Run/秒。固定速度回放的六轮高压实验中仍有三轮出现秒级长尾。当前结论限于性能原型。 [逐轮数据](synchronous-ready-prefix-20261120.json)

## 写入和恢复

例如同一分区已经有 A 的最终回答和 B 的首条完整消息。Projector 可以在同一个 PG 事务中按顺序保存二者和分区的下一读取位置。只有 A 到达时立即写 A。每批最多 16 条，按预取内存估算最多 256 KiB，单条已允许的大记录可以单独处理。不同分区各自推进。普通文本片段只更新内存，正在运行的 Run 保留重建所需的首个 Kafka 位置。PG 中的分区位置只推进到本批最后一项需要持久化的变更。

遇到工具意图、取消、需要确认的输入或 Run 完成时结束当前批。先等 PG 成功，再更新运行时视图、返回确认。工具还需要获得原来的 Kafka 消费组派发许可。停在 PG 成功和获得许可之间，新 Projector 可以接续派发。停在获得许可和发出命令之间，恢复会保留结果未知，避免重跑可能已有副作用的命令。事务回滚时，消息、Inbox 和恢复位置一起回滚。 [设计决定](../adr/0339-ready-prefix-projection-study.md) · [故障用例](../../scripts/experiments/minimal-session-storage/ready-projection.integration.spec.mjs)

## 负载与结果

两套独立的开发节点实验各自录制一份真实 Pi 提交序列，分别含 6,240 和 4,160 个 Run。每个短 Run 使用立即响应的模拟模型、约 4 KiB 的完整回答、7 条 Kafka 记录和 4 次稳定状态变更。32 个 Kafka 分区、三副本、两路 Worker 进程和 12 个 Projector 数据库连接。全部投影连接使用 PostgreSQL 17.6、`synchronous_commit=on`、`fsync=on`、`commit_delay=0`。没有调用付费模型。

下表给出完整链路重复测量的范围，延迟从压测器实际开始提交用户输入起算，到 PG 确认 Run 完成为止。原写法分四笔保存 Inbox 初始状态、首条用户消息、完整回答和 Run 完成。其余两组都包含相同的 PG 分区恢复点和 Run 写入身份检查。

520/s 每轮持续投入 20 秒，260/s 每轮持续 40 秒。两组按不同次序运行，以观察同一台开发机上的重复性。

完整链路每轮在高档分别计划发送 10,400 个 Run。压测器最多允许 384 个在途请求，达到上限会跳过新的计划到达。表中的差额都是压测器跳过的投入。已被接收的 Run 全部完成，所有完整链路在测量结束时 Kafka 积压归零。520/s 的同步合批峰值积压为 225–470 条 Kafka 记录，停止发新请求后 107–177 ms 排空。四轮累计 166,400 次逻辑写入共用了 99,467 笔 PG 事务，省下 40.2%。在 10/s 下只省下 11/800 笔。每笔事务仍包含原来的行修改和约束验证，事务数与物理 WAL 刷盘次数分别统计。 [测量口径和数据](synchronous-ready-prefix-20261120.json)

## 长尾的出处

在完整链路 260/s 的两轮慢样本里，一个 Run 等待各次 Kafka 写入确认的累计时间 P95 达到 801–831 ms，结束消息从生成到 Projector 开始处理的 P95 达到 637–725 ms。同档另两轮分别约为 52 ms 和 19–20 ms。慢样本的时间花在多个环节，这两组分位数存在重叠。 [完整链路分段数据](synchronous-ready-prefix-20261120.json)

隔离投影的回放始终把录制的数据全部送出。24 轮共回放 133,120 个 Run、532,480 次稳定状态变更。每轮按分区核对记录顺序，并对最终历史头、完整消息和 Inbox 的内容做散列比对，全部与对应录制一致。

在 260/s，合批的四轮回放 P95 为 44–167 ms。在 520/s，合批的六轮中，三轮 P95 为 48–64 ms，另三轮约为 3.5、6.3 和 14.5 秒。三个快速样本中，每笔事务从取到连接到归还平均用 7.5–7.9 ms。另两轮的发送端仍按时提供数据，发出迟到 P95 小于 2 ms，但占用连接变为约 20–21 ms，等待取连接平均约 19–21 ms。同分区后续记录因此排在前一笔事务后。最慢一轮的发送端本身已经迟到约 14.46 秒，该轮的端到端延迟不能全部归因于 PG。独立 CPU 校准也有波动，未能进一步把这两轮的连接占用时间唯一归因于 PG 执行、刷盘或宿主机调度。回放积压包含相对计划到达时间的发送落后，完整链路的 Kafka 积压单独取自分区末尾与已处理位置之差。 [逐轮观测](synchronous-ready-prefix-20261120.json)

## 验收范围

原型覆盖首条输入、follow-up、steer、已排队输入的编辑与撤回、回答已提交但 Run 尚未结束，以及有序回放后内容一致。独立故障用例在真实 PG、Kafka 上检验事务提交前断开、提交回执丢失、旧写入身份和工具派发许可两侧的进程中断。工具派发使用可计数的观察动作。吞吐负载没有真实沙箱、外部模型等待、HTTP/SSE、计费或长会话压缩。移入服务版前仍需测量混合工具负载和长会话恢复。异步投影保留为后续备选。 [复现步骤](../../scripts/experiments/minimal-session-storage/README.md)

最终回归通过 188 项事件日志与运行时单元测试、20 项性能原型辅助测试和 16 项真实传输集成测试。两条投影路径均通过冒烟验收。所有实验 Topic、消费组、临时数据库和测试 Pod 均已清理。服务实例复查为 `synchronous_commit=on`、`fsync=on`、`commit_delay=0`。
