# 共享 Fork 对最小投影的成本

对照对象是性能分支的合批、事务级全异步历史投影。Fork 自身走同步 PG 事务。两条路径使用同一份录制形状、相同的 Pi 消息、相同的投影函数调用次数规则、一个 Projector、32 个分区、三副本 Kafka 和 12 个 Projector PG 连接。所有负载在同一开发节点上串行执行。 [实验决定](../adr/0341-minimal-storage-fork-study.md) · [复现命令](../../scripts/experiments/minimal-session-storage/README.md)

## 候选布局

正文继续在 `messages`。把它的外键从调度 Run 改为独立的历史流，Run 的新入队须引用活跃会话。在已有的 Run 正常完成 SQL 调用中写入一个小的完成标记，以便源 Run 删除后还能验证历史锚点。带覆盖索引的候选为每条消息额外维护一项索引。普通追加无需查询分叉数或更新任何分叉。每批照常进行一次 Projector 到 PG 的往返，Kafka 消息体没有新增字段。

创建 Fork 时锁定幂等请求、校验已投影的已完成助手回答、固定所选 Conversation 的 Entry ID 范围和当时的提交上界，使用已有的 `HistoryDirectory` 与 `PostgresHistoryDirectory` 保存不可变目录，登记新会话的共享根、独立本地流和幂等回执。PG 计算范围中小型描述信息的摘要，锚点检查读取所选回答。同一范围里其他记录的正文在 Fork 时不复制。普通追加继续校验原 Entry 及其范围身份。 [实验存储实现](../../scripts/experiments/minimal-session-storage/fork-storage.mjs)

## Projector

三组主对照各使用 256 个源会话，每轮实际投影 51,200 条 4 KiB 调用／结果记录，还要处理相同的输入和收尾。逐 Run 将最终 PG 内容摘要与发压端对照，并检查消息顺序、完成状态、最终积压和每笔事务的实际确认模式。下表中积压组先把全部输入写入 Kafka，再同时放行各分区。吞吐降幅逐组对各自的原布局计算。

| 布局及同时发生的活动 | 投入 2,315 条/秒时的消息 P95 | 已积压时的完整消息/秒 | 相对同轮原布局的吞吐降幅 |
|---|---:|---:|---:|
| 原布局 | 23–26 ms | 7,259–7,307 | 基线 |
| 开启 Fork，计时时没有用户创建 Fork | 25–28 ms | 6,892–7,198 | 0.8%–5.6% |
| 每个源已有 4 个分叉，共 1,024 个 | 24–25 ms | 7,033–7,282 | 0.3%–3.1% |
| 已有 1,024 个，还以目标 20 次/秒创建 Fork | 23–52 ms | 6,384–7,198 | 0.9%–12.6% |

持续创建使用独立的冷路径客户端，交替从正在追加消息的源会话所继承的已完成锚点，以及独立 1,024 条历史的末尾分叉。前一类 Fork 选择先前的稳定内容。到达时间过期的冷请求单独计数，实际完成数和该路径的 P95 均保留在数据中。所有三组在 2,315 条/秒档都完整处理了输入。由这些样本看，保存已有分叉没有引入按分叉数放大的普通追加负担。持续做 Fork 会消耗同一个 PG 实例的资源。

前两套独立夹具在 6,000 条/秒档，原布局达到 5,886–5,902 条/秒，开启 Fork 达到 5,871–5,899，持续创建时为 5,780–5,888。第三套的原布局出现异常样本，实际为 840 条/秒，投递迟到 P95 4.09 秒，完整消息 P95 53.63 秒，投影事务取到连接后平均占用 183 ms。同期该临时 PG 的日志包含一次 checkpoint 文件同步 48.0 秒。这些观测不能把所有延迟唯一归因于磁盘或某条 SQL。该组原布局异常值完整保留，不用它推算 Fork 带来了正收益。第三套开启 Fork 的常规样本为 5,843 条/秒，持续创建为 5,648。 [全部对照数据](minimal-projection-fork-20261120.json)

## Fork 事务和读回

每个样本用新的幂等键创建新的目标会话，计时从客户端发起到 PG 返回已提交。随后单独测首次读最新一页（最多 30 条），以及从没有新输出的目标再次 Fork。每种大小、位置先预热一次，短历史测 50 次，32,768 条历史测 25 次。这里的“首次读”指目标会话新建后的第一读，操作系统和 PG 页缓存已预热。

| 源消息数 × 每条正文 | 从末尾创建 Fork 的 P95（三套有覆盖索引的实验） |
|---|---:|
| 16 × 4 KiB | 9–10 ms |
| 200 × 4 KiB | 9–12 ms |
| 4,096 × 4 KiB | 19–21 ms |
| 32,768 × 768 B（24 MiB） | 82–87 ms |
| 32,768 × 32 KiB（1 GiB） | 84–86 ms |

1 GiB 从中间分叉 P95 为 46–48 ms，从末尾分叉后首次读取最新 30 条的 P95 为 18–21 ms。只继承同一个完整根、没有新增本地内容时再分叉，P95 约 8–9 ms。固定条数时把正文扩大约 43 倍，对创建端耗时影响很小。扩大选中范围的记录数会增加描述信息扫描和哈希成本。所有组均验证 Fork 前后物理消息行数不变。

每代先真实追加并收尾一条本地消息，再分叉时会出现更多范围和目录节点。128 代对照中，有覆盖索引的样本 P95 为 91 ms、最后一代 103 ms。两组独立无覆盖索引样本 P95 分别为 38 和 16 ms，最后一代分别为 14 和 12 ms。它们是在不同时间分别测得，不用这些数字推断索引对嵌套 Fork 的因果影响。1 GiB 源末尾使用 8 个客户端，共提交 64 个独立 Fork，有索引时达到 79 次/秒、事务 P95 为 120 ms，无额外索引时为 75 次/秒和 122 ms。

## 额外索引是否值得

另两套夹具交错比较原布局、带覆盖索引、只使用原有主键及索引的 Fork 布局。最后一组在积压排空期间的 PG 实例 WAL 增量，按每条计数消息平均，原布局为 6,492–6,511 字节，带索引为 6,869–6,950 字节，省掉覆盖索引为 6,575–6,635 字节。额外索引减少了一些读操作，也带来了可测的写入成本。无额外索引组的积压吞吐仍有波动，去掉索引不能保证单次测试的吞吐一定更高。

对单主线的 1 GiB 历史，无额外索引时从末尾 Fork 的 P95 为 84–86 ms。无索引中点样本有一组 P95 达 91 ms、最慢 738 ms，另一组中点 P95 为 51 ms。为单独检查多 Lane，另造同一份 32,768 条、均匀分布在 32 个 Conversation 的数据，只选其中 1,024 条，交替建立／移除索引，各两轮、每轮 35 次。带索引 P95 为 11–12 ms，无额外索引为 19–20 ms。当前以普通追加为主的原型可以先复用原索引，将稀疏子会话的读取代价纳入后续生产负载评估。

## 正确性和适用范围

验证了同一请求并发重试、不同锚点复用请求 ID 被拒绝、排除迟到的低编号消息及同 Session 的旁路、源 Run 运行时从先前结算点 Fork、源裁剪后独立追加、删除源和中间分叉、旧 Run 追加被拒绝，以及最后一个引用消失后的正文和目录回收。通过实际 PG 行锁制造了 Fork 与删除竞争。独立目标在源删除后还用固定 Pi Harness 重新打开了文本历史，模拟模型实际收到了正确的继承前缀和新用户输入。

这是原型的**消息历史存储事务**。尚未包含正式 HTTP/API、完整 Pi 文档与压缩状态导入、全部子 Agent 祖先映射、产品展示快照或 S3 图片引用。冷路径实验使用租户级共享／排他锁协调 Fork、删除和回收，未测大规模并发删除或后台 GC 成本。正式版旧接口的端到端数据单独记录。 [服务版原有测量](single-path-shared-forks-20261030.md)

五套正式夹具共 60 轮，校验了 3,072,000 条计数消息以及每个 Run 的入队输入与最终回答。25 项原型辅助测试、4 项已有目录测试和原有消息投影冒烟均通过。实验 Topic、消费组、PG 数据库及 K3s 临时资源已清理。
