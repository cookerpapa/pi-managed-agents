# 每个 Run 产生 200 条完整消息时的投影能力

每天 1,000,000 个 Run，每个 Run 产生 200 条完整消息，对应每天 2 亿条，平均每秒 2,314.81 条。若每个 Run 的 200 次工具调用各自形成一条助手消息和一条结果消息，则为平均每秒 4,629.63 条。批量工具调用可能改变助手消息条数。 [上一轮短 Run 测量](moving-projection-recovery-20261120.md)

## 计数和测试方法

在性能分支以一份固定的已完成历史驱动实际 Kafka、Projector 和 PG。每个 Run 有 100 对调用及结果，调用和结果各含 4,096 个 ASCII 字节的独立伪随机 Base64 载荷。一条完整消息占一条 Kafka 记录，Projector 最多合并同分区已经到达的 16 条。每个 Run 还要处理 Inbox 初始化、首条输入、最终回答及 Run 完成。它们的时间都计入分母，200 条中间消息是分子。入队/领取行预先准备，数据中没有可派发命令，也没有模型推理、沙箱执行或回包等待。

PG 17.6 默认同步，`fsync=on`。同步组每笔投影事务等同步确认。异步组对这份可重放历史及正常收尾使用事务局部异步确认，实际提交模式逐笔核对。使用开发 K3s 上原有的三副本 Kafka、32 个分区、一个原型 Projector 和 12 个 PG 连接，数据库与 Topic 单独创建。每轮逐 Run 校验顺序、消息条数和正文摘要，一并核对 Run 的正常终态和最终积压。

按固定速率发送的轮次记录计划发送到投影确认的 P95、发送迟到、实际 Kafka 积压采样，以及停止新投入后排空所用时间。另做已积压对照，先把所有数据发进 Kafka 并等待生产确认，才同时放开各分区 Projector 处理，计时到最后一条完成确认。这组给出当前配置消化已有积压的速度。 [复现命令](../../scripts/experiments/minimal-session-storage/README.md)

## PG 恢复时的读取条件

PG 中来自 Kafka 并可按原身份、原顺序重建的投影可以异步提交。初次接受用户请求等由 PG 独立负责的写入仍同步。故障或切换后先撤销上个恢复周期的就绪状态，对每个分区捕获一次 `read_committed` 可见末尾，以“下一条位置”表示。再从 PG 已恢复的稳定状态和受保护的未完成后续记录重新消费。当 PG 逻辑提交和对应内存重建已覆盖这个固定目标，就能放行依赖它的业务查询和决策。若目标是 600，下一位置到 600 即可；随后新来的 601 等记录按正常流式路径处理。

单会话操作等自己的分区，跨分区操作等涉及的分区。第一版也可以对外统一等待所有分区。恢复程序需要能读写 PG。领取、恢复和释放资源等也要受同一恢复周期约束，避免根据暂时回退的状态采取行动。Kafka 缺少必需区间时阻止该分区开放，已获得派发许可的外部命令继续受独立的消费组边界保护。此前故障试验证实过异步确认的 `completed` 在重启后短暂变回 `running`，追平后恢复正常。 [PG 故障复验](moving-projection-faults-20261120.json) · [现有分区等待实现](../../packages/event-log/src/kafka-log-consumer.ts)

## 按固定速率投递

第一套夹具使用 256 个 Run，每一轮有 51,200 条计数消息。每档各测两次，交换先后顺序。把全部消息发出后，所有已提交记录都追平，PG 逐会话内容摘要与源端一致。

| 每秒计划消息数 | 投影提交 | 实际完整消息/秒（含排空） | 完整消息 P95 | 停止新投入后的排空时间 |
|---:|---|---:|---:|---:|
| 2,315 | 同步 | 2,309–2,310 | 67–109 ms | 45–58 ms |
| 2,315 | 异步 | 2,310–2,314 | 24–30 ms | 11–44 ms |
| 4,630 | 同步 | 4,569–4,573 | 164–176 ms | 139–147 ms |
| 4,630 | 异步 | 4,612–4,618 | 76–81 ms | 30–43 ms |

如果 2 亿条/天的每一条都有 4 KiB 正文，仅正文约为 819 GB/天（十进制）。实际消息大小、流量峰值、Kafka 保留天数和 PG 历史增长都影响部署规划。短时投影速度不能代替全天容量测量。

第二套夹具使用 768 个 Run，每轮 153,600 条计数消息。以 2,315 条/秒持续投入约 66 秒，同步和异步的 P95 分别为 76 和 31 ms，停止新投入后分别用 99 和 10 ms 排空。继续提高投递速率得到下列结果。每档每种模式各测一次，以下数据用于定位开始积压的区间。

| 每秒计划消息数 | 投影提交 | 实际完整消息/秒（含排空） | 完整消息 P95 | 停止新投入后的排空时间 |
|---:|---|---:|---:|---:|
| 6,000 | 同步 | 5,001 | 7.48 s | 5.12 s |
| 6,000 | 异步 | 5,941 | 370 ms | 253 ms |
| 8,000 | 同步 | 5,311 | 14.82 s | 9.72 s |
| 8,000 | 异步 | 5,426 | 11.73 s | 9.11 s |

8,000/s 时两组发送方的投递迟到 P95 均低于 2 ms，Kafka 分区末尾与投影进度间的采样峰值分别达到 56,926 和 50,104 条记录。两组最终都追平，实时输入时已经积压数秒。生产和消费同时争用本机资源时，速度可以低于下表的预装载排空速度。实测没有把这段耗时唯一归因于 WAL 设备或某一条 SQL。两套正式夹具共 20 轮，逐 Run 校验了 1,843,200 条计数消息及各轮额外的首条输入、最终回答。

## 已积压时的处理速度

三次同期对照都先等待 Kafka 确认全部输入，随后放开同分区有序投影，计时到 PG 逻辑提交完成。异步组的确认允许 WAL 后续刷盘，`fsync` 在两组中始终开启。

| 每轮计数消息 | 同步投影（条/秒） | 异步投影（条/秒） |
|---:|---:|---:|
| 51,200，第一次 | 5,934 | 7,020 |
| 51,200，交换顺序再测 | 6,180 | 7,641 |
| 153,600，新夹具和独立数据 | 5,361 | 7,139 |

这是一个 Projector 通过当前原型的行结构、索引、恢复点和合批策略写 PG 的速度。单独 PG 顺序写入、纯 Kafka 读吞吐以及真实工具执行的上限需要分别测量。压测用的两套原始数据只在各自的临时环境里使用，公开报告只含聚合计数和时延。 [逐轮数据](complete-message-capacity-20261120.json)
