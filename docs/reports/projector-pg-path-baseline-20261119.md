# 同一批消息直写 PG 和经过 Projector 的差异

在这台 WSL/K3s 的隔离原型上，**12 条长连接可以跟上每秒 260 个新 Run 对应的 1,040 次投影写入**。开启服务端计时的四次直写实验全部跟上。相同数据经过真实 Kafka 和 Projector 时，四轮中两轮跟上，两轮积压。到 520 Run/秒时，两条路径都出现持续积压。测试只覆盖 4 KiB 纯文本回答和这一套原型表结构。[逐轮数据](projector-pg-path-baseline-20261119.json)

## 同一份工作量

从真实 Pi Harness 录制两组独立的新会话，分别有 6,240 和 4,160 个 Run，每个 Run 包含 7 条 Kafka 记录。Projector 在真正写 PG 时录下 SQL 和绑定参数，每个 Run 恰好创建一次 Inbox、写两条消息、更新一次终态。模型使用本地确定性回复。

每组录制完成后，停下领取，在临时库中恢复完全相同的已领取 Run 和写入身份。两条路径使用同一个 Pod、同一个 Node 进程和预热好的 12 条连接，对同一个 PG 实例执行真实自动提交，`fsync` 和 `synchronous_commit` 都开启。按相同的目标速率喂入记录，保留每个分区录制时的顺序。

- **直写**从 32 条分区队列取出每条记录原本会触发的 SQL，使用录下的参数执行，保留每次提交、身份检查和写入结果校验。
- **经过 Projector** 由另一个 Pod 按相同节奏将原始消息发到三副本 Kafka。批量读取器、解码和投影处理函数走原型实际代码。每次写入都核对 SQL 正文和绑定参数。定点计时组在抽样连接的 SQL 前面加短注释，便于把 PG 状态和那一次写入配对。

22 次回放共完成 **124,800 个 Run、499,200 次 PG 写入**。每轮逐分区核对处理顺序，并对正式消息、Inbox、Run 的完成状态和历史头做摘要比对。所有结果与录制时一致。运行时生成的时间戳排除在内容摘要外。所有回放都处理完了全部输入，过载表现为积压。正式服务的表、配置和部署没有用于这些实验写入。

两组正式实验总计配对 54,952 次客户端与服务端调用，其中 1,183 次取得了可核对的 idle 边界。早期读 cgroup 的采样进程已清理，采样器改为随输入流关闭退出。一次定点驱动在负载开始前因初始化错误退出，未纳入数据。修正后的定点组重新完整运行，常规原型回归、专项冒烟和环境清理均通过。

## 速率和积压

下表汇总开启服务端计时的回放。每轮先完成录制和预热，再开始计时。P95 从该 Run 第一条原生日志应当到达的时间，算到它的完成记录写入 PG。这里不包含用户登记和模型响应时间。实际吞吐计入最后排空队列的时间。

| 目标 Run/秒 | 每条路径轮数 | 直写实际 Run/秒 | 直写 P95 | 经过 Projector 实际 Run/秒 | 经过 Projector P95 |
|---:|---:|---:|---:|---:|---:|
| 116 | 2 | 115.9 | 104 ms | 115.9–116.0 | 123–126 ms |
| 260 | 4 | 259.1–259.5 | 44–84 ms | 230.2–259.6 | 63–4,135 ms |
| 390 | 2 | 366.2–388.5 | 249–1,020 ms | 388.6–388.9 | 112–147 ms |
| 520 | 2 | 393.0–399.3 | 2,684–3,701 ms | 262.7–300.9 | 6,979–13,716 ms |

260 的两次 Projector 慢轮分别积下最多 5,802 和 3,264 条到期未处理的记录，停止投喂后分别用 3.11 和 1.42 秒排空。在较快窗口两条路径都能迅速排空。520 的两次直写也要额外 2.58–3.63 秒，经过 Projector 则是 5.82–11.76 秒。各轮串行，同一台主机在不同窗口的可用处理速度有可观波动，390 的短窗口不足以确定持续容量。额外两轮关闭抽样后端的协议日志和 I/O 计时，260 下直写与 Projector 的 P95 分别为 66 和 126 ms。

## 同一轮从跟得上到积压

下表是目标 260 的第二组 Projector 慢轮。每秒需要完成 1,040 次写入，均匀分摊给 12 条连接时，每次平均占用预算约 **11.54 ms**。在第 9 秒，占用时间超过这个预算，32 个分区中有 20 个在等连接。积压为按计划应到的记录数减去已经处理完的记录数，包含已进入 Projector 的工作。

| 时刻 | 到期未完成记录 | 等 PG 连接的处理函数 | 当秒平均占用连接 | 独立固定 CPU 计算 |
|---|---:|---:|---:|---:|
| 第 1 秒采样 | 25 | 0 | 5.96 ms | 2.37 ms |
| 第 9 秒采样 | 1,883 | 20 | 15.06 ms | 9.32 ms |
| 第 15 秒峰值 | 3,264 | 20 | 12.91 ms | 7.73 ms |

这一轮的平均占用是 11.47 ms，包含负载较轻和排空的时段。整轮平均接近理论预算时，数秒内的波动就足以积成秒级尾延迟。

## 一次实际写入在哪里耗时

在一个预热后端只打开耗时日志。两个标记之间按 PID 和顺序将每条扩展查询的 Parse、Bind、Execute 与客户端调用一一配对，并校验时间窗。PG 在处理 Sync 时完成隐式事务，随后将后端标为 idle，再发 ReadyForQuery。定点实验用只读连接约每 50 ms 观察一次 PG 状态。只有看到同一条带标识查询的 idle 时间戳才进一步切分。业务写入不需要额外的数据库往返。[PG 17 查询协议](https://www.postgresql.org/docs/17/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY) · [PG 17.6 服务端实现](https://github.com/postgres/postgres/blob/REL_17_6/src/backend/tcop/postgres.c#L4377) · [状态时间戳和等待事件](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)

同一组 4,160 个 Run、同样目标 260 Run/秒的两轮 Projector 回放：

| 观测 | 较快轮 | 较慢轮 |
|---|---:|---:|
| 投影 P95 | 63 ms | 2,609 ms |
| 拿到至归还连接，所有写入平均 | 6.08 ms | 11.47 ms |
| 完整配对的服务端查询数 | 1,396 | 1,404 |
| 这些查询的服务端 Parse + Bind + Execute，平均 | 0.82 ms | 2.04 ms |
| 还能核对 idle 边界的查询数 | 95 | 84 |
| 这些查询从 Execute 日志到服务端变为 idle，平均 | 5.23 ms | 7.07 ms |
| 这些查询从服务端变为 idle 到 Node 取到返回，平均 | 0.49 ms | 3.03 ms |
| Projector 内另一条长连接上 `SELECT 1` 的中位耗时 | 0.35 ms | 3.66 ms |
| 独立驱动进程相同的 SHA-256 计算，中位耗时 | 2.27 ms | 8.09 ms |

服务端提交收尾和返回应用两段都变慢了。Execute 到 idle 包括隐式提交期间的等待和服务端调度。能观察到 idle 的样本受轮询间隔影响，不能据此给全部查询分摊比例。日志时间戳精度为毫秒。idle 到 Node 仍包含服务端发包、网络和客户端调度。

这两轮的 PG 活跃后端采样中，约 **85% 和 70%** 落在 WAL 写入轻量锁或 WAL 同步等待上。这个比例针对后端状态采样，不能当作 Run 总耗时中的磁盘占比。WAL 等待在快轮同样常见。慢轮的独立计算和只读探测也同时变慢，PG 与 Projector 的容器 CPU 配额限流计数在这两轮均没有增长。测量支持共同的主机负载会放大尾延迟，尚不能把变化单独归给某条 SQL、磁盘、网络或 Windows 调度。WAL 计数为集群级差值，耗时开关只改实验连接，窗口也可能含后台写入。

## 加回 Worker 和用户入口

用相同 12 条连接恢复真实 PG 登记、Worker 领取、Pi 执行、Kafka 发布和 Projector 收尾。在连续两次每秒 260 个请求、每次 40 秒的试验中，一轮 10,400 个全部完成，用户登记至 PG 终态的 P95 为 **91 ms**。另一轮完成 **9,988 / 10,400**，P95 为 **2,187 ms**，峰值有 2,231 个 Kafka offset 尚待处理。余下 412 个请求是压测器达到 384 个在途上限时未发出的请求，所有已登记的 Run 均完成。

现有证据支持把优化重点放在每秒独立提交次数及 Projector 在忙时取回结果的延迟上，继续增大连接池的依据很弱。下一项可独立验证的是减少可合并的稳定写入提交，或把 Projector 和 PG 分配到独立计算资源后复测。两项应分开对照，并保持输入确认、工具派发和崩溃恢复的边界。[复现说明](../../scripts/experiments/minimal-session-storage/README.md)
