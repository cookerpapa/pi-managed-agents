运行代码动工前，用 ADR 明确修改 ADR-0376、0377、0378 哪些规则，绑定本计划中的事务、协议和故障行为。#52 原题使用“父子共用物理 Session、接回原工具等待”的旧前提，执行时同步其验收描述，保留失去 Worker 后无重复工具副作用的验收目的，并区分不同工具的恢复合同。

## 1. 从投信到 Worker 第一次请求

- 用户、子 Agent、定时计划都向 `user_or_agent_messages` 写信。用稳定的 input_id、来源、目标 Session、投递方式、队列顺序和状态标识输入。尚未选用的消息允许 turn_id 为空。HTTP 同步提交后返回 input_id，网页显示“已送达”。把 API、共享客户端、Web 中“收信一定返回 turn_id”的调用一并改成按 input_id 跟踪。保留用户采用前的撤回、重写、排序和附件 pin；Pi 的正式采用与同一 input_id 关联后才显示“已读”。
- 现有子 Agent 执行器扩为会话命令执行器，复用现有到期监听器。一次发生使用稳定的计划和发生时间标识，同步事务中去重投信并推进计划游标；计划可选 steer 或 follow-up。创建命名子 Session 和投第一封信原子提交，创建应答在登记后返回。孩子的最终消息由孩子显式 send_message。用户 HTTP 入口直接复用入信服务。 计划页只有在该计划的消息开启了目标 Turn 时才提供 Stop；服务端在原取消事务内复核开启者，删除计划后仍可验证。给已有 Turn 插入一封信只影响该次投递，删除计划仅停止以后触发。
- 由同一管理通道接收 PG 提交后的通知，按空位、有资格的热缓存和公平性定向唤醒。候选集合改为有可启动输入的空闲 Session 和有故障 Turn 待接手的 Session，从索引限量选取，避免扫描全部信箱。Worker 批领时锁 Session、复核容量和状态。新工作在同一同步事务签租约、建 Turn、预留首封输入；接手则只给原 Turn 签新一代租约，即使无人再发信也能被领走。两个 Worker 并发不得重复建轮。通知遗失沿用补查。
- 忙碌会话的 steer 在 Pi 工具边界按本地提醒取信，follow-up 在自然收尾边界取信。正常封口只释放旧执行，未采用输入留下次领取，删除原来替它随机创建下一轮的触发器。保留用户 Stop 后退回待发用户输入、未读 Agent 来信等待下次人工启动的规则。验证 T17 工作中定时到期再来用户 steer，真实模型在 T17 看见 steer，期间无提前建立的 T18。
- Session 持有默认设置，Turn 保存领取时实际采用的模型、思考与服务档位、逻辑 Workspace、目录和设备授权；显式随输入指定的设置有确定优先级。改模型对下一 Turn 生效，故障恢复沿用原 Turn。工作目录、设备的更换须静止。有效新输入对已有弹性环境尝试续期，纯聊天不新建 VM。资源管理返回保留、换代、正在回收或状态不明，Worker 只看逻辑变化；确认目录消失时告知 Agent、停止本轮，允许用户重绑。物理路由、原操作取消和卷所有权仍由执行侧负责。

## 2. 执行时序与 PG 热路径

| 数据 | 写入与读取合同 |
| --- | --- |
| `messages` | 稳定正文、已采用输入、正式 Tool Call/Tool Result、已确认执行意图、必要配置历史和执行边界按其既有语义追加。来源列区分 topic、partition、offset、同一事实里的项目序号。Pi 原生 commit_seq、ordinal、entry_id 保持原义。展示游标单列或显式映射，一批含多个展示事件时也能区分。 |
| 开始、接手与封口 | 内部行携带逻辑 Session、所属 Flow、Turn、writer 代际、边界类型、原因及其真实来源。有序的开始／接手在该 writer 的正文之前可见；领取同步登记和 Kafka 中出现的位置分别表达，不能伪造 offset 或占用 Pi 的原生 ID。故障封口关闭旧 writer，后继接手同一 Turn。正常结束、失败、用户停止保留各自原因。边界追加与执行状态转换同事务；对照组的分区进度也在该事务内推进。网页正文、模型上下文、Fork 可见范围分别过滤内部行。 |
| `turns`、`session_leases` | 保存本轮冻结设置、领取、撤销、封口和交接所需的权威执行状态。普通正文按分区及 writer 代际的有序内存视图接纳，合批 INSERT；撤掉为展示更新 Turn 或逐正文回查 Worker / 租约的 SQL。输入正式采用可在同事务更新其信箱行。投影重复可重放，迟到 writer 的正文和效果均不得通过。 |
| 分区恢复位置 | 对照组沿用 `accepted_fact_projection_offsets`，在已有稳定事务中推进 next_offset。优先验证取消每批游标更新的方案，按本分区保留下来的 Kafka 来源事实推导安全重读位置。验收见下文。两组均要求纯流式片段零 PG 写入。 |

真实消费者保留同分区现成记录合批。遇到 writer 变化、seal、失去分区所有权或外部效果，按边界拆批。分区所有权失效时废弃旧草稿和待发布效果；在 rebalance、延迟事务、旧代际迟到、接管与撤销竞态下验证 PG 里绝无旧 writer 正文，再移除当前热路径条件写。租约过期按现有控制侧封口协议处理。只有 Projector 对可重建的 Kafka 派生事务可局部异步提交；收信、计划、领取、续租、资源授权、牵涉交接/调度的封口维持同步提交。

### 删除与裁剪方案（已确认）

删除和裁剪以逻辑 Session 为单位。这项设计已确认，七天宽限和每日维护入口待实现。复用当前的 [裁剪事务](../../scripts/experiments/minimal-session-storage/fork-layout.sql) 和 [公开 API 适配](../../packages/control-plane/src/segment-history-transactions.ts)。在同步事务内，以稳定操作 ID 去重，取得与领取兼容的锁并复核无活动 writer，固定保留到的原始 Flow/Entry 及提交上界，切换可见历史，记录原历史版本、保留位置、新版本、时间和受影响的 Session。整会话删除保留独立于已删除 Session 行的操作记录。相同操作重试返回原结果。操作记录不写入共享正文、不伪造 Kafka 来源位置，也不创建可领取的 Turn。

当前 `fork_gc` 每个租户、物理 Flow 最多一行。裁剪事务已经把失去直接引用的 Flow、受影响的祖先段和配置来源用 UPSERT 登记到该表。为工作项增加最早可回收时间。一次新的删除或裁剪再次影响同一 Flow 时，将扫描位置重置到开头，最早回收时间至少覆盖本次操作后的七天。重试同一操作不延后期限。第一版允许整个 Flow 因重复裁剪而延迟回收，观测最老到期工作及积压字节。每日维护任务按到期索引取工，复用现有每事务最多检查 512 个正文键的收集函数。删除无引用的数据与推进扫描位置同事务，崩溃后接着扫描；扫描结束移除工作项，操作记录与工作项分别管理。共享前缀、配置及附件按实际引用保留。若墓碑还用于拒绝旧 Kafka 记录，只有旧位置确实退出可重放范围，或另有可靠的拒绝依据时才回收墓碑。接入正式维护入口，验证不调用测试的 collect 帮手也能回收。这里不使用用户定时投信或 Pi Worker。

### 取消每批分区游标更新的对照实验（待验证）

删除方案的实施不依赖游标实验的结论。对照实验加入两个会话共用分区的场景。日常会话 A 的最后一条稳定记录在 100，随后一次批处理会话 B 在 101～10000 产生大量记录，并在 10000 封口。删除 B 后，B 立即从用户的会话列表消失。计算恢复位置时仍要考虑宽限期内物理保留的来源行。七天后，若 B 的这些行均已回收、没有 Fork 引用，也没有其他更高的来源行，PG 保留行的最大 offset 会从 10000 退回 100。Kafka 的 offset 不倒退。恢复实验分别覆盖 Kafka 已轮转掉 B 的全部记录、仍保留部分记录，以及另一个幸存会话在 10000 后已有稳定记录三种情况，测实际重读条数和字节数。

**对照方法。** 在同一 #52 真实分区消费者、相同源记录布局和迁移版本上串行比较。A 使用现有游标，B 关闭逐批游标写入，冷启动和 rebalance 也不得读取 A 的游标。B 按同一 topic 实例与 partition，在所有租户、所有物理 Flow 的保留来源事实中找最大安全 offset；同一 Kafka 记录的所有必需 PG 变更已原子提交，才可以越过该记录。若只能证明部分批内项，则重读该 offset 并逐项去重。会话删除时间、API 请求时间、Kafka 末尾以及消费者组提交位置都不能用来填造 PG 中的已处理位置。正文查询与 Fork 的权限边界不变。记录新增来源索引造成的写放大、空间和启动读取成本。

| 故障或负载 | 验收证据 |
| --- | --- |
| 历史沉寂、突然来信，或很热的分区刚好删光高位行 | 保留下来的最大 offset 分别为 100、80 或空。测从较早位置或 Kafka 实际保留起点恢复的记录数、字节和耗时。新会话尚未投影的首条采用、封口和工具状态不能被跳过。在已知没有保留期缺口的空分区也无需跳到 Kafka 末尾。 |
| 同批多条、异步提交已返回但 WAL 未持久化，PG 与 Projector 同时退出 | 在同一分区有 A、B 交错的前提下，注入故障后与基准逐项比对正式正文、采用回执、writer 边界与 Turn 状态。故意延迟前一个事务并尝试让后一个事务先提交；如出现高位行掩盖低位缺口，B 不通过。 |
| 旧 Projector 的事务与新所有者交接、控制记录没有正文行 | 现有 SQL 同时把分区进度行用作事务锁、预期前缀校验和重复批次判定。B 必须证明这些职责由现有分区所有权与事务边界承接，或单独列出所需的低频保护。旧 writer 无写入权，正常/故障封口按有序位置只生效一次。已取得派发许可的 Bash、MCP、Skill 修改和子 Agent 创建都不得因回看重复执行。 |
| 人工 Fork、连续裁剪、删除最后引用，回收中断及七天边界 | 源会话裁回 B 后，分叉仍能读到 C、D；最后引用解除且宽限期到后才回收。观察删除与 GC 之间、GC 中途和 GC 完成后三次重启。过期旧记录不会复活历史。Kafka 实际日志起点超过推导位置时，分别验证“已覆盖后被回收”与“可能有未投影记录已过期”。无法区分时显式报告缺口，不宣称已追平。 |
| 稳定正文已落库，其他 Session 尚有半截回复或原生工具等待 | 分区正常投影完成后仍能补网页半截，并通过“先丢 Projector，再丢 Worker”接回同一 Turn。单凭分区最大值不能省略展示及原生状态各自需要的后缀。 |

比较固定 20 工具混合负载，以及空闲七天、流式多而稳定记录少、集中删除三种恢复负载。报告可见消息/s、分区 lag、收尾 p95/p99、PG 游标更新次数、锁等待、CPU/WAL、来源索引代价，并单列冷恢复耗时和额外重读量。正确性通过且常态写入成本与恢复代价可接受时，采用 B 并移除旧依赖。若仍需要持久的前缀保护，先用失败轨迹解释缺的保证，再比较仅在交接或低频边界记录进度的代价。取消每批游标写入仍以该实验结果为准。

## 3. 流式输出控制器与网页

1. 从现有 SessionLiveView 和 session-event-stream 改出明确的展示接口。第一版由当前分区所有者进程托管，Session API 路由到此所有者。Projector 派发文字追加或替换，以及 PG 提交成功后的完整可见消息。完整 M2 自带最终展示内容，能直接插入或替换半截 M2；图片与附件走原有授权引用。最后一条回答也必须送达已打开的网页。
2. 每个事件带稳定消息标识和 Kafka 来源位置，包括同条记录内的展示序号。订阅与缓存隔离键含租户、逻辑 Session 和可见历史版本。Fork、裁剪换 Flow 后不得拼入来源会话或旧分支的活动尾巴，游标只能在所属流内比较。去重按有序已覆盖范围处理。现在某些描述需要查旧 Projector 内存中的 pi.live 文档才能还原一段字，先改 Worker 的展示编码，使该片段或替换内容能从当条事实解出，尽量引用同条已有字节；测量 Kafka 体积和解码成本。保持 Pi 原生 Storage 提交完整。旧接口若要求 SSE 整数序号连续，明确处理旧代际和重放，不能从消息 ID 或稀疏 Kafka offset 猜连续性。
3. 每 Session 初始保留最近 **4 MiB** 的实际展示数据，按字节逐步淘汰，按需分配。相邻文本合并，完整消息替换已缓存的片段。设全局内存与磁盘预算，按读热度和大小将冷内容移到本机 SSD。缓存和可证明的来源范围一并保存，重启不能只留去重高位却丢掉正文。读者能区分已接上但无新字、位置已轮转、控制器尚在重建。超过单会话窗口、磁盘满或缓存丢失时明确进入重建；对仍未完成且超过窗口的回答，按需从保留的 Kafka 后缀补给读者，避免将缺开头的文字当全文或对同一缺口无限重读 PG。测量该退路的成本。没有五分钟/一天轮转，也不为此增加 Worker 探针。
4. 网页打开或刷新时，先原子建立订阅并取得不可被后续轮转修改的当前快照，暂存订阅后到达的事件；再从主库按 Session 可见 Flow 范围读有界的完整正文页；最后以覆盖位置合并快照、去重并消费在途事件。订阅是非破坏性读取。PG 与订阅之间发生 M2 收尾，多开两个标签、断线重连、缓存正在换段，均不得重字、漏字或要求 M3 才展示 M2。沿用有界 SSE 队列和重连协议。状态/Stop 接口仍可读 Turn；正文读取和分页摆脱 Turn 展示序号。

## 4. 恢复、回放和真实工具

| 场景 | 谁负责、从哪里恢复 | 必测结果 |
| --- | --- | --- |
| 单独重启 Projector 或 rebalance | 同一启动入口冷读 PG fencing。对照组从 next_offset 继续，候选组从上述按分区推导的安全位置重读。可验证且完整的展示缓存直接续接。失效分配不能再投影或派发。 | 最后封口在 100，101–105 已进 Kafka 但 PG 仍只看到封口：新消息全部投影。裁剪或回收使重读位置变早时，保留历史、封口与外部效果仍然正确。 |

**保留一个需要用故障实验决定的存储取舍。** 在当前代码中，即使流式控制器完好，Projector 还会从活跃 writer 的首条输出重建未来故障封口所需的原生任务状态。改变正常投影起点后，必须证明“先杀 Projector，再杀 Worker”也能生成真实的交接内容。先沿用现有故障专用 handoff，验证可由 PG 正文和信箱合成的字段，然后验证缺失字段从什么位置能重建。正式边界行始终保留；临时恢复数据的载体可独立演进。只有在同一服务入口证明了替代方案，才删旧首条回看、checkpoint、原生交接字段或兼容读者。若维持正确恢复必须新增常态存储，提交字段、写放大和替代方案给所有者评审，避免恢复逐片写 PG。此项通过前不切生产。

## 5. Skill、MCP 和其他现网入口

- 平台普通 Tool 保持全局目录、按模型请求固定的实现和在途旧版本保留期。显式禁用在执行准入时拒绝并给出正式工具结果。个人、项目、组织范围的 Skill/MCP 在领取或重连时加载授权快照，复用管理连接按活跃 scope 推送 revision 提醒。空闲会话下次再加载，通知遗漏可补快照；用户变化不广播给所有 Worker，也不为每个用户建 topic。
- Skill 目录在下一次模型请求生效。提示词只带有效 Skill 的名称、说明和能力要求。模型使用 `read_skill` 时携带采样时选定的不可变包版本；由 Skill 执行器在需要时准备沙箱文件并返回说明、可用路径，读取本身不执行脚本。使用 `manage_skill(publish/install/uninstall)` 管理；建议发布默认给自己安装，可显式仅发布。市场限组织内分享。目录取个人、项目、组织授权后的有效集合。
- 修改目录和登记通知同一事务，调用按 operation ID 去重。回包带 scope、base_revision、revision 和变化项。Worker 在下一次采样前达到回包要求的最低 revision；连续则本地应用、缺口则重读授权快照、迟到通知去重。故障接手也能找回已确认的最低 revision。测试“回包比订阅先到”、在途 v1 遇到 v2、卸载个人项后项目仍提供同名 Skill、显式禁用、不同租户同名资源。
- 接入现有 MCP 管理页和授权服务。成员管理个人连接，组织共享由获授权角色管理；保存连接、远端发现完成和可用工具出现分别反馈。普通 Tool 的版本保留不替代 MCP 执行前对连接可用性、授权、凭据撤销的核对。凭据只在执行侧使用。
- 打通候选 Worker 的普通 Guest、执行侧真实路由和 HTTPS 回包、附件上传/图片准备端口、资源管理端口、手动 `/compact`。回归现有 `/status` 的上下文估算和 `/usage` 的网关回执查询。原生合在 Pi 提交里的用量不裁剪；普通投影不为客户计费判定多写一遍。真实浏览器覆盖导航、长历史分页、从根到孩子逐级切换、Stop/删除子树和人工 Fork 的隔离；附件随信箱、草稿、采用和 Fork 保持各自引用。
- 父子 Session 分别领 Worker 和租约；保留 branch/fresh、命名、授权交集、主动发信及回执语义。保留免固定等待的热续聊，RAM/Worker SSD 缓存须经权威版本校验；Fork 冻结的公共段可复用。线上保留的 Cube、BoxLite、Android 和自有设备走各自声明的能力，按受影响的执行合同串行复验。分库和读副本、另建调度平台均不作为本次上线依赖。

## 6. 性能、故障矩阵与发布

复用[同一入口的混合负载及结果](independent-session-reconciliation-20261128.md)和[安装 v3 的升级长尾](independent-turn-references.md)。每个改变热路径的切片留一组可复现的前后数据，重的实验在这台主机上串行做。两个主要指标为已核对的可见调用／结果／助手回答每秒（包含排空），以及末次模型输出到 PG 确认收尾的 p95/p99；同时记正常／接手 Turn 完成数和 Turn/s，已采用输入等其他类别单列。Kafka 原始记录和 token 片段不混入可见消息分子。

1. 基线用同一份 20 工具固定 trace、480 Session、19,680 条可见记录、四分区、RF3、PG 两核、相同 Worker 空槽。先重跑约 164 和 410 条可见消息/s 的定速输入，报告每轮时长、并发、吞吐及分区 lag／增长／排空、SQL 次数、CPU/WAL、设备回包延迟。50 ms 模拟结果延迟用于可比测试，真实 Guest 调用单列。历史配套镜像在 410 档约 392.4 条/s（含排空）；它是定速对照。旧的 7,000+ 完整 Entry/s 是预积压单项测量，不作为线上端到端数字。
2. 新装、从已有候选数据升级、拟定的实际生产迁移三条都跑。现有升级实验曾降至 269.3 条/s，收尾 p99 为 23.07 s，而同次新装约 392.4 条/s、79 ms。计划分析把频繁 Turn 更新的放大定位到具体 SQL，保留逐分区 lag 及 EXPLAIN/缓冲区数据。禁止顺序扫描仅做过诊断。重复成功不能覆盖已出现的卡分区和误回收。再测有浏览器刷新/翻页和无读者的写入负载；先排查回归，再提高目标输入直到出现持续积压，报告可持续边界。1,200 条/s 可作为另列的峰值探测，不能预填为能力。
3. 缓存验收包括第一片／一千片零 PG 写、慢生成八分钟、同一记录多个展示事件、跨 4 MiB、多标签、SSD 冷读/清空、真实 HTTP/SSE 断线、无片段直接完整、无后续 M3、同一 Turn 改默认模型、两个 Projector 换主。用事件与页面正文比对，无漏字/重字、旧 writer 无效果，记录缓存字节、SSD I/O、首屏和重连耗时。用控制点故障注入卡在提交前、提交后派发前、派发后回包前。每一档保存所有轮次及有效时长，登记/领取、生产者发布、等 PG 连接、事务执行、派发、封口分别计时。以相同输入做至少三轮串行对照；如果同口径持续吞吐跌出基线波动范围、lag 不收敛或收尾再现秒级异常，先定位具体阶段，再讨论取舍。需要新增常态数据库状态或错误接手仍可重现时，同样保持发布保留。
4. 在配套部署入口对齐 API、Worker、Projector、会话命令/Skill/Tool 执行器、Web、迁移和路由；从干净 checkout 构建，通过隔离安装与同宿主串行真实模型、Chrome、沙箱验收，锁定 digest 和证据。将已验收的候选历史整体纳入 main 并核对发布树与制品来源；如果 main 同期变化改变了实际运行内容，从最终树重建并重复受影响验收。切生产前完成生产配置与路径差异检查，再按 [matched release](../MATCHED_RELEASE.md) prepare、preflight、apply；复用未受影响的镜像。暂停接单，排空旧 writer、上传及执行结果，核对开放租约、外部资源与卷实际归属；保留账号、凭据、模型和供应商配置。切换前可以撤回；新 schema 或首个新写入后走同版本修复/重放，不能让旧 writer 连回不兼容的历史。
5. 上线后用独立验收会话经过真实公共地址连续聊天、刷新、一次 Guest 调用、一次定时投信、个人目录回读和一次受控接手。记录生效 SHA/digest、分区状态、用户可见结果和剩余限制，更新架构/运行文档、Backlog 与 #52。通过才解除该候选的发布保留。“代码已经推送”“隔离镜像已经通过”“生产验收完成”分别登记。
