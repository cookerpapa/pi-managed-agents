# #52 · 续聊环境和完整消息合批投影

## 续聊先读当前 Run 的环境

控制面把空闲会话的工作目录和执行环境选择写到 PG。在登记下一条输入的同一事务中，
对环境选择加共享锁，给新 Run 留下一份确定的环境。改环境的事务锁同一行，并检查
会话已空闲。Worker 领取时一并得到这次和上个正常完成 Run 的环境。命中版本匹配的
历史缓存，可以省掉读取正文；这个缓存不提供当前目录，也不提供工具执行目标。

两组各用一份 320 KiB 的初始历史，运行真实 Pi、PG 领取和 Kafka 投影。确定性模型记录
首次请求中 Pi 已合并的系统提示。验证器另从消息表读出 Pi 提交的系统提示变更，并对
用户和助手历史逐字节校验。运行中尝试修改环境须被拒绝。沙箱重建以资源侧确认的逻辑
代次为输入；此次测的是这个事实到下一次模型请求的传递。真实 Guest 路由与取消见
[执行侧操作路由实验](workspace-operation-routing-20261121.md)。

| 两次 Run 之间发生的事 | 下一次模型请求实际收到的语义 |
|---|---|
| 首次选择目录 | 当前目录 |
| 同一 Workspace 从游戏目录切到 client 子目录 | 当前目录，以及从哪个目录切来 |
| 同一 Workspace、相同目录，已确认沙箱重建 | 当前目录；文件仍在，先前的进程可能已经退出 |
| 路径相同，换成另一个 Workspace | 应先检查这份 Workspace 的文件，然后再使用历史中的相对路径 |
| 环境连续保持不变 | 只保留当前目录；已有相同提示时不再新增原生记录 |

两组各完成 7 个 Run。第一组从第 2 个 Run 开始有两个空闲 Worker 可以领取，6 次续聊
均定向回到原 Worker，6 次历史正文读取量均为 0。第二组在沙箱重建后的第一轮先让
原 Worker 退出领取，接手 Worker 从 PG 读取 338,802 字节的历史，第一次请求就收到重建提示。
两组逐轮的有效环境相同，连续保持同样环境时新增环境更新数为 0。真实物理 VM 的状态探测
和已中断 Run 的环境恢复不在这组连续正常结束的 Run 中测量。

## 真实 Guest 的续聊验收

两台临时 Cube VM 各自有一个 Workspace。资源夹具只登记 Workspace 对应的 VM。
第一次工具意图到达执行侧时，由执行侧读取该 Run 在接收输入时固定的 Workspace 和工作目录，
取得对应的 Guest attachment。模型只调用 Bash 打印实际目录并读取相对路径 `marker`，
命令中没有 `cd` 或文件绝对路径。每个目录中的文件由 Guest 自行生成，带独立的随机标记。

| 续聊位置 | 模型收到的提示 | Bash 实际目录 | 读到的文件标记 |
|---|---|---|---|
| Workspace A 的根目录 | 当前目录 | `/workspace/game` | `root-…` |
| A 的子目录 | 工作目录已变 | `/workspace/game/client` | `client-…` |
| Workspace B 的同名子目录 | Workspace 已变 | `/workspace/game/client` | `other-client-…` |

同样的三步分别在三种调度条件下执行：两次续聊都命中原 Worker，在换目录时换 Worker，
在换 Workspace 时换 Worker。对每个 Run 核对首次请求的系统提示、Guest 中的执行记录、
第二次模型请求读到的完整结果，以及 PG 中与原 Tool Call 对应的唯一 Tool Result。
三组共 9 次派发、9 次 Guest 执行、9 条最终结果。后续 Run 的 4 次缓存命中均从 PG
重读 0 字节正文，两个切换点也分别验证了冷读。

实际命令经 Projector 的 Kafka 派发确认后，由测试驱动里的执行适配器调用固定 Guest。
Guest 经 HTTPS completion 和 Worker 原回包 Topic 交回结果。普通回包凭据只携带工具关联信息；
直接沿用正式执行器的默认回包凭据，会让 completion 把物理绑定一起送回 Worker。本次在原型的凭据签发处
选择普通回包所需字段，保留执行侧诊断探针的物理证据。Worker 在实际回包中检查这个边界。
使用同一执行器装配重跑了父子会话的 6 项回归，覆盖正常完成、执行中 Stop、接手后才回包、
接手前已回包、超时后迟到以及接手后的 Stop。每项均观察到一次物理执行和一条规范的 Bash 结果。

本项使用确定性模型、原型的 PG 登记与领取接口，以及 VM 内预置文件，覆盖正常结束的 Run 之间
切换环境。公网模型、正式资源管理页面、持久卷重挂和并发容量均有各自的验收范围。

## 投影吞吐

每轮使用同一份 768 个 Run 的会话历史，每个 Run 含 100 对已记录的工具调用和结果。
正文每条约 4 KiB，每轮计数 153,600 条。32 个分区，Kafka 副本数 3，PG 连接池 12。
逐条和合批两种模式使用相同的执行侧解码、PG 数据模型、异步提交与结果核验。
合批只取当前分区已经到达的纯历史前缀，每批至多 16 条。工具派发、取消、输入确认
和封口保留原有顺序。每轮核对 155,136 个原生 Entry 的内容和顺序、全部 Run 收尾和
最终 Kafka lag。负载没有执行历史里的 shell 操作。

| 工作负载 | 逐条投影 | 合批投影 |
|---|---:|---:|
| 预先填满 Kafka，再排空，条/秒 | 2,543 / 3,847 | 6,285 / 4,935 |
| 目标每秒输入 4,630 条，含排空的实际条/秒 | 1,695 / 2,943 | 3,766 / 4,238 |
| 预填排空期间 PG 事务数 | 156,672 / 156,672 | 12,412 / 12,357 |
| 真实短 Run，模型输出完成至 PG 收尾 P95 | 74 / 60 ms | 55 / 61 ms |

短 Run 单独测量，每轮 192 个，最多 64 个在途，运行 Pi 并调用确定性模型。正文排空
速率、端到端短 Run 每秒速率和真实外部工具每秒执行数是三种不同口径。另用隔离的 serving
Projector、PG、三副本 Kafka 和一台实际 Cube Guest 跑了一次父子会话：一次 Bash 派发，
Guest 执行一次，Pi 留下一条最终 Bash Result，Run 正常结束。该样本只核对功能。

在第一轮合批限速对照，生成器发送滞后 P95 为 6.68 秒。第二轮只滞后 1.22 ms，
投影端采样最大积压 15,313 条，预定发送窗口结束后又花了 3.07 秒排空。后一轮
直接观测到了投影落后于输入；不能只凭最终 lag 为零判定能持续承受峰值。

补测时记录同一主机时钟下生成器收到最后一条 Kafka ACK 的时间，并每 500 ms 采样消费
lag。对照直接投影和带执行路由的合批投影，两者重用同一份 tape，各重复两轮。

| 复测顺序 | Kafka 实际输入（条/秒） | PG 投影（条/秒） | 消息从预定发送至投影 P95 | 抽样最大 lag |
|---|---:|---:|---:|---:|
| 原型直接合批 | 1,728 | 1,729 | 53.59 秒 | 3,392 |
| 执行侧合批 | 4,621 | 4,625 | 84 毫秒 | 398 |
| 执行侧合批 | 1,984 | 1,986 | 38.14 秒 | 3,193 |
| 原型直接合批 | 4,622 | 4,625 | 523 毫秒 | 3,960 |

表中慢轮的生成器本身落后于预定发送时刻，P95 分别为 53.86 和 39.07 秒。四轮结束时投影均已
赶上最后一笔生产 ACK；中途仍有积压。两条实现都出现了输入偏慢的轮次，这组证据无法在
生产客户端、broker、副本确认或共享主机资源之间进一步归因。

最后两轮仍以 4,630 条/秒为目标，先阻止 Projector 写 PG，直到生产者收到整批 Kafka
ACK，再单独排空。这时 Kafka 实际输入分别为 4,623 和 4,612 条/秒，发送迟到 P95 均
低于 1.3 毫秒；之后相同投影器分别排出 7,155 和 4,463 条/秒。输入和投影同时运行时
出现的波动值得保留为下一项容量调查。现阶段可以继续在隔离环境接入真实工具，分项
复测生产端 ACK、分区积压和工具外部效果，尚无持续峰值容量或上线结论。
