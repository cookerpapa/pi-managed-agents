# 给 PostgreSQL 的原生组提交增加等待，会减少多少积压

服务实例是 PostgreSQL 17.6，实查 `fsync=on`、`synchronous_commit=on`、`wal_sync_method=fdatasync`、`commit_delay=0`、`commit_siblings=5`。默认设置已经允许并发事务搭上同一次 WAL 刷盘。`commit_delay` 可让负责刷盘的后端额外等一段时间，给其他事务加入的机会；单位是微秒。`commit_siblings` 指有多少个其他事务活跃时才值得等。每笔事务仍独立提交、独立返回。应用把多个 Kafka 记录合成一笔 PG 事务，是另一个实验。[PostgreSQL 17 的说明](https://www.postgresql.org/docs/17/wal-configuration.html) · [参数定义](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-COMMIT-DELAY)

## 保持写入语义，单独改变提交等待

在独立临时 PG 上切换服务参数并重新加载，逐一核对 Projector 的 12 条预热连接，确认等待参数、同步提交、刷盘方式和持久化开关。PG 与 Projector 在所有测量中都能使用全部 32 个 guest 逻辑 CPU。真实三副本 Kafka、相同的 32 个有序分区及稳定投影 SQL 都保持同一套配置。每轮从相同的已领取 Run 状态开始，验证每个分区的顺序、所有 SQL 绑定值，以及消息、Inbox 和 Run 终态内容。参数恢复后销毁实验实例。[实验代码](../../scripts/experiments/minimal-session-storage/pg-group-commit.mjs) · [逐轮汇总](pg-native-group-commit-20261119.json)

第一套录制有 6,240 个新会话 Run，一次回放包含 43,680 条原生日志与结束记录、24,960 次 PG 自动提交写入。以每秒 260 个 Run 交叉比较四种设置，每种四轮，均衡其在每组中的顺序。另以 520 Run/秒各测两轮，再恢复用户登记、Worker 领取、Pi、Kafka 和 PG，按每秒 260 个请求、每轮 40 秒各测两轮。使用本地确定性模型。回放全部投喂，完整链路驱动最多等待 384 个在途请求。

| 等待时间 / 其他活跃事务门槛 | 260/s 回放，每千笔投影写入的 WAL 同步次数 | 回放达标 | 回放 P95 范围 | 完整链路达标 | 完整链路 P95 范围 |
|---|---:|---:|---:|---:|---:|
| 0 / 5，默认 | 290 | 2/4 | 66–1,214 ms | 0/2 | 1,038–4,163 ms |
| 0.5 ms / 5 | 259 | 3/4 | 70–7,862 ms | 0/2 | 2,675–3,884 ms |
| 1.5 ms / 5 | 225 | 2/4 | 70–3,287 ms | 0/2 | 1,974–2,337 ms |
| 1.5 ms / 0 | 205 | 4/4 | 69–337 ms | 0/2 | 2,342–4,315 ms |

达标条件为所有计划请求发出并完成、P95 不超过 1 秒、结束投喂后 1 秒内排空。WAL 次数取临时实例 `pg_stat_wal.wal_sync` 的窗口差值，只在工作量完全相同的投影回放间按写入数归一化。计数可能含少量后台活动，不能据此还原每一组包含哪些事务。完整链路还会执行登记、领取等其他数据库事务，另报端到端结果。

第一套 260/s 回放中，额外等待 1.5 ms、门槛为 0 时，WAL 同步次数较默认减少约 29%。同一设置的完整链路仍出现超过 2 秒的尾延迟。520/s 时所有设置两轮都未达到门槛，即使同步次数较少仍有积压。各轮运行在同一 WSL 节点的不同时间，独立主机速度校准也有波动，单个快轮的尾延迟不能当作持续容量。

## 独立复测与低负载

第一组回放表现最好的设置是 1.5 ms / 0。用新的临时 PG 和独立录制的 4,160 个 Run，只比较这个候选和默认配置，反转开始顺序。每种设置回放四轮，另以 260/s 和 10/s 各做两轮完整链路测试。

| 独立复测 | 默认 0 / 5 | 1.5 ms / 0 |
|---|---:|---:|
| 260/s 回放，每千笔投影写入的 WAL 同步次数 | 274 | 203 |
| 260/s 回放达标及 P95 范围 | 4/4，63–862 ms | 2/4，65–3,151 ms |
| 260/s 完整链路达标及 P95 范围 | 1/2，98–3,686 ms | 0/2，3,383–4,232 ms |
| 10/s 完整链路 P95，两轮均完成全部请求 | 61 / 74 ms | 83 / 87 ms |

WAL 同步次数下降约 26% 的效果在新录制上重现。投影尾延迟的改善没有重现。两组实验合计，目标 260/s 的完整链路试验中，默认配置四轮有一轮达标，1.5 ms / 0 四轮均未达标。驱动达到 384 个在途请求上限时，分别有 3,904 和 6,419 个计划请求未发出，已发出的均完成。此处完整链路从用户提交计时到 PG 终态。回放则从首条原生记录应当到达时开始计时。独立慢窗口的整机速度也有差异，不能据此断言主动等待在所有部署上都会更慢。

两套正式数据合计 **32 轮相同内容回放，183,040 个 Run，732,160 次真实投影事务**。全部通过分区顺序、参数和最终表内容核验。结果支持**保留默认 `commit_delay=0`、`commit_siblings=5`**。对于四次独立事务的成本，应用侧在满足同一确认边界时减少事务数，仍是可单独检验的实验。本次没有合并应用事务，也没有降低任何提交的持久性。

## PG 已经有位置，Kafka 消费组位置还管什么

维护中的 Session Projector 在 PG 的 `accepted_fact_projection_offsets` 按 Topic、分区保存下一条位置，与需要落库的稳定投影同事务提交。重启时也会查未封口 Run 和有待重建的文档所需的最早日志。纯数据库投影可以用事务内的 PG 位置重新定位，只要 Kafka 仍覆盖所需区间。消费组提交不删除 Kafka 消息。当前 Session Topic 关闭按大小和时间自动过期，平台清理器依据 PG 检查点、未完成重放所需的下界及保留时间裁剪旧前缀。[投影与恢复位置](../../packages/runtime-core/src/accepted-fact-recovery.ts) · [Session Topic](../../packages/runtime-core/src/execution-log-topic.ts) · [安全清理](../../packages/runtime-core/src/kafka-safe-retention.ts)

这个消费者还派发工具。假设 offset 120 是工具意图，PG 写好后 `next_offset=121`。消费组还在 120 时，接手者仍能读到该记录，按当前身份和规则争取派发许可。消费组已成功确认到 121 时，即使因为更早的恢复需要而重读 120，也会跳过该次外部派发。这个标记消耗了一次派发机会；它不能证明 Bash 已执行，也不能证明执行结果。确认成功与真正发出命令之间崩溃仍可能导致结果不确定。控制发布事务也使用当前组成员作为所有权保护。实际起点综合 PG 的重放需求与消费组的投递位置，取需要的较早处。本次实验只改临时 PG 的 WAL 刷盘等待。[消费与派发边界](../../packages/event-log/src/kafka-log-consumer.ts) · [控制发布保护](../../packages/event-log/src/kafka-partition-reader.ts) · [Kafka 的外部位点存储说明](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

已对照服务容器中的恢复代码，在线 Topic 实查为 32 个分区、三副本、最小同步副本数 2，`retention.ms` 和 `retention.bytes` 都为 -1。独立 RF3 故障检查验证了消费组已前进但 PG 仍需回放，以及 PG 已前进但有投递尚未完成两种情况。另测了倒回重建时跳过旧派发边界内的命令。第一次 Docker 测试夹具在关闭阶段超时，已确认容器退出并移走剩余空网络，使用全新夹具复验通过。[真实 Kafka 恢复检查](../../scripts/run-kafka-consumer-isolation-check.mjs) · [工具派发保护测试](../../packages/event-log/test/ordered-effects.test.ts)
