# 同一 Run 连续两次 Worker 交接

候选存储原先只验证了第一代写入者的封口。放开测试的代次限制后，B 从 PG 接回了
子 Agent 的 Bash 等待，Projector 在 B 的首条原生提交处停住。原生序号在同一次
执行中连续，而 Projector 为新写入者创建的空检查点从 0 起算。另一个边界是 B
刚领取就退出：此时没有属于 B 的新原生提交，C 仍需读到与 B 的封口匹配的交接信息。

在第一次处理 B 的原生提交时，Projector 从已有的 PG 交接字段恢复 A 的状态，
按原生序号折入 B 的已接纳提交。已经存在的 Inbox 文档通过其创建序号和文档 ID
识别，待发正文仍归当前 Inbox 行。若 B 完全没有发布，控制事务在确认上一代
租约已封口释放、位点及身份匹配、本代没有输出前缀且原生状态一致后，将该状态
随 B 的封口交给 C。使用原有 Run 行和 PG 事务。此改动没有数据库表结构迁移。

## 真实链路验收

在私有测试资源中，固定 Pi 实际压缩了父 Conversation 的早期历史，父 Agent
随后等待一个子 Agent。子 Agent 在真实 Cube VM 上执行有计数标记的 Bash。
A 与初始 Projector 都被终止。A、B 的恢复封口投影完成后分别从隔离的 Session
Kafka 分区删除相应前缀，最后由 C 从 PG 恢复并监听 A 的原回包 Topic。模型为
确定性测试端点。C 的父模型输入必须包含摘要且已移除压缩掉的原始标记；子模型
须拿到原 Bash 读出的随机值，父模型再拿到子 Agent 的回答。

| B 退出时的状态 | C 接回原操作 | Guest 执行次数 | 子会话最终 Bash 结果数 |
| --- | --- | ---: | ---: |
| 已经重新挂上等待，并已提交对原 follow-up 的编辑 | 原操作 ID、Topic、绝对截止时间均一致，C 还读到了 B 的编辑 | 1 | 1 |
| 刚领取，尚未打开 Pi | 从 B 的封口接回 A 的原操作与原截止时间 | 1 | 1 |

两个 Run 都正常结束。HTTP 父子会话视图和候选存储均核对过。该组故障只在
第一次交接前杀掉 Projector，第二次交接考察 Worker 丢失。原有单次交接的
晚回包、重复回包、超时和 Stop 场景沿用各自断言。该实验在物理 Session 的
首个根 Run 内完成，包含一次真实父上下文压缩；后续 Run、复杂多工具及完整
服务部署仍需各自验证。[实验说明](../../scripts/experiments/minimal-session-storage/README.md#atomic-handoff-after-loss-of-the-worker-and-session-projector-52)

C 在两次实验中从已领取到恢复状态与原邮箱就绪分别耗时 3.09 秒（B 未打开 Pi）
和 3.14 秒（B 已编辑待发消息）。每种时序各一次，时间不含租约过期、封口和 C
进程启动。六种场景结束后临时资源清理通过。[脱敏结果](repeated-family-handoff-20261122.json)
