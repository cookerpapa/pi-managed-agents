## Short Run throughput

Same host: Ryzen 9 7945HX, 32 logical CPUs, approximately 24 GiB WSL memory.
The matched comparison uses 192 cold, single-response Runs, concurrency 64,
zero simulated first-byte delay and 4,096-byte output. Measurement-driver hashes
are identical. The before measurement was made while build-only source edits
were in progress; serving application images were still the original release.

| Measurement | Completed | Runs/s | Run settlement p95 |
| --- | --- | --- | --- |
| Before | 192/192 | 4.66 | 16.26 s |
| After | 192/192 | 7.68 | 15.81 s |
| After, repeated | 192/192 | 7.83 | 16.48 s |

Throughput improved in this comparison, but high-concurrency tail latency did
not materially improve. The separate short matrix measured 0.79, 2.88, 7.13,
9.78 and 11.18 Runs/s at concurrency 1, 4, 8, 16 and 32 respectively. These are
bounded observations, not a universal maximum or a production capacity promise.

Pairing timestamps within each single-request Run shows where waiting moved:

| Interval p95 | Before | After | Repeated after |
| --- | --- | --- | --- |
| Submission → provider start | 16.05 s | 7.78 s | 6.36 s |
| Simulated provider | 9 ms | 24 ms | 19 ms |
| Provider finish → Run settlement | 1.36 s | 9.44 s | 10.78 s |

Percentiles must not be added. The faster front path exposes substantial waiting
after provider completion, including native publication, projection and settlement.
Observed Kafka lag peaks rose from 162 to 1,316/1,405 and active Root Runs from 34
to 63/64. These measurements support investigating the downstream queue, but do
not isolate its exact split between writer acknowledgements and PG projection.

Fixed-rate trials lasted 45 seconds. At 4 offered Runs/s, all 180 completed.
At 8/s, the generator reached its 32-in-flight bound: 315 completed and 45 were
never submitted, with settlement p95 7.42 s. The driver's functional acceptance
flag does **not** establish sustainable 8/s. No admission or durability limit was
removed to improve these numbers.

## History behavior

The matched history case uses eight Runs, concurrency two and 32 MCP Tool rounds
per Run. Before deployment all Runs completed but two history reads failed;
after deployment all eight history loads and all 16 requested pages succeeded.

| Measurement | Before | After |
| --- | --- | --- |
| Whole history load p50 | 712 ms | 780 ms |
| Whole history load p95/max (eight samples) | 8,816 ms | 1,095 ms |
| Subsequent-page p95 | 515 ms, 12 successful pages | 595 ms, 16 successful pages |
| History failures | 2 | 0 |

The improvement is removal of the reproduced severe outlier/failure, not a claim
that every ordinary page became faster. Source regression also bounds real PG
buffer work for a tiny page under underestimated tenant statistics, and preserves
Fork/source deletion, off-page Tool arguments, byte budgets and child histories.

## Acceptance and operating notes

The 17-profile functional matrix completed 924 submitted Runs with no unexpected
Run/history failures. It covered real Guest Tools, HTTP MCP, long Tool loops,
children, images and SSE fan-out. Warm continuation, expired-context fallback and
native compaction passed. The distinct 8/s generator drops above are retained.

Fault acceptance passed Worker replacement with the same logical Run, Projector
restart, Stop with ignored late replies, and lost-reply handling without repeated
physical effects. Injected 429/disconnect requests settled as expected failures;
subsequent recovery requests succeeded. This does not fix the separately tracked
synthetic-429/quota classification. Every fixture restored configuration and
drained owned Run/lease/Kafka work before cleanup. The receiver's real health
endpoint and two transport contract tests also passed.

The owner explicitly chose existing vulnerability databases. Scans used the
November 15 vulnerability database and November 13 Java database; dates were not
rewritten. The cached scans passed. A stopped download resumed from completed
images with original source/digest checks, without another image build. The first
Guest build's browser download was replaced by cache content verified to match
the already deployed Chromium/Headless Shell/FFmpeg revisions.

Long steady-state memory behavior, fleet scale and the downstream saturation
point still need measurement. The existing native old-template deletion timeout
also remains a cleanup follow-up; its ownership records were retained.

Final original-machine inspection found a separate recovery defect: the background
creation path failed to persist a validated no-effect creation refusal, although
the initial provision path already did. A later recovery therefore treated the
allocation as uncertain. The repair reuses the existing absence field and fresh-
send validation; capsule adoption and recovery-time local errors cannot claim
absence. A replacement also clears the old allocation's in-memory absence flag.
The 66 controller and 31 real-PG state checks pass. Publication and restoration
of the two affected originals are still pending at this report checkpoint.
