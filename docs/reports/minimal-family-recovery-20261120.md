# 子 Conversation 的 Inbox 投影与恢复

[#52](https://github.com/cookerpapa/pi-managed-agents/issues/52) 的第一项修复已在性能分支实现。原型曾在 Inbox 创建时断言 Conversation ID 等于 1，写 PG 时也固定写 1。原生 Pi 按 Conversation 区分输入请求；旧原型在整个物理 Session 上唯一约束请求 ID，会拒绝父子 Conversation 使用相同请求号的合法输入。另一个问题是子会话消息和压缩标记可以改变根会话的历史计数和读取范围。

## 已验证的行为

同一个 Pi 原生事务可以同时修改多个 Inbox。PG 只保留每个 Conversation 当前的待发内容，同一批内重复改动保留最终序号和位置。状态和正文共同接受；任何一个队列非空都会保留该段尚未由检查点覆盖的后缀。已完成 Run 的根历史头只统计根消息；若根发生压缩，在其收尾事务内读取最新可见的根范围并更新统计。子 Conversation 压缩不会移动根的读取起点。

固定 Pi Harness 和本地模拟模型实际创建了父 Tool 拥有的子 Conversation。父 Tool 等待子会话完成，子 Tool 等待测试门闩。父子各收一条 follow-up，并在同一次原生提交里修改两条待发内容。此时有 4 个活跃原生 Task。销毁原型 Projector 的内存视图，用新的 Projector 从真实 PostgreSQL 读取检查点、重放捕获的 13 条后续记录后，两个队列分别找回自己的内容。随后分别放开等待，验证输入各放置一次、父子取得各自的工具结果，并检查子压缩、根压缩和下一 Run 打开时的 Inbox 可见范围。

这个测试重建的是 Projector。Pi Harness 在该用例里没有退出，两个工具是本地受控测试函数。另有原有真实 PG/RF3 恢复和原回包测试。它们不能合并当作一次“新 Worker 在新存储上接手正在 Cube 执行的子工具”的验收。

## Worker 冷恢复的决策点

后续已用独立 Worker 进程和真实 Cube 验证读取方案。[接手和 Kafka 保留期实验](retained-family-handoff-20261121.md)

实测根的 `pi.agent` 文档在这段受保护的 Projector 后缀之前已创建。现有 PG 检查点可以重建队列和投影视图，但正文和 Inbox 没有完整记录父任务等谁、子 Conversation 归哪个 Task 所有、每个 Task 当前执行到哪个阶段。Worker 仅从这个后缀启动无法还原完整原生会话。服务版已有相应的原生状态和回复接管能力，参见 [#21](https://github.com/cookerpapa/pi-managed-agents/issues/21)。

可以保留经提交的原生当前状态，或从可供 Worker 打开的稳定检查点加受保护的 Kafka 后缀恢复。前者需要测每次状态变化的额外写入，后者需要证明长 Run、日志保留边界、重放时间和原始副作用授权。原型的真实 Worker A → B 接手、沙箱执行唯一性、两个回包时序、Stop、迟到结果及 handoff P95 尚待验证。#53 的租约语义未作改动。

## 两个冒烟指标

在隔离 K3s 夹具上串行运行，使用已有三副本 Kafka 和临时 PostgreSQL。普通根会话的每档短 Run 共 520 个，每个 Run 带一个请求和一个模拟助手回答，模型无额外等待；每秒计划送入 260 个。最多 16 条同分区记录合批时，同步和选择性异步组分别完成 252.98 和 252.16 Run/s。新增的“最后一次模型输出完成 → PG 逻辑收尾”P95 分别是 32、36 ms。两组都完成了 520 个 Run。指标取自模拟服务商流的最终回复和 Projector 在提交成功后的确认，排除重放时没有模型请求的样本。

独立消息重放每档 32 个 Run、6,400 条计数消息，分子为完整的工具调用和结果，开头用户输入与最终回答只进入耗时分母。计划每秒送入 2,315 条时，可重放历史异步组实际约 2,297 条/秒；预装积压再排空约 3,005 条/秒。各组最终积压为 0。这里是单轮小样本，不能与更大批次的容量测量直接比较，也未测真实 Worker 接手后的吞吐或 P95。[逐档聚合数据](minimal-family-recovery-20261120.json)
