# Worker 批领、驻留容量与同会话优先领取

在本机原型中，常规批领上限从 8 提高到 32 降低了登记至领取的等待，再提高到 64 的收益取决于积压情况。单个实验进程同时容纳了 256 个等待模拟模型的 Pi 根会话。让续聊回到旧 Worker 可利用内存中的稳定历史，但当前生产代码会在上一个 Run 结束时关闭 Harness 和 Storage。[实验命令](../../scripts/experiments/minimal-session-storage/README.md) · [两轮逐组数字](worker-claim-sizing-20261119.json)

## 领取多少

每轮比较两组实际 Worker 进程。第一组由 128 个客户端持续补交，共 512 个 Run。第二组先将 256 个不同会话全部入队，再同时允许两个 Worker 连接领取。每个 Worker 最多有 128 个执行位。批量上限按 8、16、32、64 和逆序各跑一遍。整项实验独立做了两轮，表中是每种配置四个样本的范围。每个 Run 都执行真实 Pi，使用不加延迟的本地模型，并经三副本 Kafka 投影到 PG。16 个批量场景和 6 个驻留场景每轮合计 7,040 个 Run，全部完成，终态核验时 Kafka 积压为零。

| 每批上限 | 持续补交时，PG 登记至领取 P95 | 已积压 256 个 Run，实际领取 SQL 次数 | 积压场景，PG 登记至领取 P95 |
|---|---:|---:|---:|
| 8 | 64–104 ms | 39–42 | 196–277 ms |
| 16 | 50–53 ms | 23 | 115–130 ms |
| 32 | 41–54 ms | 15 | 115–165 ms |
| 64 | 43–67 ms | 11 | 117–139 ms |

登记至领取取 PG 行创建至原子改为 running 的同一数据库时钟。积压组包含等所有输入登记和管理连接就绪的时间。查询数是实际发出的领取语句，包含空查。四组使用相同的 5 ms 合并窗口与 200 ms 定向补问。常规配置选 32 时，一台只空 3 个位的 Worker 仍只申请 3 个。长期有积压的池可试 64，关注最老任务的等待和各 Worker 的分布。

## 同时跑多少

只启用一台实验 Worker。每个根会话有独立的 32 KiB 随机文本输入。模型回调核对收到的文本长度，等所有指定会话同时到达才统一释放。64 和 128 个会话共同等待 2 秒，256 个共同等待 10 秒。每个档位两轮累计四个样本。每条回答都经过 Pi、Kafka 和 PG，结束后逐条验证。

| 同一进程内实测同时等待的模型请求 | 进程峰值 RSS | 进程事件循环延迟 P99 |
|---|---:|---:|
| 64 | 356–407 MiB | 10.8–14.4 ms |
| 128 | 369–407 MiB | 12.0–25.8 ms |
| 256 | 371–405 MiB | 12.2–27.8 ms |

这是已预热的 Node 进程。不同阶段共享 V8 已分配的内存，RSS 范围不可用于反推单会话固定占用。测试 Pod 的资源请求为 250m CPU 与 384 MiB 内存，未设 CPU 或内存硬上限。长历史、图片、多步活跃计算、并发子 Agent、真实服务商配额和长时间内存增长都需要另测。生产容量按活跃物理 Session 计，子 Conversation 共用家族槽位，模型请求有独立并发控制。建议把 128 个根会话作为下一轮生产形态压测的起点。[运行时容量语义](../RUN_LIFECYCLE.md#claim-and-execution-ownership)

## 优先回到有缓存的 Worker

生产的本地 owner 键包括租户、物理 Session、租约 ID 和 fencing 代数。最后一个 handle 释放时会关闭 Harness、Storage 及授权，并移除 owner。同一进程再次领到这个会话，仍要用新授权重新打开。网关侧的模型续传缓存独立于 Worker。[Session host](../../packages/pi-session-postgres/src/durable/session-host.ts) · [模型续传设计](../adr/0289-provider-owned-model-continuation.md)

本次分别测了两段成本，没有改变生产调度或实现完整跨 Run 缓存。

1. **领取开销。** 在 8,192 个根 Run 的轻量队列中，8 个并发领取者各竞争同一个 FIFO，每批 16 条，每组共 192 次独立提交。优先查询用主键及租户、队头资格检查尝试一个指定 Run，其余位置从普通 FIFO 补齐。给出已经运行的旧 ID 时仍能领满普通任务。测试也核对了优先 ID 无法越过已加锁或正在运行的同会话前序 Run。普通领取 SQL 的中位耗时在第一轮为 6.2–6.7 ms，优先命中为 8.7–9.0 ms。第二轮分别为 8.6–9.0 ms 和 12.0–14.6 ms，旧 ID 未命中为 12.2–12.7 ms。每个数字计入客户端到 PG 的一次往返。没有缓存线索的批次可以完全沿用原 SQL。
2. **读历史的收益。** 在简化存储中冻结上一个 Run 的 128 条文本 Entry。两组都从 PG 核对所属会话、已经完成的前序 Run 和最新用户输入，每次新建原生 Pi Harness 组装上下文并验证结果相同。冷读路径从 PG 取回正文并解析，命中路径复用已解析的只读 Entry。64 KiB 历史的中位耗时为 3.13 → 1.60 ms，4 MiB 为 41.79 → 1.96 ms。每组测 12 次，另验证编辑下一轮输入后仍取得最新文本。时延覆盖该段读取与原生上下文构建，不含模型首字、任务恢复和服务商传输。

建议先让唤醒端优先通知仍在线、已举手且持有有效前缀的 Worker。普通队列始终开放，旧 Worker 已满或缓存被逐出时立即走 FIFO。通知当前只携带批量提示，单改唤醒顺序在积压时无法保证指定 Run 一定被这台 Worker 取到。若需要更高命中率，可仅对有价值的命中线索携带一个具体 Run ID。每个新 Run 正常领取新租约，按租户、会话分支和已确认的历史版本校验缓存，重新读取新输入、可变任务和本轮配置。实验里冻结单个前序 Run 的判定不足以覆盖生产的裁剪、分叉和压缩，需要在接入前验证失效与冷读回退。缓存应有字节预算并可随时逐出，不占执行槽。[Temporal 的工作流缓存与 Sticky Execution](https://docs.temporal.io/workflow-execution#workflow-cache)
