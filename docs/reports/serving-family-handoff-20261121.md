# #52 · 从 Session API 提交到子会话恢复

这次把最小存储原型接到正式的 HTTP API、Run 领取、PG 续租、过期扫描、Outbox 和 Session Projector。每个场景有一台独立的 Cube VM。子 Agent 的 Bash 在 VM 中写下一行标记，等待放行，再读出 VM 内随机生成的值。判断恢复是否成功要同时检查物理标记、子会话的原生结果、父模型实际收到的上下文，以及网页使用的会话历史接口。

## 交接经过

1. HTTP 接受用户输入。A 通过 RunExecutor 领取 Run，持有唯一的物理 Session 租约。父 Pi 调用研究用的委派工具。控制侧的 PostgresSubagentConversations 根据已投影的父任务创建子会话视图，子 Pi 和父 Pi 共享 A 的租约。
2. Guest 已执行 Bash，子 Inbox 中的 follow-up 已投影。此时杀掉 A 的 Node 进程。实验将租约设为 12 秒，每 3 秒续一次。PG 时钟自然到期后，SessionExpiryReconciler 申请封口。正式 Outbox 和 Projector 将封口写入 Kafka，确认后重新开放同一个 Run。实验核对了旧租约的释放时间、封口位置和 Outbox 的发布状态。
3. B 通过同一个领取入口取得新身份。其冷读取连接使用单独的只读 PG 角色，只能读取原型正文、Inbox、分区位置和指定的 Run 字段。正式服务的原生任务表未授权给这个角色。B 从已确认的旧封口确定读取上界，在 Kafka 中恢复任务树、原操作的沙箱绑定、原 writer、原回包 Topic 和截止时间，重新挂上 waiter。
4. 在等待期间点 Stop 的场景，HTTP 先持久化取消请求，B 领取时读到 stopOnResume。RunCancellationExecutor 确认这次请求确实属于 B，再调用 Pi 的中止接口。工具取消经过 Session Kafka 和 Projector，Guest 收到的仍是 A 启动的那个操作的身份。
5. 超时场景将原 waiter 的截止时间缩短到 18 秒，单独延长测试用 Guest 投递凭据，使迟到的真实回包仍可观察。B 注册探针 waiter 后，探针经过 Session Kafka、Projector、同一 Guest、HTTPS completion 和 B 的回包邮箱。探针成功后，Pi 可以把原命令的未知结果交给模型。原命令的最终输出在 Run 收尾后才放行。

## 同一工作负载的五种时序

每种各跑一次，串行执行。下表中的冷读从 B 开始读取本 Run 的前缀算起，到恢复旧回包邮箱为止。最后一列从父模型完成最终输出算到服务版终态投影和候选位置均已确认。

| 时序 | Run 终态 | 沙箱执行次数 | 杀掉 A 至封口 | B 冷读与挂回邮箱 | 最终输出至投影 |
|---|---|---:|---:|---:|---:|
| 全程由 A 执行 | completed | 1 | — | — | 308 ms |
| B 恢复后才回包 | completed | 1 | 10.53 s | 7.23 s | 268 ms |
| B 接手前已有两份相同回包 | completed | 1 | 10.81 s | 7.24 s | 275 ms |
| 原截止时间已过，最后才放行真实回包 | completed | 1 | 10.33 s | 6.23 s | 350 ms |
| 封口后、B 领取前点 Stop | cancelled | 1 | 10.23 s | 7.27 s | — |

每例均有一个根 Run、一个原生子会话、一个 Bash 和一条子 follow-up。两种正常回包次序都产生一个最终 Bash 结果，父模型都读到了 Guest 的随机值。超时后子页面的 Bash 状态为 unknown，父模型可见该结果，随后收到的随机值没有覆盖它。Stop 的确认与完成时间均已记录，新 Worker 新增模型调用数为零，原生子 Submission 最终为 unanswered。这个子输入由测试直接提交给 Pi，网页输入框取回草稿的交互没有纳入测量。

B 每次读取 19 次已接受的原生提交。最后一例扫描了 202 条可见分区记录，其中 182 条与本 Run 无关。实验读取器从分区当前保留的起点开始，分区变长会增加扫描量。Projector 的投影游标和工具回包的保护位置分别有自己的用途，两者都不足以自动确定这一段原生任务状态的起点。压缩祖先、历史已结束子分支、多次接手，以及分区放大后的耗时，仍需在 #52 对照测量。

每种时序样本量为 1。此表只用于复现功能和定位等待，不能据此估计 P95、单独归因于候选存储或外推吞吐。

## 联调发现

原型的 PG 写入条件只认 running。接入正式取消确认后，Run 在合法 Worker 写完中止结果前已进入 cancel_requested。复现中第 21 次原生提交被当成过期，读到第 22 次时原型报序号断裂。现在同一租约在取消收尾期间仍可保存原生记录、更新 Inbox、解除原操作的等待引用。新执行意图可以作为历史保存，PG 在同一个已锁住 Run 的事务中抑制派发；重放也核对当前状态。旧租约、已结束 Run 的保护继续生效。这个修正只涉及实验分支的原型。

另一处差异出在实验 Worker。第一版只写原生正文，没有带子会话的展示序号，导致正式子页面历史接口读工具时返回 400。实验现在使用服务端对应的 Worker 文字与工具展示逻辑，并从已接受的记录恢复各分支的序号。测试实际解析了父、子两个 HTTP 响应。

取消调度的另一次复跑中，已存在的请求第一次领取返回了 idle。这条查询使用 SKIP LOCKED；单次返回空不能判断请求丢失。实验 Worker 现按服务版的行为重新检查尚待领取的请求，并要求同一请求的确认和完成记录都落入 PG。

## 实验边界

Session Kafka、控制 PG、Session HTTP 服务和控制 Projector 都是临时实例。Session 日志使用正式 Projector 的保留配置，按七天轮转和缺失前缀的验证见[上一组实验](retained-family-handoff-20261121.md)。原工具回包和探针使用已安装的 Guest 与 HTTPS completion，在开发集群建立本次独占的回包 Topic。运行结束后核实 Guest 物理删除，并清理回包 Topic、消费组、隔离 PG 和 Kafka。

这一轮侧重故障行为。同一条被接受的原生提交先经过服务版投影，再交给候选投影以供 B 冷读。Run 状态、租约和封口只有正式控制链路可以修改。终态的浏览器查询走服务版现有读路径。实验直接复用服务版取消收尾；原型单独运行时仍只有正常完成的收尾 SQL。两个投影在本实验分两次事务执行，不能用本次结果证明切换到单一新存储时的事务原子性。父子模型为本地确定性模型，控制器到 Worker 的测试管理调用通过进程间消息传递，沙箱由夹具分配。完整的产品工具选择、资源池调度和浏览器 DOM 均不在这组验证内。

原有四个 Guest 恢复场景重新通过，其中包括仍活跃的原生创建记录已轮转时安全拒绝接手。29 项原型辅助测试和 21 项隔离 PG/Kafka 集成测试全部通过。最终五例使用 Worker 注册时的真实 boot ID 命名各自邮箱，并断言其与 Session lease ID 不同。复核时，带实验标签的存活 VM 和本地临时 PG/Kafka 容器均为零。先前复跑偶尔记录了通用 consumer.failed，随后消费继续；日志缺少消费者身份，无法据此定位具体客户端。最终这一轮没有出现该事件。
