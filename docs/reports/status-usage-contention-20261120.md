# 上下文状态、网关用量与 PostgreSQL 争用

本次在性能分支实现输入型命令与对应的 Session API/SDK。输入 `/status` 查看当前 Conversation 的估算已用量、模型窗口和压缩阈值；输入 `/usage` 查看自创建以来 CLIProxyAPI 回执中的累计输入、缓存、输出和总量。缓存是输入的子集，推理输出包含在输出中。页面支持按需刷新和计入可见子 Agent。缺少完整回执的已知请求单独显示，收到迟到的完整回执后重新查询即可更新。费用资格、压缩阈值和原生文档恢复保留既有各自的证据来源。公开命令独立读取，只读、无支付、无模型或沙箱调用。

## 测量

隔离 PostgreSQL 17.6 容器，2 vCPU、768 MiB。单个投影连接处理 64 批，每批 16 条约 4 KiB 工具调用或结果，来自 16 个 Session；每轮 1,024 条。并写组另用一个连接，512 个请求各产生 started、attempt、usage、finished 四条回执，按每批 32 条递交。预生成输入后同时启动两路，分别从开始计时到各自完成。每种布局预热后测 6 次，轮换顺序。轮末逐会话核对正文、累计状态和回执行数；用归档 SQL 复测时还通过产品的计量读取函数验证 16 个会话各有 4,096 tokens。所有实例和测试数据在结束时清理。

同库使用两套业务表；同实例分库把原始回执放到另一个逻辑数据库。后者仍共享 CPU、缓存、WAL 和存储设备。以下是 PG 投影用时中位数（毫秒），收集代码不等待 Projector 的返回；两条链路可能因共用资源而减速。

| 固定正文投影，不含执行结算 | 只做投影 | 同数据库并写 | 同实例分库并写 |
|---|---:|---:|---:|
| #49 源端直接 SQL | 902 | 924 | 917 |
| 同一份直接写入 SQL，独立复测 | 1,070 | 1,202 | 1,094 |
| 性能分支已有的计量接收器路径 | 852 | 884 | 861 |

两次直接写入同库的正文处理用时分别多约 2.5%、12.4%。这些是短时固定负载结果，包含客户端和服务器的时间。SQL 对照使用项目当前 #49 源迁移中的实际写入函数、真实数据库驱动、索引和事务，输入为合成网关回执。新命令和受控 DB 路径分别验收；压力测量没有接入真实模型请求、网关 HTTP/本地持久队列、Kafka 调度、多个 Projector 或后台计价服务。

## 同一请求的执行结算

另做 18 轮，保留上述输入和两路独立连接，把 512 次模型执行逐一和相应的助手消息绑定。每笔正文事务也调用现有 `ModelExecutionAccounting.settle` 写入相应请求的接受证据，并使用同步提交。网关按相同 invocation ID 和真实源函数写入各次回执，模拟同一请求归属。每轮都验证 512 条 execution 记录、1,024 条消息，并写组另验证 2,048 条源回执和命令读取的 token 总数。控制组也付出执行结算开销。微实验将同批独立请求按 invocation ID 取得锁，不包括正式 Kafka 分区调度及全部原生文档。

| 包含执行结算的 PG 路径 | 投影完成中位数 | 相对只做投影 |
|---|---:|---:|
| 只做投影及结算 | 1,944 ms | 基线 |
| CLIProxyAPI 同库并写回执 | 2,277 ms | +17.1% |
| 同实例分库并写回执 | 2,248 ms | +15.6% |

拆成同实例两个库，两路仍争抢底层资源，且原本同库的财务关联查询不能直接跨库完成。同库组与分库组的中位数相差约 29 ms，样本有波动。若未来监控持续显示资源饱和，再区分 CPU、WAL/磁盘、连接池及 invocation 行锁等待。独立实例且独立资源预算才提供更强的隔离。保留会话库内与原生状态共同提交的执行证据，另为计量侧设计可靠对账，然后才有充分依据做物理拆分。

## 正确性与范围

用真实 PG 测试聚合时，覆盖独立 Session、租户、子 Agent、请求重试、重复投递、迟到和不完整回执、缓存与推理计数。查询直接使用 execution ID 已去重的源表，完整重试消耗保留；公开用量与应计费数量的定义独立。对当前开发库做只读比对，计量读取函数与一份真实已归档回执集合的独立求和一致；当时没有可见并带完整回执的业务会话供新页面在线验收。

生产数据和部署未改动。本次提供真实项目的 Web、SDK 和 Session API 命令；纯最小存储负载夹具本身还不是可独立上线的完整服务。此次命令拆分也没有删除原生 Pi 的冷恢复数据。
