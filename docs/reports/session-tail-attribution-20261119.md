# 一条结束记录在何处等待

普通新会话的秒级长尾主要发生在 Kafka 已经接到结束消息、Projector 的 Node 进程还在逐条从原生客户端取消息的时候。投影工作也会产生另一种排队。当消费端把数据交给 JavaScript 的速度提高后，32 个分区可以同时争用 12 条 PG 连接，每个分区仍按 offset 等前一条处理完。两种等待在不同的速率和主机状态下占比不同。这次只做了诊断，没有发布读批量和调度策略变动。[逐组证据](session-tail-attribution-20261119.json) · [实际 SQL](session-projector-statements-20261119.sql)

## 在原来的 160 Run/s 下复现

原来的一分钟试验中，提交至领取 P95 为 37 ms，终态记录从产生至进入处理函数 P95 为 2,676 ms，进入后的处理 P95 为 13.21 ms。该轮 9,257 个已接纳的 Run 中，消息写入的 PG 客户端调用最大 46.38 ms，终态更新最大 25.99 ms。积压最高的采样点有 2,534 个 Kafka offset 尚未处理，JS 本地等待队列为 154，PG 连接池等待数为 0，PG 有 2 个 Run 等领取。这些是原始观测，不能通过相减几个独立 P95 来拆解一条真实 Run。

在相同负载、同样逐条取数和完整投影下再跑 90 秒。这次为每条私有 Topic 记录的原生回调及处理入口打点，并同时观察 Worker 的生产确认。13,007 个已发出的请求全部完成，另外 1,393 个计划请求因生成器的 384 个在途名额占满而没有发出。下表各行来自**同一条**耗时恰在端到端 P95 的 Run。

| 先后经过的阶段 | 耗时 |
|---|---:|
| 用户提交 → Worker 确认领到 | 29 ms |
| 领取 → Worker 产生结束记录，含模拟模型和前面的原生提交 | 107 ms |
| 产生结束记录 → Kafka 原生客户端回调把记录交给 JS | 3,409 ms |
| 回调交付 → 轮到本分区处理这条结束记录 | 14 ms |
| 进入处理函数 → 收到 PG 终态提交确认 | 12 ms |

总计为 3,572 ms，分项显示到整数毫秒。这条记录在 Worker 看到生产 ACK 后，仍等了 3,400 ms 才交给 JS。ACK 可能与消费重叠，因此没有将 ACK 时间作为额外一段叠加。按端到端延迟选出的最慢 651 个 Run，平均总耗时 8.53 秒，其中平均 8.03 秒在产生结束记录至原生消费回调之间，0.29 秒在 JS 回调之后等本分区，终态处理平均 9 ms。积压最高的采样点是 2,575 个 offset，本地等待 177 条，PG 池等待 0，待领取 Run 为 1。librdkafka 的分区 offset 统计中，已经取回但还未交付应用的差值之和最高为 1,601。

## 为什么读得慢，PG 在何时成为限制

一个普通单轮会话产生 6 条原生提交和 1 条独立终态。所以 160 Run/s 对应约 1,120 条 Kafka 记录/s。现有读循环只挂一个原生 `consume(1, callback)`，回调交付、分区交接和本轮轮询收尾后才发下一次。底层可以从 broker 成批预取，而 Node 应用在所有 32 个分区上共用这条取数循环。[读循环](../../packages/event-log/src/kafka-partition-reader.ts#L265)

保持原来的 SQL、分区顺序和确认逻辑，以 260 Run/s 在一个阶段中每 4 秒切换取数上限，用 1、32、32、1 循环。中间的第 3–14 号窗口每档各 6 个。逐条取时平均交给 JS 619 条记录/s，上限 32 时为 1,318 条/s。三次从逐条切到批量时，原生已取回但未交付的差值在切换前最后一个半秒采样分别为 1,554、983、940，切换后都回到个位数或零。批量仅等待第一条到来，随后带上当前可用记录。即使在同一个进程内，记录交付变快也不会让同一分区内的业务处理并行。

在主机校准相近的独立慢窗口里，这两种排队分别表现为：

| 260 Run/s 的诊断对照 | 应用逐条取，完整投影 | 每次最多取 32 条，完整投影 |
|---|---:|---:|
| 端到端 P95 | 6,544 ms | 3,810 ms |
| P95 那条 Run 的结束记录，产生至交给 JS | 6,126 ms | 58 ms |
| 同一记录，交给 JS 至进入处理函数 | 92 ms | 3,412 ms |
| 同一记录，自身终态处理 | 10 ms | 45 ms |
| 阶段内 JS 队列峰值 | 498 | 2,232 |
| 阶段内 PG 连接池等待数峰值 | 0 | 20 |

对右列这个 Run，3,412 ms 本地等待中，约 1,982 ms 与**同分区前序处理**领取 PG 连接重叠，约 1,361 ms 与它们的 PG 调用至回调重叠。约 3,212 ms 的前序处理属于其他 Session。这里“属于谁”和“在等待什么”是同一组区间的两种统计方式。独立诊断只写终态、跳过消息与 Inbox 时，慢窗口中逐条取的 P95 仍有 5.48 秒，每次最多 32 条时为 0.59 秒。省略历史的对照不能当作可用聊天系统的吞吐。较快窗口里 260/s 两种真实投影都通过，P95 分别为 105 和 99 ms。主机哈希校准显示可用处理速度会变化，此实验未识别物理层变慢的原因。

## 续聊为什么会等在领取之前

续聊还会把前序终态的等待传回领取入口。另做两组起始历史 512 KiB 的测试。140/s 的较快窗口中，8,400 个 Run 都完成，终态 P95 为 92 ms，没有后继在登记时被未完成的前序阻挡。在 220/s 的超载窗口中，已接纳的 2,941 个 Run 全部完成，其中 2,516 个登记时前序还没结束。按 PG 行创建至领取排在 P95 的一条记录等了 6,237 ms。用它的同一物理 Session 队列位置找到紧前一条 Run 的真实 PG 完成时间，6,183 ms 在等前序完成，具备领取资格后花了 54 ms。不能把整段都算给领取查询，或都算给前一条终态 UPDATE。这些区间还可能包含前序 Run 自身等待更早一轮、执行和投影的时间。

## PG 实际写了什么

新会话的一问一答共 7 条 Kafka 记录，默认单语句投影有 **4 次 Projector 侧 SQL 往返**。首次创建当前 Inbox 一次，用户与最终助手 Entry 各一次，独立的 `work_finished` 更新 Run 一次。另外两条原生状态提交和一条纯 live 提交在这一原型中都不写 PG。普通续聊复用已有空 Inbox，少一次创建，开头多一次读前序稳定版本与 Inbox，合计同样是 4 次。以上计数不含 API 登记、Worker 领取或读历史。包含待发输入取用等复合变更时，Inbox 移除和正式用户消息要放在同一个显式事务中。

- `pma_message` 先按租户、物理 Session、Run 和领取 UUID 检查当前 running 行并加 `FOR SHARE`。然后将绑定的 Entry 数组拆行，写入正文、角色、来源输入、提交序号及批内顺序。冲突键为租户、物理 Session、Entry ID。已有行的载荷及位置完全一致时可返回相同 Entry ID，内容冲突时返回零行，调用方拒绝冲突。整条 CTE 只有一次数据库往返。
- `pma_inbox` 复用同样的写入身份检查，将完整的最新 items 写回同一行。重复键只接受同一文档且更新位置严格递增。检查的是已登记的 Run 写入身份，没有逐消息去查 Worker 心跳或租约到期表。
- `pma_finish` 用一次有条件的 UPDATE 将 Run 设为 completed，并保存完成时间与稳定历史头。历史头包含版本、原生 seq、下一个 ID、有效历史起点、条目数和字节数。普通回答直接使用 Projector 已经汇总出的值。有效历史起点发生变化时才另外汇总新范围。

从抽样 PG 连接实际捕获了这三条写入 SQL。第四条续聊开头的 SELECT 从原型执行代码取出。已逐一核对[完整 SQL 及参数表](session-projector-statements-20261119.sql)，在仅含临时表的事务内准备并执行，验证重复、冲突、过期身份及后继读取。在包含 8,192 个其他 Run 的临时样本中，三条写语句的 Run 定位均使用 `runs_one_active` 索引，消息使用原有唯一键处理冲突。空载执行计划不代表带载延迟。

复现 160/s 时，将一个抽样后端记录的 PG Parse/Bind/Execute 耗时与客户端查询按 PID 和毫秒窗口关联。1,972 个客户端样本中，1,705 个可以唯一匹配到完整的三项服务端耗时。下表的客户端和服务端分别在同一组匹配样本上计算 P95。

| SQL | 成功匹配的样本数 | PG 服务端三段耗时 P95 | Projector 调用至回调 P95 |
|---|---:|---:|---:|
| Inbox | 451 | 3.62 ms | 18.16 ms |
| 消息写入 | 863 | 6.11 ms | 20.46 ms |
| Run 终态更新 | 391 | 2.01 ms | 16.03 ms |

客户端区间包含连接上的往返、事务同步以及 Node 得到执行机会之前的等待。协议日志没有单独量出隐式提交的 WAL 刷盘或网络时间。这里不能把两列相减解释成某一项。诊断使用同一台 WSL/K3s 上的两个 Worker、一个 Projector 和独立实验库及 Topic，记录完整性通过原有核验。未改生产配置、应用读循环或 SQL。
