# #52 · 单个 Projector 投影工具密集型 Run 的吞吐量

## 一次 Run 实际产生什么

在单机开发 K3s 中使用一个原型 Projector、32 个分区的三副本 Kafka、PG 17.6 和 12 条 Projector PG 连接。128 个独立会话、128 个热绑定模拟沙箱。每个 Run 接收一条用户输入，依次调用 200 次 Bash，产生 200 个不同操作编号和 200 个 1,024 字节结果。固定 Pi 的 32,768 token 测试窗口自然触发一次压缩，之后正常生成最终回答并发送完成信号。专用假模型应答压缩与工具请求，工具结果按调用编号确定。执行侧向独立 WebSocket 端点派发，模拟端延迟 100 ms 返回接单确认。该测试测 Projector 在投影、展示和热路由派发下的能力，未计真实模型、实际 shell 或沙箱冷启动。

| 每个 Run 的单位 | 数量 |
|---|---:|
| 实际工具调用及对应结果 | 200 对 |
| 完整调用消息与结果消息 | 400 条 |
| PG 正文表全部原生 Entry | 405 条，含调用与结果，以及首条输入、2 条系统消息、1 条压缩和 1 条最终回答 |
| Kafka Session 日志记录 | 1,812 条，含原生状态变化和 Run 收尾 |

每轮共 25,600 对工具、51,200 条调用/结果、51,840 条历史和 231,936 条 Kafka 记录。工具对占历史正文的 98.8%。平均一次工具调用及其结果在这份完整流中对应约 9.06 条 Kafka 记录。

在线组直接在 Pi Storage 提交时等待真实 Kafka 确认，Projector 同时处理。定速组和预装组重放同一份消息的相同字节、身份与分区内顺序。没有改变投影持久性、展示及外部派发许可规则。各轮均核对全部 PG Entry 分类、每个 Run 的 200 个工具调用编号和有序结果、结果长度、等待引用清空、正常完成行、模拟端接单、网页开始展示及 Kafka 位点。速率的分母从放行到 Projector 处理最后一条记录，包含等待 PG、派发许可与发送能力的时间。预装组的生产耗时单独排除。

## 读数口径

- “Kafka 记录/秒”是已完成 Projector 处理的记录数除以整个窗口耗时。目标输入速率、生产者实际确认速率和 Projector 处理速率各自计量。
- “完整历史条/秒”以 PG 中已核对的 51,840 条原生 Entry 为分子；“调用与结果条/秒”只数其中 51,200 条。一调用配一结果称作一对，分子为 25,600。
- 均匀输入用约半秒一次的分区积压采样，比较投入窗口 25%、50%、75% 和生产完成附近。末尾还要多久才能追上另行计时。预装组从放行起算，此时 Kafka 中已存好整份记录。
- 本轮每次模型工具响应只提出一个调用。每个 Run 200 次调用后，全天 100 万 Run 的平均需求约为 2,315 次调用/秒、4,630 条调用/结果消息/秒。按本样本的提交形状，对应约 20,972 条 Kafka 记录/秒，PG 全部历史约 4,688 条/秒。
## 实测

| 方式 / 计划记录每秒 | 实际生产记录/秒 | Projector 处理记录/秒 | 全部完整历史条/秒 | 其中调用与结果条/秒 | 工具对/秒 | 输入结束后追平 |
|---|---:|---:|---:|---:|---:|---:|
| Pi 在线运行 | 2,212 | 2,215 | 495 | 489 | 244 | 源端汇总确认时已追平 |
| 定速 2,500 | 2,497 | 2,474 | 553 | 546 | 273 | 0.86 秒 |
| 定速 3,500，两轮 | 3,494 / 3,495 | 3,435 / 3,435 | 768 / 768 | 758 / 758 | 379 / 379 | 1.14 / 1.15 秒 |
| 定速 4,600 | 4,590 | 4,389 | 981 | 969 | 484 | 2.31 秒 |
| 定速 6,500 | 6,480 | 3,789 | 847 | 836 | 418 | 25.42 秒 |
| 一次预装全部记录 | — | 3,978 | 889 | 878 | 439 | 放行后 58.30 秒处理完 |

- 在 3,500 档，投入窗口前三个采样点的总积压分别为 48/58/48 和 27/45/40 条；结束附近为 958 和 905。两轮均用约 67.5 秒处理完 231,936 条记录。主体期间能紧跟输入，末尾少数会话收尾仍需约一秒。
- 在 4,600 档，投入窗口四个采样点为 394/53/409/2,215 条；峰值 2,426。主体期间积压能回落，结束时仍需追赶。该档只测一轮。
- 在 6,500 档，总积压依次为 21,389/40,300/57,035/73,946 条，停发后才逐步追平。这一档已经过载。预装一组让现有的 128 条发送连接同时处理积压，与有并发生产者的定速工况不同。这里记录实测下降，没有把原因单独归给 PG、CPU 或网络。
- 该负载确实包含同步和异步 PG 投影。在定速 4,600 的一轮，共有 127,681 笔投影事务，其中 75,713 笔同步、51,968 笔异步。较早的[完整消息容量测试](complete-message-capacity-20261120.md)写入的是可批投影的历史记录，当时没有实际可派发的命令和接单确认。

在本机实测范围内，3,500 条 Kafka 输入/秒是两次重复得到的参考点；4,600 已有可见收尾积压，6,500 出现持续积压。按这台机器每秒处理约 379～484 对工具、每个 Run 200 次工具换算，距每天百万 Run 所需的平均工具吞吐仍差约 4.8～6.1 倍，尚未计流量峰值。数据来自单机短时实验；未测多 Projector 扩容、长时间持续运行、真实公网设备、图片或大结果，也没有从单机数字外推需要多少实例。

所有七轮均核对 128 个终态、完整消息、工具引用和分区进度，最终 Kafka 积压为零。临时 Topic、消费组、测试数据库和 Pod 完成清理。[复现步骤](../../scripts/experiments/minimal-session-storage/README.md#tool-dominated-run-throughput)

## 每天百万 Run、每个 Run 20 次工具调用

同一实验配置下，把每个 Run 改为 20 次顺序 Bash；每轮 1,024 个会话，共有 20,480 次工具调用，结果大小仍为每次 1 KiB。样本没有触发压缩，每个 Run 实际生成 187 条 Kafka 记录、43 条 PG 正文，其中 40 条为工具调用或结果。这里将 20 次作为待评估的负载假设。

每天 100 万个 Run 的平均需求是 11.57 Run/秒、231.48 对工具/秒、462.96 条调用或结果消息/秒。按实际提交形状，输入 Projector 的 Session Kafka 日志约 2,164.35 条/秒。每轮实发 191,488 条记录。初始 Run 行和沙箱路由提前准备好；在线组保留真实 Pi 提交顺序，等待 Kafka 确认。各定速组重放同一份捕获，验证每个 Run 的 20 对操作、正式结果、原始顺序和完成状态。每轮结束核对各个 Kafka 分区的最终位点。

Kafka 读取与 PG 事务的批量大小各自决定。读取器空闲时先等一条，有积压时每次最多取 32 条，再按分区顺序处理。该原型可将同分区连续的纯历史 Entry 提交合并写 PG（此配置最多 16 条）；符合条件、热路由已知且目标不同的普通工具意图，上限 8 条。输入确认、取消、封口等顺序边界结束当前批次。仅含流式进度的增量在内存应用，恢复依赖 Kafka 后缀和必要的 PG 检查点；不为每个增量在 PG 正文表插一条消息。

| 负载 | 实际输入 Kafka 记录/秒 | Projector 处理记录/秒 | 整轮完成 Run/秒 | 积压峰值（记录） | 生产完成后追平 |
|---|---:|---:|---:|---:|---:|
| Pi 生成并等待 Kafka 确认 | 3,329 | 3,334 | 17.83 | 253 | 源端汇总确认时已追平 |
| 日均 1 倍，两轮 | 2,162 / 2,162 | 2,154 / 2,154 | 11.52 / 11.52 | 96 / 73 | 0.33 / 0.32 秒 |
| 日均 1.5 倍 | 3,242 | 3,219 | 17.22 | 885 | 0.42 秒 |
| 日均 2 倍 | 4,321 | 4,259 | 22.78 | 1,773 | 0.64 秒 |
| 日均 3 倍 | 6,479 | 3,812 | 20.38 | 68,838 | 20.68 秒 |

日均档的两轮各约 89 秒。输入窗口 25%/50%/75% 时总积压为 21/18/10 和 13/15/19 条。每轮 20,480 个工具意图中，仅 1,211 和 1,221 个与其他意图共用 PG 事务，约 6%。两倍档输入过程中积压曾回落，最后能在一秒内清空。三倍档的四个积压采样点为 16,969/36,449/53,053/68,044 条，形成持续积压。全部六轮最终位点、工具顺序、回执和 PG 终态通过验收，临时资源已清理。

按本次结果，可以将单 Projector 的平均负载目标设为每天百万个 20 工具 Run。若把同样的工作集中到 8 小时，处理需求约为全天均值的三倍，该档已超过本机实测能力。测试窗口为短时，仍需单独验证生产模型网关并发、Worker 服务容量、真实沙箱池和长时间存储增长。[20 次工具的复现步骤](../../scripts/experiments/minimal-session-storage/README.md#one-million-runs-per-day-at-20-tools-per-run)
