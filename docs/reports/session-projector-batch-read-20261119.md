# Session Projector 批量读取与完整 Run 对照

Projector 可以用公开的客户端 API 及时交付单条消息，并在有积压时批量取数。固定积压的测试显示读取耗时下降。完整 Run 的对照里，轻载时两种方式非常接近。260 Run/s 下仍出现分区队列积压，端到端吞吐尚无稳定提升。本次变更位于性能分支。

## 读取和确认

Session Projector 空闲时向 Confluent 原生客户端等一条，收到就交给处理函数。接下来用公开 API 将轮询超时设为零，每次最多读取 32 条已有记录，一次没取满就恢复到等待一条的方式。每个分区仍按 offset 处理，一次运行一个处理函数。持久化、工具派发和进度确认沿用原有次序。回复消费者及其他角色使用原有轮询设置。

早期诊断试过 Confluent 1.10.1 的私有首条等待开关。核对上游实现和类型声明后，最终读取器采用公开的 `consume` 和 `setDefaultConsumeTimeout`。下表采用重新执行的公开 API 版本数据。

队列的全局高水位为 4,096 条或估算 32 MiB，单分区为 256 条或估算 4 MiB，包括正在处理的记录。一次回调可能带回超出剩余空间的消息。Projector 保存该分区第一条未入队记录的 offset，暂停取数，让已接下的记录处理完，再从那个 offset 读取。分区末尾的追平通知要等这些记录处理完，交接或显式 seek 会替换旧位置。这些临时位置只存在于内存。一次原生回调最多含 32 条，在 Worker 的 900 KiB 单条传输上限下，回调内的正文最多约 28.1 MiB，另外还有客户端和 JS 对象开销。队列的字节阈值仍最多超出一条已接纳记录的大小。[读取与确认约定](../adr/0331-bounded-partition-prefetch.md)

## 先测读取本身

三个真实 Kafka Broker、32 个分区、每分区 256 条预置记录，每条带 2 KiB 填充。每次从相同位置开始，逐条校验分区序号。处理函数不访问 PG，计时从首条处理开始，到最后一条结束。每组按逐条、批量、批量、逐条运行，第二组重新创建 Topic。

| 读完 8,192 条记录 | 第一组两次 | 第二组两次 | 四次中位数 |
|---|---:|---:|---:|
| 逐条 | 1,416 / 1,283 ms | 1,419 / 1,259 ms | 1,349 ms |
| 批量 | 1,061 / 163 ms | 189 / 192 ms | 190 ms |

这一段的中位耗时下降约 86%，批量版也出现过 1,061 ms 的慢样本。按 8,192 条记录和各自耗时计算的读取速率，逐条约为 5,772–6,505 条 Kafka 记录/秒，批量约为 7,720–50,196 条/秒。一个新会话的简单 Run 会产生 7 条记录，还有登记、执行和 PG 写入，因此完整 Run 另做对照。

## 再测完整 Run

同一台 WSL 主机的 K3s，两个 Worker，一个 Projector，32 个分区，Kafka RF3、minISR 2，直接使用当前检出的读取代码。每条请求都走 PG 登记、领取、Pi Harness、模型模拟器、完整消息投影和终态写入。模型不引入等待，生成 4 KiB 的回复。每一轮先以 160 Run/s 提交 25 秒，再以 260 Run/s 提交 25 秒。只切换实际读取器的逐条或批量选项。Projector 使用 12 条 PG 连接，监测代码不改写本次的取数条数。

| 顺序 | 读取 | 目标 Run/s | 发出并完成 / 计划 | 完成 Run/s | 提交至终态 P95 | Kafka 峰值待处理 offset | 提交窗口结束后排空 |
|---|---|---:|---:|---:|---:|---:|---:|
| 1 | 逐条 | 160 | 4,000 / 4,000 | 159.69 | 85 ms | 38 | 54 ms |
| 2 | 逐条 | 260 | 6,500 / 6,500 | 259.25 | 96 ms | 41 | 75 ms |
| 3 | 批量 | 160 | 4,000 / 4,000 | 159.65 | 84 ms | 35 | 59 ms |
| 4 | 批量 | 260 | 6,500 / 6,500 | 259.35 | 96 ms | 39 | 66 ms |
| 5 | 批量 | 160 | 4,000 / 4,000 | 158.64 | 801 ms | 412 | 217 ms |
| 6 | 批量 | 260 | 5,612 / 6,500 | 223.92 | 3,193 ms | 2,226 | 66 ms |
| 7 | 逐条 | 160 | 4,000 / 4,000 | 159.66 | 83 ms | 43 | 58 ms |
| 8 | 逐条 | 260 | 6,500 / 6,500 | 256.60 | 98 ms | 58 | 333 ms |

压测器最多同时等待 384 个请求。超过这个并发数时跳过当时计划发出的请求，表中分母包括这些请求。积压按各分区的 Kafka 高水位减去 Projector 已处理的下一位置求和，也包含已经进入 JS、尚未处理完的记录。所有实际发出的请求都通过了消息和终态一致性校验，各轮最终积压为零。主机执行速度随时间波动，25 秒窗口不足以把 260 Run/s 定为可持续容量。

另做两分钟混合负载。以 116 Run/s 交替提交新会话和在已有 512 KiB 历史上续聊的会话。计划的 13,920 个 Run 全部完成，端到端 P50 为 84 ms，P95 为 247 ms，P99 为 360 ms，最大值为 633 ms。Kafka 积压采样峰值为 54 条，提交窗口结束后 102 ms 排空。上述完整 Run 实验使用相同的 Projector 可执行脚本，SHA-256 为 `db01ba5f6ff7fd82f02588fce72d9c88ae52884531d0379fe704d9094c4a1968`。[原型复现命令](../../scripts/experiments/minimal-session-storage/README.md)

## 慢的一条记录具体等在哪里

前一次诊断曾测到已被 Kafka 确认的终态记录等待 3.4 秒才进入应用回调。本轮公开 API 版本在 260 Run/s 的较慢一轮，终态记录从产生到进入客户端回调的 P95 为 85 ms，进入回调后到轮到该分区处理为 2,816 ms。其他窗口中，逐条读取也能迅速交付终态记录，因此不能把不同窗口间的差额全归给代码改动。

取这一轮总延迟排在 P95 的**同一个 Run**。总耗时 3,193 ms，其中终态记录已到 JS，但在分区内等了 2,817 ms。这段时间里，前序处理等 PG 连接约 1,664 ms，持有连接从发 SQL 到收到回调约 1,092 ms。终态记录轮到自己后只处理了 33 ms。前序工作也来自其他 Session。这些观测区分了连接池等待和客户端 PG 调用区间，不能由此单独推出数据库执行、网络或 WAL 各花了多少时间。[上轮 SQL 与服务器时序](session-tail-attribution-20261119.md)

## 加倍 PG 连接的对照

固定实际批量读取，260 Run/s，28 秒，其他设定相同。在独立实验进程依次用 24、12、12、24 条连接。

| 连接数 | 完成 / 计划 | 完成 Run/s | 提交至终态 P95 | 连接池等待者采样峰值 |
|---:|---:|---:|---:|---:|
| 24 | 5,711 / 7,280 | 194.42 | 3,360 ms | 8 |
| 12 | 7,280 / 7,280 | 259.47 | 94 ms | 1 |
| 12 | 7,280 / 7,280 | 259.19 | 101 ms | 3 |
| 24 | 5,519 / 7,280 | 189.02 | 3,862 ms | 8 |

在上述四轮中扩大连接池没有取得收益。最后一轮里，分区前序工作等待连接的重叠时间 P95 为 664 ms，连接上的 PG 调用重叠时间 P95 为 2,502 ms。整机执行速度会波动，此表无法单独证明缩小连接池会在其他环境带来同样提升。原型保留默认的 12 条连接。下一项值得单独比较的是在保持分区顺序和输入确认边界的条件下，怎样减少前序稳定投影占用连接的时间。

## 工具确认和恢复

用同一版读取器在 RF3 的 32 个分区上重复提交模拟工具意图。每个分区负责自己的 offset，在观察到原生 commit 回调覆盖它之后才允许记录一次模拟派发，最后从 Broker 读取各分区保存的位置逐一核对。

- 让 32 个分区都准备好再同时请求确认。批量读取的两次测量各有 64 波，每波都是一次原生 offset commit。整波通过确认的 P95 分别为 13.17、13.35 ms。
- 取消同步屏障、让每个分区自然请求确认。批量版两轮都将 2,048 个工具意图合并成 68 次提交，逐条版分别为 104 和 103 次。八组测试都验证了确认先于模拟派发、分区顺序和最终位置。这里计时到派发许可，实际沙箱运行时长另计。
- 在仓库的 RF3 恢复测试中阻塞一个分区，验证另 31 个分区的工具均已获得 Broker 确认。随后释放阻塞、注入一次失败并核对重试结果。测试也覆盖了只剩事务结束标记的空闲分区、带缓存的分区交接，以及已经中止的 Kafka 事务。[真实分区与 EOF 测试](../../packages/event-log/test/prefetch.integration.test.ts) · [交接测试](../../packages/event-log/test/rolling-reader.integration.test.ts)

两包类型检查通过。Event Log 和 Runtime Core 常规套件通过 185 项，原型辅助检查通过 8 项，独立 RF3/PG 传输套件通过 13 项。负载发生在独立 Topic、消费组和临时数据库中，测试结束后均已核对清理。完整 Pi 服务仍按原定计划等待存储与发布决策。
