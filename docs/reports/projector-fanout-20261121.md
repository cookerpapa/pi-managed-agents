# #52 · 一个 Projector 向 4,000 个沙箱目标分发工具

## 负载和验收

每秒计划发出 4,600 条完整工具执行意图，均匀轮转到 4,000 个逻辑沙箱，每台目标每秒约
1.15 次。每个目标对应一个已登记的物理 Session、一个活跃 Run 和一条独立的持久 WebSocket
连接。每个 Kafka 分区承载 125 个目标。运行在独立进程中的模拟器仅核对命令并返回接单回执。
网络经过 K3s Pod 网络。所有连接使用同一接收 Pod，不做真实远程 TLS、设备重连、Bash 执行或模型调用。

预热阶段完成连接建立、PG Run 登记、初始原生提交和路由加载。正式路径每条消息运行 #52
的解码、执行路由、真实 PG 待回包记录投影及 Kafka 派发位置确认。两个模式都先获得 Kafka
许可才向目标发送。串行模式等远端回执才处理同分区的下一条记录。并发模式把后续回执放在
执行侧等待，同一目标同时最多发出一条。先预留名额再取得许可，默认全局 3,072 个名额，
每个预留 4 KiB。达到数量或字节上限时，新的操作在获得许可前等待。这个状态只属于隔离实验。

在接收端逐连接验证目标、操作 ID、命令次序和条数。每轮排空后，PG 中每个 Run 的操作
集合按原生任务号排序后核对摘要，再检查所有分区的消费组进度。只测试派发，每个操作的原回包
引用保留在候选 PG 存储，到试验清理时释放。该工作负载没有生成用户可见的最终工具结果。

## 真实投影和派发

下列各轮分别发出 8,000 条工具意图，每个目标两条。表内速率从预定发送开始计至收到最后一条回执，
包含积压排空时间。每条意图都有独立的 Kafka 派发许可。底层客户端可以把不同分区到达的
offset 请求合成一次提交，同一分区的下一条工具仍须等待上一次许可。

| 增加的回执延迟 | 当前逐条等待（次/秒） | 跨目标并发（次/秒） |
|---|---:|---:|
| 0 ms | 1,063 | 1,025 |
| 20 ms | 651 | 988 |
| 100 ms | 237 | 920 |
| 500 ms | 59 | 911 |

这组短轮的生产端实际 Kafka ACK 速率在目标附近但低于 4,600 次/秒。四组网络直连校准每组
发 32,000 次，稳定发送窗口内各秒接收数约为 4,600。500 ms 延迟时，直接传输最多同时占用
2,365 个名额，而真实 Projector 跨目标并发的短轮峰值为 661。逐条等回执的峰值是 32。
热路由的并发短轮中，Kafka 派发许可平均约 22–24 ms，PG 意图投影平均约 4–5 ms。
两项都位于每个分区的发送前路径上。


## 输入积压和内存

100 ms 回执的较长对照向 Kafka 提交 92,000 个新操作，持续按目标速率投入约 20 秒。
生产者实际确认 4,587 条/秒。投入窗口结束时只有 13,411 条远端回执到达。约 101 秒时
才全部收到，吞吐 909 次/秒，4,000 个沙箱各收到 23 个命令。20.3 秒处的样本同时观察到
78,168 条 Kafka lag 与 104 个已预留的派发名额。该轮名额峰值为 207。

这里有三项不同的内存开销：

- 在一个独立的长测进程中，建立 4,000 条已就绪连接耗时约 2.0 秒，连接前后 Projector
  进程 RSS 约为 197 与 247 MiB。模拟器和生产者各在其他进程。
- 单测接收链路、每台等待 500 ms 时，128,000 次的长轮最多占用 2,374 个名额。稳定发送
  窗口的完整秒内，接收端平均每秒收到约 4,600 次。默认上限 3,072 个名额，按包体上界预留
  总计 12 MiB。这项预算只约束待发和待回执的命令包。
- 上述端到端 92,000 次、100 ms 的长轮里，Projector 的 RSS 从约 504 升至 581 MiB，
  排空时派发名额为 0。RSS 还包括 WebSocket、Kafka 预取、运行时堆以及原型保留的原生
  待回包记录。这组试验覆盖派发接单，不能验证全天工作负载的进程内存上限。

单独把派发上限降为 128 个，回执仍为 500 ms。在 8,000 条输入中观察到的名额峰值
恰为 128，最多预留 512 KiB，Kafka lag 峰值 7,486 条，最终均按序送达。
这正是资源不足时预期的背压位置。Kafka 客户端自己的预取缓冲另计。

## 派发许可的成本

在同样的 32 分区与 RF3 Kafka 上，先用两项不发送命令的对照定位热路径：

| 32,000 条输入 | 处理速率 | 实际行为 |
|---|---:|---|
| 仅位点确认 | 2,068 条/秒 | 消费并验证测试记录，逐条取得真正的 Kafka 位点确认，不写工具 PG 记录 |
| 仅意图投影 | 4,172 条/秒 | 使用原型正常的路由与 PG 意图投影，扣住所有外部派发许可 |

第一项的 32,000 次位置请求在原生客户端合成了 1,610 次提交，平均每次涵盖约 20 个分区位置。
从调用客户端原生提交到收到回调平均 7.8 ms，单个逻辑许可平均等 9.7 ms。包含 PG 和网络的
92,000 次长轮则合成 9,353 次原生提交，逻辑许可平均耗时约 18.6 ms。这些数字含客户端
调度与回调，不能全部解释为 broker 网络 RTT。PG 对照保留普通消费进度的后台提交。

换序复测 32,000 条输入，只做 PG 为 4,257 条/秒，只做 Kafka 许可为 2,530 条/秒。
后者有 1,382 次原生提交。再将派发窗口限定为 128，释放一个名额只唤醒可获得它的
等待者，500 ms 下得到 247 次/秒，等待容量的分区回调峰值为 32。放开到原实验窗口后，
500 ms、12,000 次的复测得到 1,218 次/秒，实际名额峰值 849。该轮核对到 12,000 个
异步 PG 投影事务和 12,000 个远端接单。耗时会随共享主机状态和测试窗口变化。

## 结论

在本机的单 Projector、32 分区配置下，把低频调用分散给大量沙箱能解除单 VM 热点，
跨目标重叠回执也能明显缓解慢设备造成的分区等待。但同时保留每条意图 PG 投影和
逐条 Kafka 派发许可时，测出的持续处理速率仍低于每秒 4,600 次。增加等待名额
不能省掉同一分区下一条命令开始前的许可等待。

无模拟延迟的 92,000 次长轮提供了独立证据：生产端实际 ACK 速率为 4,594 条/秒，
全部接单用时 92.0 秒，约 1,000 次/秒，Kafka lag 峰值 68,911 条。另一次先在 Kafka
中备好 48,000 条，再放行消费，生产端为 4,584 条/秒，排空速率 874 次/秒。还有一次
48,000 条、500 ms 的同时生产/消费，生产端自身只达 3,026 条/秒，这一轮端到端收齐为 788 次/秒。

后续若评估改变位点确认粒度，需明确同一分区一次确认多条后，崩溃时可能有多少条已获
许可却尚未发出。当前分支仅增加隔离实验，不据此改动正式服务的派发与恢复协议。
