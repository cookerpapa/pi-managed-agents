# Ordinary root conversation on the candidate store

Issue [#52](https://github.com/cookerpapa/pi-managed-agents/issues/52) needs a public conversation and its next Worker to agree about what happened. This experiment selects the candidate as the only native writer for an ordinary root. The API still uses the existing tables for tenants, Sessions, admissions and leases. The production composition stays on its current store under [#48](https://github.com/cookerpapa/pi-managed-agents/issues/48).

## What the user and the next model observe

1. Submit a prompt using the Chrome chat composer. The first Worker claims its Run and the embedded Pi Harness issues a Bash call. The real Cube Guest appends a physical execution marker and waits. Reload the page during the wait and check the running tool and its arguments.
2. Release the shell command. Bash reads a random value from the Guest. The Worker receives the ordinary Kafka reply and Pi commits the canonical tool result and final answer. Verify that the result replaces the pending tool with the same task identity and command.
3. Close and recreate the Session API and Projector, discarding the first owner's in-memory state. Reload the same conversation and submit a second prompt. A separate Worker process cold-loads the candidate PG records. Its deterministic model inspects the actual request and requires exactly one prior tool proposal, one matching result, the previous answer and both user messages. Its answer quotes the value taken from the tool result. Reload Chrome again and count both answers and one completed tool.

The fixture uses the product React application, HTTP admission and history, SSE, the Session Projector, real Run claims, the pinned Pi Durable Harness, RF3 Kafka, PG and the fixed Bash Guest. The fixture starts a fresh Worker process for each admitted Run. It supplies a matched Worker storage adapter, a fixed sandbox binding and a deterministic model. The database identity serving reads and native writes has direct access to zero legacy native/history relations. The fixture also compares row counts in seven legacy storage tables before and after the two Runs.

## Storage and recovery

- The Run header supplies the initial prompt. A page selects bounded message positions before fetching full bodies. A result can recover its original input via the assistant Entry ID even on a separate page. A pending tool carries the original task ID and validated input until settlement. The navigation read selects a bounded caption from the same row.
- Text fragments reach the browser through the ordered Kafka/SSE path. Accepted stable messages and their display coverage are materialized together. An ordinary terminal transaction publishes the new cold-history head, retires the Run and its lease, advances progress, and clears the execution route. The acceptance aborts the first transaction after writing the history head. On retry an independent PG connection still sees the old Run running, no terminal event, no new head and a partition cursor at or before the failed record. The second attempt commits and the Guest marker still counts one Bash execution.
- Opening the chat page also reads the pending-input and manual-compaction status and the navigation tree. These root readers use the candidate's current values. A root input with attachment metadata is rendered from its human text and attachment references; model-facing file annotations stay out of the transcript.

## Acceptance and limits

The [browser result](normal-root-message-store-20261122.json) contains only aggregate assertions. The tool's physical execution marker, actor identities, prompts, random result and credentials stay out of the report. The harness removes its Guest and checks removal of its reply topics and consumer groups. One earlier browser trial emitted a Kafka consumer restart with only the generic error class recorded. The following HTTP and Chrome trials completed. The earlier error message does not identify its cause. The existing transport regression group passed 22 tests. The seven selected conversation/storage files passed 73 tests, including the candidate history regression. The separate PG history test covers single-record pages, tool anchors across settlement, byte limits, tenant scope, original human uploads, navigation and command lookup.

This is a two-Run functional acceptance. It does not measure throughput or actual provider latency. Prior mixed-load results apply to the measured Projector configuration in the [capacity report](tool-loop-capacity-20261121.md). The next integration gate is an in-flight human input, its confirmed delivery and Stop/Worker replacement through the same public surface. Compacted multi-tool families, Fork mutation, accounting and the full serving Worker composition still need matched acceptance before a release.
