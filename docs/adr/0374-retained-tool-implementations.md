# ADR-0374. Retain ordinary Tool implementations for in-flight requests

Accepted for the isolated independent Session candidate. An ordinary platform Tool binds to the implementation presented in the model request. The Worker uses that round's definitions for Pi argument validation, for all parallel or sequential calls, and for the Kafka intent. After the tool round, the next model request adopts the latest published directory. The active selection can be reconstructed on Worker handoff.

During a versioned Tool-host activation, the operator runs each code release at a trusted release-specific internal address. PG selects the new generation and grants the superseded generation a bounded acceptance window in the same transaction. Keep the old executable reachable through that window and drain its accepted operations before retiring it. Ordinary delisting updates discovery. An admitted intent addresses its original release and generation, including when another tool caused the new publication. Once the window expires an unstarted invocation receives a definite refusal. A transport loss after submission has an unknown outcome and does not authorize trying another release.

An authenticated operator can disable a Tool by name across all retained versions. The PG mutation simultaneously revokes admission and changes the published directory. The check immediately preceding the host's acceptance is the ordering point for concurrent disable and execute. A request admitted earlier can finish. Re-enabling publishes a new generation while previously revoked pins remain invalid. The authenticated result travels through the original reply mailbox.

MCP credentials and connection withdrawal retain ADR-0373 business admission. Guest programs and device executors retain their own lifecycle. This candidate uses ordinary HTTP endpoint routing and the existing catalog, PostgreSQL and operator release authority.

## Operating the candidate

1. Start the existing code-owned Tool host with the candidate entry point `scripts/experiments/minimal-session-storage/tool-host-main.mjs`. Supply the normal Tool host secrets and settings plus `PI_CLOUD_TOOL_HOST_VERSION_URL`, a stable internal URL dedicated to this executable and manifest. Each concurrently retained release needs an independently reachable address. `PI_CLOUD_TOOL_HOST_GRACE_MS` defaults to 604800000 (seven days), matching the candidate Session log's retention horizon. PG measures the interval from the activation that supersedes a generation. Kafka measures record retention from its own log timestamps. Keep each superseded executable reachable until its recorded deadline and drain accepted operations afterwards.
2. The independent Projector connects using `connectToolHost({url, token, brokers, versioned:true})`. Start independent Workers with `versionedTools:true`. They subscribe to the compacted catalog. The candidate's ordinary-tool composition exposes platform handlers with no Workspace preparation requirement, including the built-in schedule tool. Workspace operations and named delegation continue on their separate paths.
3. For upgrades, bring up the new host alongside the old one. Use the authenticated `/internal/v1/tools/manifest` and `POST /internal/v1/tools/activate` with its `releaseId`, manifest `revision` and current `expectedGeneration`. Removing a tool from the new executable's manifest is an ordinary delisting. The old handler remains addressable during the grace period. On the old host, wait until `retention.current` is false and `retention.acceptUntil` is null, then drain active operations before terminating that host. A single Recreate deployment cannot supply this overlap. The serving chart cutover remains separate.
4. To stop new admissions immediately, an authenticated operator posts `{"name":"export_report","disabled":true,"expectedGeneration":7}` to `/internal/v1/tools/availability` on the current host. Read the current generation from the manifest. A successful response includes the new generation. Repeat with `disabled:false` and that generation to enable future requests. After a lost response, read the selected manifest before retrying. All retained hosts consult the same durable revocation at admission, even before subscribers receive the new catalog.
5. Run `npm run test:segment-mcp` against disposable PG and RF3 Kafka. It also starts separate PDF and spreadsheet fixture executables, switches incompatible argument schemas while the provider is sampling, and exercises delisting, immediate disable, re-enable, old-version expiry, and Worker replacement during sampling. The final round uses the built-in schedule handler.
